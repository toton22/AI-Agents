The big idea

Most "AI agent" projects that fail do not fail because the model was weak. They fail because the team picked the wrong shape. They built a fully autonomous agent for a job that was really a three-step checklist, then spent months chasing the agent's creative detours.

A design pattern is a reusable shape for wiring model calls, tools and people together. You already know these shapes from organisations. An assembly line. A triage desk that sends each case to the right specialist. A project manager who breaks work up and hands it out. A maker-checker arrangement, the "four eyes" principle every Indian bank runs on, where one person prepares and another verifies before anything goes out. AI systems use the same shapes, with model calls in some of the seats.

The most useful distinction comes from Anthropic's December 2024 essay "Building effective agents". It separates two families:

  • Workflows: "systems where LLMs and tools are orchestrated through predefined code paths." You decide the steps; the model does the work inside each step.
  • Agents: systems where the model dynamically directs its own process and tool use. The model decides the steps.

Workflows are predictable, cheaper and easier to test. Agents are flexible and handle the unexpected, at the cost of predictability. The same essay gives the advice this page is built on: find the simplest solution possible, and add complexity only when it clearly pays for itself.

Manager's lens

When a vendor or your own team proposes "an autonomous agent", ask them to draw it. If the drawing has fixed boxes and arrows, it is a workflow, and that is good news: workflows are easier to audit, cost less per run and fail in predictable ways. Pay for autonomy only where the path genuinely cannot be known in advance, such as open-ended research or a messy customer case. Autonomy is a cost line, not a badge.

How it works

There are five workflow patterns and a handful of agent patterns. Learn their shapes once and you will spot them inside every framework and vendor product.

Workflow patterns

Prompt chaining. Break the task into fixed steps, where each model call works on the previous one's output. Put a check (a "gate") between steps, so a bad intermediate result stops the line instead of polluting everything downstream. For the Deal Desk: extract the request details, check they are complete, draft the reply, then format it. Use it when the task splits cleanly into stages and accuracy matters more than speed.

Routing. Classify the input first, then send it to a specialised handler. Each handler can have its own prompt, tools and even its own (cheaper or stronger) model. Customer service runs on this: billing questions go one way, delivery complaints another. Use it when inputs fall into distinct types that need different treatment.

Parallelisation. Run independent pieces at the same time, then combine the results in code. Two flavours. Sectioning splits a task into independent parts: check the tier cap, the margin rule and the credit position simultaneously. Voting runs the same task several times and compares answers: three independent reviews of a contract clause, flag it if any one says "risky". Use it for speed, or when several perspectives raise confidence.

Orchestrator-workers. A lead model looks at the task, decides what subtasks it needs (the number and kind are not known in advance), hands them to worker calls, and synthesises the results. A competitive review that needs "however many competitors are relevant" fits this. The difference from parallelisation is that the subtasks are decided at run time, not by you.

Evaluator-optimizer. One call generates, another evaluates against clear criteria and returns feedback, and the generator revises. Loop until it passes or you hit a limit. This is maker-checker for machines. It works when you can write down what "good" looks like (a rubric, a policy, a style guide) and when a revision based on feedback usually helps. Customer emails, contract summaries and translations are natural fits.

Agent patterns

ReAct (reason and act). The model alternates between thinking ("I need the customer's tier"), acting (calling a tool), and observing the result, until it can answer. Yao and colleagues introduced the idea in 2022, and nearly every tool-using agent you will meet today runs some version of this loop. It is the default agent shape in this course.

Plan-and-execute. The model writes a plan first, then works through it step by step, revising the plan when results surprise it. Better than pure ReAct for long tasks where losing the thread is the main risk, and the written plan is something a human can review before anything runs.

Reflection or self-critique. The model reviews its own output before finishing: "Did I check the margin rule? Does my email promise more than was approved?" Reflexion (Shinn and colleagues, 2023) and Self-Refine (Madaan and colleagues, 2023) showed that this kind of feedback loop can improve results on many tasks. It is the evaluator-optimizer pattern with one model in both seats, which is cheaper but shares the same blind spots.

Tool use. The model decides which function to call and with what arguments, as in Module 04. Every other agent pattern sits on top of it.

Human-in-the-loop. At defined points the agent stops and asks a person: approve this discount, confirm this payment, choose between these options. Not a weakness. In regulated work it is the design. The Deal Desk's rule "never promise a discount above policy without approval" is this pattern.

Choosing the simplest pattern that works

Think of the patterns as a ladder. Start at the bottom and climb only when a real test shows the current rung is not enough.

  1. One good model call

    A clear prompt with the right context. Many "agent" ideas end here, and that is a win.

  2. Add retrieval or a tool

    Ground it in your documents (Module 05) or let it fetch one live fact.

  3. Chain, route or parallelise

    Fixed workflow shapes. Predictable, testable, cheap.

  4. Add an evaluator

    When you can write the rubric and errors are costly.

  5. Orchestrator or ReAct agent

    When the steps truly cannot be known in advance.

  6. Multiple agents

    When one agent's context, tools or permissions are overloaded. Expensive; see Module 08.

Four questions decide the rung. Can I write the steps down in advance? If yes, use a workflow. Do inputs fall into clear types? Route. Can I write down what "good" looks like? Add an evaluator. What does a mistake cost, and who must sign off? That tells you where the human checkpoint goes, whatever the pattern.

Hands-on: route and check

The Deal Desk has made its decision. Now it must write the email to the customer, and this is where things go wrong in real life: a friendly draft that "softens" an escalation into a promise. We will route the decision to the right email template, then run a maker-checker loop that blocks any draft promising more than was approved.

This works in n8n, Make or Power Automate. Node names below are n8n's; the others have equivalents (Router in Make, Switch or Condition in Power Automate).

  1. Start from the decision

    The previous step (your Deal Desk agent) outputs structured fields: customer, asked_pct, approved_pct, status (approve, escalate or decline) and reason. If your agent outputs prose, add a structured-output step first. Routing on prose is guessing.

  2. Route

    Add a Switch node on status with three outputs. Because the decision is already structured, you do not even need a model to route here. That is the simplest pattern working. Use an LLM classifier only when the input is free text, such as an inbound customer email.

  3. Draft on each branch

    On each branch, add an LLM node with the branch's instruction. Approve: "Confirm the exact % and that it applies to the next order only." Escalate: "Do NOT promise any discount. Say it is with a manager; reply within 1 working day." Decline: "Say no politely, give the policy reason in one line, offer one alternative."

  4. Check

    Merge the branches into one LLM "Reviewer" node. Give it the facts and the rubric: never state a discount above approved_pct; promise nothing if status is escalate; under 120 words; no internal margin figures. Ask for JSON: {"pass": true/false, "problems": [...]}.

  5. Loop with a limit

    An IF node on pass. True: send to the salesperson for a final glance. False: pass the problems back to the drafting node and increment a counter. After three failed rounds, stop and route to a human with the draft and the problems listed.

# deal_email.py  -  routing + evaluator-optimizer for the Deal Desk reply
import os, json
import anthropic

client = anthropic.Anthropic()                       # reads ANTHROPIC_API_KEY
MODEL = os.getenv("MODEL", "claude-sonnet-5-5")
CHEAP_MODEL = os.getenv("CHEAP_MODEL", MODEL)        # a smaller model is fine for routing

def ask(prompt: str, model: str = MODEL, max_tokens: int = 600) -> str:
    msg = client.messages.create(model=model, max_tokens=max_tokens,
                                 messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text

# ---------- 1. ROUTING: what kind of email is this? ----------
ROUTES = {
    "approve": "Confirm the discount warmly. State the exact % and that it applies to the next order only.",
    "escalate": "Do NOT promise any discount. Say the request is with a manager and give a reply time of 1 working day.",
    "decline": "Say no politely, give the policy reason in one line, and offer one alternative (e.g. volume bundle).",
}

def route(decision: dict) -> str:
    prompt = ("Classify this Deal Desk decision into exactly one label: approve, escalate or decline.\n"
              f"Decision: {json.dumps(decision)}\nReply with the label only.")
    label = ask(prompt, model=CHEAP_MODEL, max_tokens=5).strip().lower()
    return label if label in ROUTES else "escalate"   # unknown label -> safest route

# ---------- 2. GENERATE ----------
def draft(decision: dict, label: str, feedback: str = "") -> str:
    prompt = (f"Write a short email (under 120 words) from a Meridian Supplies salesperson to the customer.\n"
              f"Facts: {json.dumps(decision)}\nInstructions: {ROUTES[label]}\n"
              + (f"Fix these problems from the reviewer: {feedback}\n" if feedback else "")
              + "Return only the email body.")
    return ask(prompt)

# ---------- 3. EVALUATE ----------
RUBRIC = """Check the email against these rules. Return JSON only:
{"pass": true/false, "problems": ["..."]}
1. It never states a discount higher than approved_pct.
2. If status is escalate, it promises no discount at all.
3. Under 120 words, polite, no internal margin figures.
4. Names the customer correctly."""

def evaluate(email: str, decision: dict) -> dict:
    out = ask(f"{RUBRIC}\n\nFacts: {json.dumps(decision)}\n\nEmail:\n{email}", max_tokens=300)
    try:
        return json.loads(out[out.find("{"): out.rfind("}") + 1])
    except ValueError:
        return {"pass": False, "problems": ["Reviewer output was not valid JSON"]}

# ---------- 4. LOOP: draft -> check -> fix, at most 3 rounds ----------
def write_reply(decision: dict, max_rounds: int = 3) -> dict:
    label = route(decision)
    feedback = ""
    for attempt in range(1, max_rounds + 1):
        email = draft(decision, label, feedback)
        verdict = evaluate(email, decision)
        if verdict.get("pass"):
            return {"route": label, "email": email, "rounds": attempt}
        feedback = "; ".join(verdict.get("problems", []))
    return {"route": label, "email": email, "rounds": max_rounds,
            "needs_human": True, "open_problems": feedback}

if __name__ == "__main__":
    decision = {"customer": "Bluewave Logistics", "asked_pct": 6, "approved_pct": 0,
                "status": "escalate", "reason": "2 late payments: cap is 3%"}
    print(json.dumps(write_reply(decision), indent=2))

What this does, part by part:

  • ask is a one-line helper around the Messages API so the rest of the code reads like a process, not plumbing.
  • Routing. route asks a (possibly cheaper) model for one of three labels. If the answer is anything else, it falls back to "escalate", the safest route, because a wrongly routed escalation costs a day while a wrongly routed approval costs margin. Each route has its own instruction in ROUTES.
  • Generator. draft writes the email from the facts plus the route's instruction, and on later rounds includes the reviewer's complaints.
  • Evaluator. evaluate checks the draft against a written rubric and returns JSON. If the reviewer's reply is not valid JSON, the draft fails rather than slipping through.
  • Loop. write_reply runs draft, check, fix up to three times. If it still fails, it returns the last draft flagged needs_human with the open problems, instead of sending something that broke the rules.
Make the checker stricter than the maker

Some rules do not need a model at all. "Never state a discount higher than approved_pct" can also be checked in code: pull every number followed by % from the draft and compare. Use code for what code can check, and the model evaluator for tone and judgement. Even better, give the evaluator a different model or a different provider, so the two seats do not share the same blind spots.

In the business

Case · Customer service

Routing an e-commerce inbox

An Indian online retailer's support inbox mixed refund requests, delivery complaints, product questions and abuse. A single "do everything" agent kept applying refund logic to delivery complaints. The team replaced it with a router (a small, fast model) and four handlers, each with its own tools and tone. Misroutes still happen, so every handler can bounce a case back to the router once, and anything bounced twice goes to a person. The handlers are now tested separately, which made weekly prompt changes much less risky.

Case · Finance

An invoice chain with gates

A distribution company's accounts payable team built a prompt chain: extract fields from the PDF invoice, match against the purchase order and goods receipt, validate the GSTIN and tax split, then propose the ERP posting. Each step has a gate in code. A missing PO number stops the chain at step one with a clear message, instead of producing a plausible posting with a guessed PO. No agent autonomy anywhere; that was the point. Auditors liked it because each step leaves a record.

Case · Marketing

Maker-checker for campaign copy

A consumer brand's marketing team uses an evaluator-optimizer loop for social and search ad copy. The evaluator's rubric covers brand voice, banned claims ("best", "guaranteed" without substantiation), and the ASCI code points the legal team flagged. The generator revises up to three times. Copy that still fails goes to the brand manager with the reviewer's notes attached, which turned out to be a useful training tool for junior copywriters too.

Case · Supply chain

Parallel quote comparison

A manufacturer's procurement team receives five to eight supplier quotes per tender, each in a different format. A parallel workflow extracts each quote into the same template at once (price, lead time, payment terms, warranty, exceptions), then code builds the comparison table. A second, voting-style step has three independent passes flag unusual terms. The buyer gets the table and the flags; the award decision stays with the buyer and the approval matrix.

Pitfalls

  • An agent where a workflow would do. If you can draw the steps, draw them in code. Autonomy adds cost, latency and new failure modes.
  • The rubber-stamp evaluator. The same model, same prompt style, checking its own work, tends to approve it. Use a different model, a stricter rubric, and code checks for hard rules.
  • Loops without limits. Evaluator loops and ReAct loops must have a maximum round count and a defined hand-off to a person.
  • Routing with no fallback. Every router needs a safe default for "none of the above" and a way for a handler to bounce a misrouted case.
  • Pattern stacking. Routing into orchestrators into evaluators into sub-agents: each layer multiplies cost and makes failures harder to trace. Add one layer at a time and measure.
  • Hidden human checkpoints. "A human reviews it" on the slide, but the review screen has an Approve-all button and a 40-item queue. Design the checkpoint so a person can actually judge.
  • Vague rubrics. "Make it professional" is not checkable. "Under 120 words, no margin figures, names the customer" is.
Measure before you climb

Before adding a pattern, run the simpler version against 30 to 50 real cases and note where it fails. If the failures are about missing facts, add retrieval, not an evaluator. If they are about tone, add an evaluator, not an orchestrator. Patterns fix specific failure types; Module 10 shows how to measure them.

Practice

  1. Name the pattern

    Which pattern fits each? (a) Summarise 40 call transcripts, one summary each. (b) Turn a vendor contract into a risk memo: extract, assess, write. (c) Reply to inbound emails that could be orders, complaints or job applications. (d) Write a press release that legal must approve against a checklist.

    Hint / model answer

    (a) Parallelisation (sectioning). (b) Prompt chaining, with a gate after extraction. (c) Routing. (d) Evaluator-optimizer for the checklist, plus a human-in-the-loop sign-off from legal.

  2. Climb down the ladder

    A colleague proposes a multi-agent system to answer HR leave questions from a 10-page policy. Argue for the lowest rung that works, and say what evidence would make you climb.

    Hint / model answer

    One model call with the policy in context (or a no-code assistant with the file attached). Climb only if testing on real questions shows specific failures, for example missing location-specific rules (add retrieval with metadata) or the need to check leave balances (add one tool).

  3. Write the rubric

    Write a five-point rubric for an evaluator that checks Meridian's "approve" emails. Each point must be checkable as yes or no.

    Hint / model answer

    1. States exactly approved_pct, no other percentage. 2. Says it applies to the next order only. 3. Names the customer correctly. 4. Contains no internal margin or cost figures. 5. Under 120 words and ends with a clear next step.

  4. Break the router

    In the Python version, what happens if the routing model replies "Escalate." with a capital E and a full stop? Trace it and suggest a fix.

    Hint / model answer

    .strip().lower() gives "escalate." which is not in ROUTES, so it falls back to "escalate". The result happens to be right, but by luck. Strip punctuation too, or better, skip the model: route on the structured status field, as in the no-code version.

  5. Design with a checkpoint

    Pick a process from your own organisation (or a past internship). Draw it as a pattern from this page, mark where a person must decide, and estimate what a mistake at each step would cost.

    Hint / model answer

    A good answer names the pattern, shows the fixed steps or the agent loop, places the checkpoint where an error becomes expensive or irreversible (money leaves, a customer is told something, a record is changed), and states the round or step limits.

Quiz

What separates a workflow from an agent, in Anthropic's framing?

  1. In a workflow, code fixes the path; in an agent, the model directs its own steps and tool use
  2. Workflows cannot call tools
  3. Agents always involve several models
  4. Workflows do not use language models

Workflows orchestrate models and tools through predefined code paths. Agents decide their own process. Both can use tools and models.

You must check every supplier quote for the same five things, and quotes are independent. Which pattern fits best?

  1. Orchestrator-workers
  2. Routing
  3. Parallelisation (sectioning)
  4. ReAct

The subtasks are known in advance and independent, so run them at once and combine in code. Orchestrator-workers is for when the subtasks are only known at run time.

The evaluator in a maker-checker loop keeps approving drafts that break the rules. What is the best first fix?

  1. Raise the number of rounds to ten
  2. Remove the evaluator
  3. Ask the generator to be more careful
  4. Make the rubric concrete, check hard rules in code, and consider a different model as reviewer

Rubber-stamping comes from vague rubrics and shared blind spots. Checkable rules, code checks and a different reviewer model address the cause; more rounds do not.

Which of these is NOT one of Andrew Ng's four agentic design patterns?

  1. Reflection
  2. Routing
  3. Planning
  4. Multi-agent collaboration

Ng's four are reflection, tool use, planning and multi-agent collaboration. Routing is one of the workflow patterns from Anthropic's essay.

In the Kite Fintech trace, why does the agent escalate even though 5% is within the Bronze cap?

  1. Kite has late payments
  2. Bronze customers always need approval
  3. Margin after discount would be 11%, below the 12% floor
  4. 5% is above 15%

16 minus 5 is 11, which breaks the margin rule. Both rules must pass. Kite has no late payments.

The routing model returns a label that is not on the list. What does a well-designed router do?

  1. Falls back to the safest route and logs it
  2. Picks a route at random
  3. Sends the case to the approve handler
  4. Retries forever until it gets a valid label

A safe default (here, escalate) limits damage, and the log tells you the router needs work. Defaulting to approve is the most expensive mistake.

Key takeaways

  • Workflows fix the path in code; agents let the model choose. Prefer workflows wherever you can draw the steps.
  • The five workflow patterns: prompt chaining, routing, parallelisation, orchestrator-workers, evaluator-optimizer.
  • The core agent patterns: ReAct, plan-and-execute, reflection, tool use and human-in-the-loop.
  • Ng's four (reflection, tool use, planning, multi-agent collaboration) map onto the same ideas.
  • Climb the ladder one rung at a time, and only when tests show the current rung failing.
  • Every loop needs a round limit and a hand-off to a person; every router needs a safe default.
  • Check hard rules in code, and give the checker a different model or a stricter rubric than the maker.
