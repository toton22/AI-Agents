The big idea

The Deal Desk agent works on your laptop. Congratulations: you are about 20% of the way there.

The other 80% is everything a laptop hides. Who is allowed to use it, and how do they sign in? Where does the API key live? What happens at 11 a.m. on the last day of the quarter, when 40 salespeople hit it at once and the model provider is having a slow day? How much will it cost by month-end? When a Sales Manager says "it told Asha she could give 10% to Bluewave", can you find that exact conversation, see which tools ran, and prove what the agent knew? And when Tuesday's prompt change makes things worse, how fast can you put Monday's version back?

LLMOps is the name for the discipline that answers those questions. It borrows from DevOps and MLOps, then adds the parts that are special to agents: versioning prompts and model choices as carefully as code, running evals before every release, tracing multi-step tool use, and keeping token spend under control.

None of this is glamorous. It is also where most agent pilots quietly die. The demo impressed the leadership team, then the project hit IT security review, procurement, identity integration and a cost question nobody could answer, and six months later it was still a pilot.

Manager's lens

A pilot that five enthusiasts use is not a product. "In production" means five things exist: a named owner, a support route for users, a budget line with alerts, an incident and rollback plan, and evidence (evals, logs) that you could show an auditor. Ask for those five before you call anything live, and budget real time for them; they usually take longer than building the agent.

How it works

A reference architecture

Every production agent, whether built in Copilot Studio or in Python, ends up with roughly the same parts. Naming them helps you ask the right questions of any vendor or internal team.

In plain words, for the Deal Desk:

  • Channels are where people meet the agent: a Teams app for salespeople, perhaps a panel inside the CRM later. WhatsApp matters more for customer-facing agents in India than for internal ones.
  • The gateway is the front door. It checks who you are (single sign-on), applies rate limits, and rejects junk before it costs money.
  • The orchestrator runs the agent loop you built in M04: call the model, run tools, repeat.
  • The policy engine holds rules that must never depend on the model's mood: discount caps, approval thresholds, who may see what. In M11 that was the policy_check() function.
  • The model router sends each call to a suitable model: a small, fast one for simple lookups, a stronger one for the decision and the reply.
  • Tools and MCP servers connect to the ERP, CRM and approval workflow (see M09). Knowledge is the policy library and any retrieval index (M05). Memory keeps session history (M06).
  • Observability records every step: traces, latency, token cost, eval scores and the audit log.

Identity, secrets and data residency

Identity. Users sign in with their company account (Microsoft Entra ID, Okta, Google Workspace) through single sign-on. No shared passwords, no "everyone uses the same API key". Then decide whose permissions the agent uses when it calls a tool. Either it acts on behalf of the user, so a salesperson in Pune only sees Pune accounts, or it uses its own service identity with tightly scoped rights. On-behalf-of is better for anything involving personal or confidential data, because existing access controls keep working.

Secrets. API keys and database passwords live in a secrets manager (Azure Key Vault, AWS Secrets Manager, Google Secret Manager or similar), are injected at runtime, and are rotated on a schedule. Never in code, never in the container image, never in a prompt.

Data residency in India. Map where each kind of data sits: prompts and replies in transit to the model, conversation memory, audit logs, traces in your observability tool, and any vector index. All the major clouds run regions in India, but a given model or agent feature is not always available in every region, so check before you commit. The DPDP Act permits transfers abroad except to countries the government restricts, but sector rules can be stricter (the RBI's payment-data storage directive is the classic example), and many enterprise customers write in-country processing into contracts anyway. The practical rule: decide residency up front and choose the hosting option that satisfies it, rather than discovering the problem in a security review.

Observability and tracing

When something goes wrong with an agent, the question is always "what exactly happened on that request?" A trace answers it: one record per request, broken into spans for each model call and tool call, with timings, token counts, inputs and outputs. Here is what a trace for one Deal Desk request might look like, with the timings an operations dashboard would show.

Bluewave Logistics wants 6% off. (request 9f2c41d07a3b · user asha.k · agent v1.4.0)
Model call 1 · 1.6 s · 2,940 tokens in / 48 out. Need the customer record.
find_customer(name="Bluewave Logistics") · 140 ms
{"id":"C-102","tier":"Silver","late":2,"margin":18}
Model call 2 · 1.4 s · 3,080 in / 61 out. Two late payments: cap is 3%. Check policy to be sure.
get_discount_policy() · 35 ms
"Max discount by tier: ... 2 or more late payments this FY are capped at 3% ..."
Model call 3 · 1.9 s · 3,310 in / 92 out. 6% is above the 3% cap. Escalate to Sales Manager.
request_approval(customer_id="C-102", discount_pct=6, approver="Sales Manager", reason="2 late payments; cap 3%") · 410 ms
"APR-3B81E0 created and PENDING with Sales Manager."
Model call 4 · 1.3 s. DECISION: ESCALATE, ticket APR-3B81E0. Total 6.8 s · 4 model calls · 13,100 tokens · policy check passed.

Notice where the time goes: about 6.2 of the 6.8 seconds are model calls. That is typical, and it tells you where to look when users complain about speed.

Tools for this, as of 2026, include Langfuse (open source, self-hostable), LangSmith, Arize Phoenix, and the observability services built into the cloud agent runtimes. Many now speak OpenTelemetry, the open standard for traces, which has a set of generative-AI conventions that are still evolving. Using OpenTelemetry means you can switch observability vendors without re-instrumenting your code, a lock-in question worth asking early.

Watch out

Traces contain everything the agent saw, including personal data. Redact before you send them to a third-party tool, restrict who can view them, and set a retention period. Your observability platform is now part of your DPDP footprint.

Cost: a worked rupee model

Agent costs surprise people because each user request triggers several model calls, and each call resends the growing conversation plus all the tool definitions. Here is a monthly model for the Deal Desk. Every number below is an assumption, labelled so you can swap in your own. Prices in particular are placeholders, not any vendor's real rate card.

#AssumptionValue
A1Users × requests per day × working days40 × 3 × 22 = 2,640 requests a month
A2Model calls per request (loop turns)4
A3Tokens per call3,000 in (of which 2,000 are the fixed system prompt and tool definitions), 250 out
A4Main model price (placeholder)₹250 per million input tokens, ₹1,250 per million output tokens
A5Small model price (placeholder)One-fifth of the main model
A6Cached input price (placeholder)10% of normal input price; cache-write premiums ignored for simplicity
A7Eval runs12 cases × 3 repeats × 20 runs a month = 720 agent runs
A8Hosting, tracing, log storage (placeholders)₹12,000 + ₹8,000 + ₹2,000 a month

Per request at baseline: 12,000 input tokens × ₹250 per million = ₹3.00, plus 1,000 output tokens × ₹1,250 per million = ₹1.25. So ₹4.25 a request, ₹11,220 a month for production traffic. Now apply two standard optimisations.

Line item (₹ a month)Baseline+ Prompt caching+ Caching and model routing
Model cost per request₹4.25₹2.45₹1.47
Production traffic (2,640 requests)₹11,220₹6,468₹3,881
Eval runs (720)₹3,060₹1,764₹1,058

Total₹36,280₹30,232₹26,939
All-in cost per request₹13.74₹11.45₹10.20

Prompt caching reuses the fixed 2,000-token prefix (system prompt and tool definitions) across calls at a discount; the arithmetic is 4 calls × (1,000 × ₹250 + 2,000 × ₹25) per million, plus output. Model routing sends two of the four calls (the simple lookups) to a small model at one-fifth of the price. Together they cut model cost by about two-thirds.

Here's the thing, though. At Meridian's scale, after optimisation, the fixed platform costs are most of the bill. Token cost only dominates at much higher volumes, say a customer-facing agent handling lakhs of conversations a month. So the cost levers differ by stage: for an internal pilot, keep the platform lean; for a high-volume agent, caching, routing and token budgets (a hard cap on tokens per request and per user per day, enforced at the gateway) matter a great deal. Either way, set a monthly budget alert at 80% of plan.

Latency

Users of a chat tool start to notice delays after a few seconds and give up somewhere past 15 to 20. Since model calls dominate, the main fixes are: fewer turns (one good tool that returns customer, policy cap and margin together beats three small ones), parallel tool calls where the model supports them, a smaller model for simple steps, streaming the reply so the first words appear quickly, and timeouts with a graceful fallback ("I've passed this to the deal desk") instead of a spinner. Track latency at the median and at p95, the slowest 5%, because complaints come from the slow tail.

Versioning, rollback and incidents

An agent's behaviour depends on more than its code. The real unit of release is a bundle: code, system prompt, tool definitions, model ID and version, policy rules and a snapshot reference to the knowledge base. Give the bundle one version number (Deal Desk 1.4.0), store it in source control, and log that number on every trace. Then "what changed?" always has an answer.

Rollback should be a button, not a project: redeploy the previous bundle, or flip a feature flag that routes traffic back to it. Rehearse it once during the pilot. Pin model versions where your provider allows it, so a provider-side change does not arrive unannounced.

Incident response for agents follows the usual pattern with a few additions. Define severities up front (a wrong discount promised to a customer is high severity; a slow reply is low). Keep a kill switch that turns the agent off and shows users a fallback message. Then the runbook: contain (kill switch or rollback), find the affected requests in the traces, notify the people affected and, if personal data was involved, your DPO for DPDP breach obligations, fix the cause, and add the failing case to the golden set so it can never silently return.

Deployment checklist

  • Named business owner and technical owner; support route published to users
  • Single sign-on for users; agent's tool permissions scoped (on-behalf-of where possible)
  • All secrets in a vault, rotated; nothing sensitive in prompts or images
  • Data residency decided for prompts, memory, logs, traces and indexes; vendor DPA signed
  • Golden set passing in CI; release blocked on regression
  • Guardrails from M11 in place: allow-list, policy check in code, approval gate, PII redaction
  • Tracing on every request with agent version, user, tokens, latency and cost
  • Rate limits, token budgets and a monthly spend alert
  • Model version pinned; bundle versioned in source control
  • Rollback rehearsed; kill switch tested; incident runbook written
  • Log and trace retention periods set and documented
  • Users told what the agent can and cannot do, and how to reach a human

Pilot to scale: a 30-60-90 day plan

Two rules make this plan work. First, agree the exit criteria for each phase before day 1: for example, "zero unapproved above-policy discounts in shadow mode" and "median request time down from 25 minutes to under 5". Second, measure the baseline during the pilot, because without "before" numbers you cannot prove "after" (that is the whole subject of M13).

Hands-on: ship the Deal Desk

You will wrap the guarded agent from M11 in a small web service, package it as a container, and call it the way Teams or the CRM would. Put these files next to deal_desk_agent.py.

1. app.py: the HTTP front door.

"""HTTP front door for the Deal Desk agent. Run: fastapi run app.py --port 8000"""
import logging
import os
import time
import uuid

from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel, Field

from deal_desk_agent import run

AGENT_VERSION = os.getenv("AGENT_VERSION", "dev")
API_KEYS = {k for k in os.getenv("DEAL_DESK_API_KEYS", "").split(",") if k}

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("deal_desk")
app = FastAPI(title="Meridian Deal Desk", version=AGENT_VERSION)


class DealRequest(BaseModel):
    message: str = Field(min_length=5, max_length=2000)
    user: str = Field(min_length=3, max_length=120)


class DealResponse(BaseModel):
    request_id: str
    decision: str
    approver: str | None
    reply: str
    agent_version: str
    seconds: float


@app.get("/health")
def health():
    return {"status": "ok", "agent_version": AGENT_VERSION}


@app.post("/v1/deal-desk", response_model=DealResponse)
def deal_desk(req: DealRequest, x_api_key: str = Header(default="")):
    if x_api_key not in API_KEYS:                 # empty key list = nobody gets in
        raise HTTPException(status_code=401, detail="Invalid or missing API key")
    request_id = uuid.uuid4().hex[:12]
    start = time.perf_counter()
    try:
        result = run(req.message, user=req.user)
    except Exception:
        log.exception("agent_error request_id=%s", request_id)
        raise HTTPException(status_code=502, detail=f"Agent error. Quote ref {request_id}")
    seconds = round(time.perf_counter() - start, 2)
    log.info("request_id=%s user=%s decision=%s seconds=%s version=%s",
             request_id, req.user, result["decision"], seconds, AGENT_VERSION)
    return DealResponse(request_id=request_id, decision=result["decision"],
                        approver=result.get("approver"), reply=result["reply"],
                        agent_version=AGENT_VERSION, seconds=seconds)

What this does, in plain English:

  • DealRequest and DealResponse define exactly what callers may send and what they get back. FastAPI rejects anything else automatically: an empty or 10,000-character message gets a 422 error before it costs a rupee.
  • /health is what the hosting platform pings to check the service is alive. It also reports the agent version.
  • /v1/deal-desk checks an API key sent in the x-api-key header. If no keys are configured, nobody gets in; the service fails closed. In a real deployment the gateway would handle SSO and pass the verified user identity; the key here stands in for that.
  • Each request gets a request_id, is timed, and is logged with user, decision, latency and agent version, so you can find it later.
  • If the agent throws an error, the user gets a polite 502 with a reference number, and the full error goes to the log, not to the user.

2. requirements.txt: pinned versions, so the container you test is the container you ship.

fastapi[standard]==0.143.0

3. Dockerfile: the recipe for the container image.

FROM python:3.12-slim
WORKDIR /code
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py deal_desk_agent.py ./
RUN useradd --create-home appuser && chown -R appuser /code
USER appuser
ENV AGENT_VERSION=1.4.0
EXPOSE 8000
CMD ["fastapi", "run", "app.py", "--port", "8000"]

What this does: starts from a slim official Python image, installs the pinned packages, copies in the two Python files, creates a non-root user (so a compromised process has fewer rights), stamps the agent version, and starts the app with fastapi run, which uses the Uvicorn server underneath. Note what is missing: no API keys. Secrets are passed in at run time.

4. Build, run and call it.

# 1. Build an image tagged with the agent version
docker build -t meridian/deal-desk:1.4.0 .

# 2. Run it locally; secrets come from your shell, never from the image
docker run --rm -p 8000:8000 \
  -e ANTHROPIC_API_KEY \
  -e DEAL_DESK_API_KEYS \
  meridian/deal-desk:1.4.0

# 3. In another terminal, call it the way Teams or the CRM would
curl -s http://localhost:8000/v1/deal-desk \
  -H "Content-Type: application/json" \
  -H "x-api-key: $MY_KEY" \
  -d '{"message": "Bluewave Logistics wants 6% off", "user": "asha.k"}'

Set DEAL_DESK_API_KEYS to a comma-separated list of keys and MY_KEY to one of them before running. You should get something like:

{
  "request_id": "9f2c41d07a3b",
  "decision": "escalate",
  "approver": "Sales Manager",
  "reply": "DECISION: ESCALATE\nBluewave has 2 late payments this year, so the cap is 3%. I have raised APR-3B81E0 with the Sales Manager for 6%.",
  "agent_version": "1.4.0",

From here, the same image runs on any container platform: Azure Container Apps, Cloud Run, ECS, Kubernetes, or a cloud agent runtime that accepts containers. In production you would add the pieces from the checklist: secrets from a vault rather than shell variables, the audit log shipped to central logging rather than a local file, and a tracing library sending spans to your observability tool.

If you built the Deal Desk in Copilot Studio (see the Copilot Studio method page), publishing it to Teams takes minutes. Getting it approved for the whole company takes your Teams admin. Labels below follow Microsoft's documentation as of 2026; screens change, so check the linked docs.

  1. Set authentication first

    In the agent's security settings, choose Microsoft authentication so only signed-in Meridian employees can use it. Microsoft advises not changing this after the agent is added to Teams, since users may then hit permission errors.

  2. Publish the agent

    Select Publish. An agent must be published at least once before channels can use it, and again after every change you want users to see.

  3. Add the Teams channel

    Go to Channels and open the Teams and Microsoft 365 Copilot tile. Keep "make agent available in Microsoft 365 Copilot" ticked if you want it there too, then select Add channel.

  4. Test it yourself

    Select See agent in Teams, then Add. Run the M10 golden set and the M11 red-team list in Teams, not only in the test pane; channel behaviour can differ.

  5. Pilot with named users

    Under Availability options, choose Show to my teammates and shared users and share the agent with your 20 pilot salespeople. It appears for them in the Teams app store's "Built with Power Platform" section.

  6. Request organisation-wide rollout

    When the pilot passes, choose Show to everyone in my org and Submit for admin approval. Your Teams admin reviews and approves it in the admin centre, after which it appears under "Built for your org". Changes to the agent's details need a fresh submission; content-only updates do not.

  7. Watch it

    Use Copilot Studio's analytics for sessions, escalations and abandonment, and agree with IT where conversation transcripts are stored and for how long.

Tip

Ask your admin about environments early. Building in a separate development environment and moving finished versions to production gives you the same versioning and rollback discipline as the Python path, without code.

In the business

Case · Supply chain

The loop that ate the budget

A logistics company's shipment-status agent called a tracking API that sometimes returned "try again". The agent dutifully tried again, and again, inside a single conversation. Nobody noticed until the monthly model bill arrived at several times the forecast. The fixes were textbook LLMOps: a step limit per request, a daily token budget per channel at the gateway, a cost-per-conversation panel on the operations dashboard, and an alert at 80% of the monthly budget.

Case · HR

A helpdesk agent with the wrong keys

An HR helpdesk agent on Teams answered leave and payroll questions. In the pilot it read the HR system through a service account with broad access, which meant a cleverly worded question could surface a colleague's data. Before scaling, the team switched to on-behalf-of access: the agent now calls HR systems with the signed-in employee's own permissions, so it can never see more than the person asking.

Case · Finance

Residency decided on day one

A mid-sized Indian private bank wanted an agent to help relationship managers prepare credit notes. Its risk team required that customer data stay in India and that every interaction be auditable for years. The architecture was chosen to fit: a cloud agent runtime in an Indian region with a model available there, self-hosted tracing inside the bank's own network, and redaction before anything reached a log. Choosing this up front avoided the common fate of a pilot rebuilt from scratch after the security review.

Case · Customer service

When the model provider had a bad hour

A consumer brand's WhatsApp support agent depended on a single model provider. During a provider outage, customers saw nothing at all. The post-incident changes: a fallback model behind the router, a timeout after which customers get "we've passed this to our team, reference number…", a status check on the provider in the dashboard, and an incident runbook that names who decides to switch providers.

Pitfalls

The pilot that never ends. No exit criteria, no baseline, no decision date. Set go/no-go criteria for each phase before day 1, and put a date on the decision.

Unversioned prompts. The system prompt lives in a web console and gets edited in place. When behaviour changes, nobody can say what changed or roll it back. Prompts belong in version control, inside the release bundle.

Floating model versions. Pointing at "the latest model" means the provider can change your agent's behaviour without a release on your side. Pin versions and upgrade deliberately, after evals.

Costs measured per token, not per outcome. Token price per million tells you little. Cost per completed request, and cost per request that actually saved someone time, tell you whether the agent pays.

Observability that leaks. Full prompts and replies, with personal data, sent to a third-party tool with default retention. Redact, restrict access and set retention.

No owner after go-live. The project team moves on, the agent keeps running, the policy changes and nobody updates the agent or its golden set. Every production agent needs a named owner with time in their week for it; see M13.

Shadow IT agents. Teams build agents on personal accounts or unapproved platforms because the official route is slow. Make the paved road (approved platform, templates, checklist) faster than the shortcut.

Practice

  1. Draw your architecture

    Redraw the reference architecture for a customer-facing WhatsApp agent that answers order-status questions for Meridian's school customers. Which boxes change, and what new risks appear?

    Hint / model answer

    Channels become WhatsApp via a Business API provider; the gateway must handle unauthenticated users, so you need customer verification (an OTP or a registered number) before any order data is shown. Transparency duties apply: tell users they are talking to an AI. The tools must be scoped to the verified customer only. Data residency now covers the messaging provider too.

  2. Re-run the cost model

    Meridian decides to open the Deal Desk to its 120-person inside-sales team, each making 5 requests a day. Recompute monthly cost at baseline and with caching plus routing, using the same assumptions. At what point do token costs exceed the fixed platform costs?

    Hint / model answer

    120 × 5 × 22 = 13,200 requests. Baseline model cost 13,200 × ₹4.25 = ₹56,100; with caching and routing 13,200 × ₹1.47 = ₹19,404. With ₹22,000 fixed costs, baseline tokens already exceed platform costs; with optimisation they roughly match. Optimisation now saves about ₹36,700 a month, which is worth an engineer's attention.

  3. Write a rollback runbook

    Version 1.5.0 of the Deal Desk goes live on a Monday. By Tuesday noon, three Sales Managers report that it is escalating every Gold-tier request. Write the runbook steps from first report to closure.

    Hint / model answer

    Acknowledge and assign an incident lead; check the traces for Gold requests since the release; roll back to 1.4.x via the feature flag; confirm escalations return to normal; tell users what happened; find the cause (often a prompt or policy-rule edit); add Gold boundary cases to the golden set; re-release through the full pipeline.

  4. Choose a hosting option

    For each company, pick SaaS platform, cloud runtime or self-hosted container, and justify in two sentences: (a) a 300-person firm on Microsoft 365 with no developers; (b) a bank with strict residency and a platform team; (c) a SaaS startup building agents into its product.

    Hint / model answer

    (a) SaaS, Copilot Studio: identity and Teams are already there and nobody needs to run servers. (b) A cloud runtime in an Indian region or self-hosted containers in its own network, chosen by where approved models are available. (c) A cloud runtime or containers, since the agent is part of the product and needs portability and control.

  5. Design the ops dashboard

    Sketch the one-screen dashboard the Deal Desk agent owner looks at every morning. Name at most eight tiles and say what would trigger action on each.

    Hint / model answer

    Requests yesterday; success rate from online checks; escalation rate versus last week; p95 latency; cost per request and month-to-date spend versus budget; error rate; guardrail blocks (policy-check overrides, refused tools); user feedback (thumbs down). Each needs a threshold, for example policy-check overrides above zero triggers a review of the prompt.

Quiz

In the reference architecture, which component should enforce the discount caps and approval thresholds?

  1. The model router
  2. The memory store
  3. The policy engine (deterministic code)
  4. The channel (Teams)

Rules involving money and authority belong in deterministic code the orchestrator consults, not in the model or the user interface.

Why is "on-behalf-of" identity often better than a broad service account for an HR agent?

  1. The agent can only see what the signed-in user is already allowed to see
  2. It makes the model faster
  3. It removes the need for audit logs
  4. It is required by the EU AI Act

Existing access controls keep working, so a clever question cannot surface a colleague's data. It does not replace logging (c), and (d) overstates the law.

In the worked cost model, why does optimisation barely change the total bill at Meridian's pilot scale?

  1. Caching does not work for agents
  2. Small models are more expensive
  3. Evals cost more than production
  4. Fixed platform costs (hosting, tracing, logs) dominate at low volume

Model cost drops by about two-thirds, but ₹22,000 of fixed costs remain. At higher volume, token costs dominate and the same optimisations matter far more.

What is the right "unit of release" for an agent?

  1. The Python code only
  2. A versioned bundle of code, prompt, tool definitions, model version, policy rules and knowledge snapshot
  3. Whatever the model provider currently serves
  4. The system prompt only

Behaviour depends on all of these. Versioning them together is what makes "what changed?" answerable and rollback possible.

The trace shows 6.2 of 6.8 seconds spent in model calls. Which fix is most likely to help?

  1. A faster database
  2. More logging
  3. Fewer model turns, for example one tool that returns customer, cap and margin together, plus streaming the reply
  4. Moving the gateway to a different region

Time goes where the trace says it goes. Cutting turns and streaming attack the model time; the database (a) is already fast.

In Copilot Studio, what is needed before a Deal Desk agent shows up for everyone in the company's Teams?

  1. Nothing; adding the Teams channel makes it visible to all
  2. Submitting it for admin approval and having a Teams admin approve it
  3. Rewriting it in Python
  4. A Microsoft support ticket

Adding the channel lets you and shared users install it. Organisation-wide availability goes through "Show to everyone in my org" and admin approval.

Key takeaways

  • The laptop demo is a fraction of the work. Production means an owner, support, a budget, a rollback plan and audit evidence.
  • Know the reference architecture: channels, gateway, orchestrator, policy engine, model router, tools, knowledge, memory and observability.
  • Pick hosting by your existing cloud, skills and data rules: SaaS platform, cloud agent runtime or self-hosted container.
  • Use SSO, on-behalf-of access where possible, a secrets vault, and a residency decision made on day one.
  • Trace every request; model cost per request and per month with labelled assumptions; cache, route and budget tokens.
  • Release versioned bundles through eval gate, shadow and canary; rehearse rollback; run a 30-60-90 plan with agreed exit criteria.
