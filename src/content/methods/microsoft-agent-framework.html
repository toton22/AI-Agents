Microsoft used to have two agent projects that overlapped awkwardly. AutoGen, from Microsoft Research, made multi-agent conversations popular. Semantic Kernel was the enterprise SDK that many .NET shops used to wire models into their applications. In October 2025 Microsoft announced Microsoft Agent Framework (MAF), one open-source framework that takes the agent ideas from AutoGen and the enterprise plumbing from Semantic Kernel. It shipped as a public preview that month, and version 1.0 of the Python package appeared on PyPI in April 2026.

As of October 2026, MAF is the stable, recommended path. The core packages are past 1.0 and release frequently (this page was checked against 1.21). Some connectors, such as Copilot Studio, are still marked preview. AutoGen's repository now says it is in maintenance mode and points new users to MAF, and Semantic Kernel's repository describes MAF as its successor. Both have official migration guides.

The framework has two main parts. Agents are a model plus instructions, tools, middleware and sessions (conversation memory). Workflows are graphs of "executors" joined by edges, with checkpoints, human-in-the-loop requests and ready-made multi-agent orchestrations: sequential, concurrent, handoff, group chat and Magentic. Around them: OpenTelemetry tracing, a developer UI, and hosting on Microsoft Foundry (formerly Azure AI Foundry).

Manager's lens

If your company already runs on Microsoft 365, Entra ID and Azure, MAF is the path of least resistance with your IT and security teams: the identity, hosting, monitoring and procurement are already in place. That is a real advantage. The risk is the mirror image: the more Foundry services you build on, the harder it is to leave. Keep your tools as plain Python functions and you keep your options open.

When to pick it

Pick MAF when you are a Microsoft shop, when you have .NET developers as well as Python ones (the APIs are deliberately parallel), or when you are migrating an existing AutoGen or Semantic Kernel project. It is also a solid general-purpose choice: it works with OpenAI, Anthropic, Ollama and other providers, not only Azure.

Its workflow engine is a good fit for processes with approvals and long waits, similar in spirit to LangGraph. The built-in orchestrations (handoff, group chat, Magentic) give you multi-agent patterns without writing the coordination yourself.

Look elsewhere if your team wants the smallest possible dependency (the full install pulls in many integration packages; install only what you need), if you need a no-code tool (Copilot Studio is Microsoft's low-code option), or if you have no Azure footprint and prefer another ecosystem's hosting.

Strengths

  • One framework for agents and workflows, in Python and .NET
  • Tool approval built in (approval_mode="always_require")
  • Workflows with checkpoints and human requests
  • OpenTelemetry tracing out of the box
  • Natural fit with Entra ID, Azure and Foundry

Watch-outs

  • Fast release pace; older preview-era samples may not match 1.x
  • Many tutorials online still show AutoGen or Semantic Kernel code
  • The full package installs a lot; prefer selective installs in production
  • Some connectors remain preview as of 2026
  • Foundry-specific features increase switching cost

How it works

Start on the left. A chat client talks to one model provider: OpenAIChatClient, FoundryChatClient, and others. Swap the client and the rest of your code stays the same.

An agent wraps a client with instructions and tools. Tools can be plain Python functions; MAF reads the type hints and docstring. Wrap a function with tool(approval_mode="always_require") and the agent will stop before calling it, returning an approval request instead. Your app shows the request to a person, sends back their yes or no, and the agent continues. A session holds the conversation, including the pending approval, so the answer is tied to the right request.

A workflow is a graph. Each node is an executor: a class with @handler methods, or a function with @executor. Executors pass typed messages along edges with ctx.send_message() and produce final results with ctx.yield_output(). When an executor needs a person, it calls ctx.request_info(); the workflow pauses and the run result lists the open requests. You answer by running the workflow again with responses={request_id: answer}, and a @response_handler method picks it up. Add a checkpoint store and the pause can outlive the process.

The orchestrations package builds common multi-agent workflows for you, for example SequentialBuilder(participants=[analyst, writer]).build(). And because every agent and workflow emits OpenTelemetry traces, you can watch runs in Azure Monitor, or in any OpenTelemetry-compatible tool you already use.

Step 2: the tools (meridian_tools.py)

"""meridian_tools.py - the Deal Desk agent's tools, in plain Python.

In a real company these functions would call the CRM and the ERP.
Here they read a small in-memory table so the whole agent runs on a laptop.
"""
import difflib
from datetime import datetime

CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian Supplies discount policy (FY 2026-27)
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""

TIER_CAP = {"Bronze": 5, "Silver": 8, "Gold": 12}
MARGIN_FLOOR = 12
APPROVALS = []  # stands in for your ticketing system


def get_customer(customer_id: str) -> dict:
    """Return the customer record for an id such as C-101."""
    record = CUSTOMERS.get(customer_id.strip().upper())
    return record or {"error": f"No customer with id {customer_id}"}


def find_customer(name: str) -> dict:
    """Fuzzy lookup by customer name. Returns the best-matching record."""
    by_name = {c["name"].lower(): c for c in CUSTOMERS.values()}
    query = name.strip().lower()
    for full_name, record in by_name.items():
        if query and (query in full_name or full_name in query):
            return record
    close = difflib.get_close_matches(query, list(by_name), n=1, cutoff=0.5)
    return by_name[close[0]] if close else {"error": f"No customer matching '{name}'"}


def get_discount_policy() -> str:
    """Return the current discount policy text."""
    return POLICY


def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % left after the discount (simplified: margin minus discount)."""
    return round(current_margin_pct - discount_pct, 2)


def request_approval(customer_id: str, discount_pct: float, approver: str, reason: str) -> str:
    """Log an approval request for a discount above policy. A named person must decide."""
    ticket = f"APR-{len(APPROVALS) + 1:04d}"
    APPROVALS.append({"ticket": ticket, "customer_id": customer_id, "discount_pct": discount_pct,
                      "approver": approver, "reason": reason,
                      "raised_at": datetime.now().isoformat(timespec="seconds")})
    return f"{ticket} logged with {approver} for {discount_pct}% on {customer_id}."


def evaluate_request(customer: dict, discount_pct: float) -> dict:
    """The policy written as code: the same rules, checked the same way every time."""
    cap = 3 if customer["late_payments_fy"] >= 2 else TIER_CAP[customer["tier"]]
    margin_after = margin_after_discount(customer["gross_margin_pct"], discount_pct)
    problems = []
    if discount_pct > cap:
        problems.append(f"{discount_pct}% is above the {cap}% cap")
    if margin_after < MARGIN_FLOOR:
        problems.append(f"margin after discount would be {margin_after}%, below the {MARGIN_FLOOR}% floor")
    approver = None
    if problems:
        approver = "Regional Head" if discount_pct > 15 else "Sales Manager"
    return {"within_policy": not problems, "cap_pct": cap, "margin_after_pct": margin_after,
            "problems": problems, "approver": approver}

What this does: the customer table and discount policy from the course case, five plain tool functions, and evaluate_request, the policy written as code. MAF builds tool descriptions from each function's name, type hints and docstring, so no decorators are needed except where you want behaviour such as approval.

Step 3: one agent with an approval gate (maf_agent.py)

"""maf_agent.py - Deal Desk as a single Microsoft Agent Framework agent with an approval gate."""
import asyncio

from agent_framework import Agent, Message, tool
from agent_framework.openai import OpenAIChatClient

import meridian_tools as mt

# Plain functions work as tools. The escalation tool is wrapped so it never runs unseen.
request_approval = tool(approval_mode="always_require")(mt.request_approval)

agent = Agent(
    client=OpenAIChatClient(),     # reads OPENAI_API_KEY and OPENAI_MODEL from the environment
    name="DealDesk",
    instructions=(
        "You are the Deal Desk assistant at Meridian Supplies, Pune. Look the customer up, read "
        "the discount policy and compute the margin with the tool. Approve only within every "
        "rule and draft a short reply. Otherwise call request_approval and never promise the "
        "discount. request_approval only runs after the approver says yes; if it is rejected, "
        "say so and offer the within-policy maximum. Quote the numbers you used."),
    tools=[mt.find_customer, mt.get_customer, mt.get_discount_policy,
           mt.margin_after_discount, request_approval],
)


async def main():
    session = agent.create_session()     # keeps history, including the pending approval
    result = await agent.run(input("Salesperson: "), session=session)

    while result.user_input_requests:    # the agent paused at the gate
        answers = []
        for req in result.user_input_requests:
            print(f"\nAPPROVAL NEEDED: {req.function_call.name} {req.function_call.arguments}")
            ok = input("Approve? (y/n): ").strip().lower() == "y"
            answers.append(Message("user", [req.to_function_approval_response(ok)]))
        result = await agent.run(answers, session=session)

    print("\n" + result.text)


if __name__ == "__main__":
    asyncio.run(main())
# Foundry version of maf_agent.py: change two imports and one argument.
# Setup once:  pip install azure-identity   (already included with agent-framework)
#              az login                      (a managed identity replaces this when deployed)
#              export FOUNDRY_PROJECT_ENDPOINT="<your Foundry project endpoint>"
#              export FOUNDRY_MODEL="<your model deployment name>"
from agent_framework.foundry import FoundryChatClient
from azure.identity import AzureCliCredential

# in Agent(...), replace  client=OpenAIChatClient()  with:
#     client=FoundryChatClient(credential=AzureCliCredential()),

What changes: the agent now calls a model deployed in your Foundry project, and it authenticates with your Azure identity instead of an API key. On a server, a managed identity takes the place of az login, which means no secret to rotate or leak.

What this does:

  • tool(approval_mode="always_require")(mt.request_approval) wraps the escalation tool so the framework will not run it on the model's say-so. The other four tools are passed as plain functions and run freely.
  • Agent(client=..., name=..., instructions=..., tools=[...]) is the whole agent. The instructions include the order of work and the rule about never promising a discount.
  • agent.create_session() creates the conversation memory. Every call passes the same session, so the approval answer is matched to the pending request. MAF ignores approval responses that do not match a pending request in the session, which stops a replayed or forged "yes".
  • After each run, result.user_input_requests lists any tool calls waiting for approval. The loop shows each one, asks for y or n, and sends back to_function_approval_response(ok).
  • When nothing is pending, result.text is the reply.

Like every model-led design, this version relies on the model to recognise that Kite at 5% breaks the margin rule. The gate guarantees no escalation goes out unseen; it does not guarantee the model escalates when it should. That is what the workflow fixes.

Step 4: the workflow version (maf_workflow.py)

"""maf_workflow.py - the policy decision as a deterministic workflow; the model only writes."""
import asyncio
from dataclasses import dataclass

from typing_extensions import Never
from agent_framework import (Agent, Executor, WorkflowBuilder, WorkflowContext,
                             executor, handler, response_handler)
from agent_framework.openai import OpenAIChatClient

import meridian_tools as mt


@dataclass
class DealRequest:            # what the salesperson's form sends
    customer_name: str
    discount_pct: float


@dataclass
class DealCase:               # what the policy gate hands to the writer
    customer: dict
    discount_pct: float
    verdict: dict
    decision: str


@dataclass
class ApprovalNeeded:         # what the human approver sees
    ticket: str
    question: str
    case: DealCase


class PolicyGate(Executor):
    @handler
    async def check(self, req: DealRequest, ctx: WorkflowContext[DealCase]) -> None:
        customer = mt.find_customer(req.customer_name)
        if "error" in customer:
            raise ValueError(customer["error"])
        verdict = mt.evaluate_request(customer, req.discount_pct)
        case = DealCase(customer, req.discount_pct, verdict, "")
        if verdict["within_policy"]:
            case.decision = "approved within policy"
            await ctx.send_message(case)
            return
        ticket = mt.request_approval(customer["id"], req.discount_pct, verdict["approver"],
                                     "; ".join(verdict["problems"]))
        question = (f"{verdict['approver']}: allow {req.discount_pct}% for {customer['name']}? "
                    f"Problems: {'; '.join(verdict['problems'])}")
        await ctx.request_info(ApprovalNeeded(ticket, question, case), str)   # pause here

    @response_handler
    async def on_decision(self, request: ApprovalNeeded, decision: str,
                          ctx: WorkflowContext[DealCase]) -> None:
        request.case.decision = decision
        await ctx.send_message(request.case)


writer = Agent(client=OpenAIChatClient(), name="DealWriter",
               instructions="Write short, warm, accurate replies for Meridian Supplies' sales team. "
                            "Offer only what the decision allows.")


@executor(id="draft")
async def draft(case: DealCase, ctx: WorkflowContext[Never, str]) -> None:
    reply = await writer.run(f"Customer: {case.customer}. Asked: {case.discount_pct}%. "
                             f"Policy check: {case.verdict}. Decision: {case.decision}. Draft the reply.")
    await ctx.yield_output(reply.text)


gate = PolicyGate(id="policy_gate")
workflow = WorkflowBuilder(start_executor=gate).add_edge(gate, draft).build()


async def main():
    result = await workflow.run(DealRequest("Bluewave Logistics", 6))
    while requests := result.get_request_info_events():
        answers = {}
        for event in requests:
            print("\nAPPROVAL NEEDED:", event.data.question, f"[{event.data.ticket}]")
            answers[event.request_id] = input("Decision (e.g. 'approve 4%' or 'reject'): ")
        result = await workflow.run(responses=answers)
    print("\n" + result.get_outputs()[0])


if __name__ == "__main__":
    asyncio.run(main())

What this does:

  • Three small data classes describe what flows through the graph: the salesperson's request, the case after the policy check, and the question shown to the approver.
  • PolicyGate is an executor. Its check handler looks the customer up and runs evaluate_request. Within policy, it sends the case straight on. Otherwise it raises a ticket and calls ctx.request_info(...), which pauses the workflow and publishes the question.
  • on_decision, marked @response_handler, receives the approver's answer, records it on the case and sends the case on.
  • draft is a function executor that asks the writer agent for a reply and yields it as the workflow's output. It is the only model call.
  • WorkflowBuilder(start_executor=gate).add_edge(gate, draft).build() wires the two steps together.
  • main runs the workflow, answers any open requests with workflow.run(responses=...), and prints the output.

Taking it to production

Identity and SSO

This is where MAF fits most naturally. Use Entra ID for the people (salespeople and approvers) and managed identities for the service itself, so the agent reaches Foundry models without API keys. Microsoft's own guidance is to prefer a specific credential, such as ManagedIdentityCredential, over DefaultAzureCredential in production. Map approver roles to Entra groups so only Sales Managers can answer Sales Manager requests.

Data access

Tools call your CRM and ERP with a least-privilege identity. If the CRM is Dynamics 365 or data sits in SharePoint, keep access going through governed connectors rather than broad service accounts. Decide what reaches traces: the OpenTelemetry setup has an option to include or exclude sensitive message content, and for customer data under the DPDP Act 2023 you will usually exclude it outside development.

Hosting

Options as of 2026: your own container or Azure App Service behind an API; Azure Functions with Microsoft's durable extension for long-running agents; or Foundry hosted agents, which the MAF README describes as deploying an agent to Foundry-hosted infrastructure with a couple of extra lines. Choose an Azure region that meets your data residency needs; India has Azure regions, but check that the model you want is offered there.

Cost control

The workflow version makes one model call per request; the single agent makes several. Use the workflow for anything high-volume. Set tool invocation limits (max_invocations on a tool), use smaller model deployments for simple steps, and set Azure budgets and alerts on the Foundry resource.

Monitoring and approvals

Send OpenTelemetry traces to Azure Monitor or Application Insights and build a dashboard for escalation rate, latency and errors. For approvals, connect request_info or user_input_requests to Teams with an adaptive card or to a Power Automate approval, and add a checkpoint store so pending approvals survive restarts. Add expiry and no-self-approval rules, as on every page.

  • Managed identity for the service, Entra ID for users
  • Approver roles mapped to Entra groups
  • Sensitive content excluded from production traces
  • Checkpoint storage for paused workflows
  • Selective package install, versions pinned
  • Budget alerts on the Foundry resource

Practice

  1. Gate a second tool

    Suppose the agent can also email the customer through a send_reply tool. Which approval_mode would you use for it, and why?

    Hint / model answer

    always_require, at least during the pilot. Sending an email to a customer is an external action that cannot be undone. Once the team trusts within-policy replies, you might gate only replies that mention a discount above the cap.

  2. Two-step approval

    Orchid Schools Trust asks for 18%. Using the workflow, sketch how you would require both the Sales Manager and the Regional Head to approve.

    Hint / model answer

    Add a second executor after PolicyGate: if the first approval says yes and the discount is above 15%, it calls ctx.request_info again with a Regional Head question, and its response handler sends the case to draft. Alternatively, have on_decision raise the second request itself before sending anything on.

  3. Read an old tutorial

    You find a 2024 AutoGen tutorial with an AssistantAgent and a UserProxyAgent chatting. What are the MAF equivalents, and what would you check before reusing its design?

    Hint / model answer

    The assistant becomes an MAF Agent with tools; the user proxy's role (a human or code stepping in) becomes tool approval or a workflow request_info. Check whether the design relies on free-form agent chat to make decisions; for business rules, move them into an executor.

In the single-agent version, what happens when the model calls request_approval?

  1. The tool runs and the manager is emailed
  2. The run fails with an error
  3. The run returns with a user_input_request; the tool runs only after an approval response
  4. The model is asked to try a different tool

approval_mode="always_require" turns the call into a pending request. You send back to_function_approval_response(True or False) in the same session.

In the workflow, how does the PolicyGate executor pause for a person?

  1. It calls ctx.request_info(...), and a @response_handler receives the answer
  2. It raises an exception that the app catches
  3. It calls input() inside the handler
  4. It sends a message to the writer agent asking for approval

request_info publishes a request event and pauses; workflow.run(responses=...) delivers the answer to the response handler.

Why is the workflow version safer for Kite Fintech at 5% than the single agent?

  1. It uses a larger model
  2. It has more tools
  3. It runs on Foundry
  4. The margin rule is applied in code by evaluate_request, not left to the model

The approval gate only controls what happens when the model escalates; the workflow makes sure escalation happens whenever a rule fails.

For a production service on Azure calling Foundry models, which authentication approach fits Microsoft's guidance best?

  1. An API key in the code
  2. A managed identity via a specific credential such as ManagedIdentityCredential
  3. A developer's az login session
  4. DefaultAzureCredential with every fallback enabled

A specific credential avoids secrets in code and the unintended fallbacks of DefaultAzureCredential; az login is for development.
