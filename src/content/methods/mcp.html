Every other method page on this site builds the Deal Desk tools inside one agent. That's fine until the second agent arrives. Then the third. Then someone wants the same customer lookup inside ChatGPT, and the IT team wants it in Copilot Studio. Before long you have five copies of get_customer, each with its own bugs and its own idea of who's allowed to call it.

The Model Context Protocol fixes that. MCP is an open standard for connecting AI applications to tools and data. You write a server once, describing your tools in a standard way. Any MCP-capable host (Claude Desktop, ChatGPT, Copilot Studio, VS Code, Cursor, your own agent) can connect to it and use those tools. It is often compared to USB-C for AI: one plug shape, many devices.

Anthropic introduced MCP in November 2024 and donated it to the Agentic AI Foundation, a Linux Foundation project, in December 2025. As of October 2026 the current specification revision is dated 2026-07-28; among other changes, it made MCP stateless at the protocol level, with no protocol sessions to manage. The official Python SDK moved to version 2 the same week. One rename to know: the high-level server class long known as FastMCP is now MCPServer. Code written for version 1 still runs if you pin mcp<2. (A separate community project called FastMCP, the fastmcp package, also exists and has its own API.)

This page is the hands-on companion to M09 Protocols: MCP and A2A, which covers the concepts in more depth.

Manager's lens

MCP turns "integrate system X with AI tool Y" from a project per pair into a project per system. That changes the economics. It also changes the risk: one server now feeds many AI apps, so its security and access rules matter more than any single agent's prompt.

When to pick it

Build an MCP server when a system will be used by more than one AI app or agent, or when you want business users to reach it from tools they already have. A CRM lookup, a policy library, a ticketing system, an ERP report: these are natural servers. Build it once, govern it once, and let the Claude Desktop users in sales, the Copilot Studio agents in service, and the developers in VS Code all share it.

It's also the cleanest way to keep tool logic out of agent code. Your agent framework can change next year; the MCP server doesn't have to.

Skip it for a single throwaway prototype where one agent uses one tool; a plain function in your framework is faster. And note that MCP is about tools and data, not about agents talking to each other. For agent-to-agent delegation, look at A2A (also in M09).

Strengths

  • One integration, many AI apps and frameworks
  • Tools, read-only resources and prompt templates in one package
  • Standard OAuth-based authorisation for remote servers
  • Good test tooling (MCP Inspector)
  • Supported by the major AI vendors as of 2026

Watch-outs

  • Each host supports a different subset of features
  • A server shared by many apps is a juicy target; security work is real
  • Tool descriptions and results flow straight into model context
  • Spec and SDKs have moved fast; pin versions

How it works

Three roles. The host is the AI application the user sees. Inside it, an MCP client holds the connection to one server. The server exposes capabilities. When the user asks a question, the host lists the server's tools, sends their descriptions to the model, and when the model picks a tool, the client calls the server and hands back the result.

The three things a server offers

Tools are actions the model can call: get_customer, request_approval. Most hosts ask the user before running one. Resources are read-only content identified by a URI, such as policy://meridian/discounts; the host or user decides when to attach them. Prompts are reusable templates the user picks from a menu, like a saved "check this deal" request. Not every host shows resources and prompts, so we also expose the policy as a tool.

Two transports

stdio: the host starts your server as a local program and talks through its standard input and output. Simple, private to one machine, no network port. Streamable HTTP: your server is a web service at a URL such as https://mcp.meridian.example/mcp, protected with OAuth bearer tokens. Use it for anything shared or cloud-hosted. The older SSE transport is deprecated; Copilot Studio, for one, has dropped it.

Watch out

A stdio server must never print to standard output. Those bytes are the protocol channel, and one stray print() breaks the connection. Log to standard error instead; the code below does.

Build the Meridian server

  1. Create the project

    The MCP docs use uv, a fast Python package manager. Install it, then create a project and add the pinned SDK with its command-line extras:

    uv init meridian-mcp && cd meridian-mcp
uv add "mcp[cli]==2.3.0"
# save the server below as meridian_server.py, then:
uv run mcp dev meridian_server.py                      # opens the MCP Inspector
# or, with Node 22.19+ installed:
npx @modelcontextprotocol/inspector uv run meridian_server.py
  2. Write the server

    Save as meridian_server.py:

    """Meridian Deal Desk MCP server: customer lookups, margin maths, approvals."""
import json
import logging
import os
from datetime import datetime, timezone
from pathlib import Path

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations

logging.basicConfig(level=logging.INFO)  # logs go to stderr, never stdout
log = logging.getLogger("meridian")

mcp = MCPServer(
    "meridian-deal-desk",
    instructions="Meridian Supplies tools for checking discount requests. "
                 "Read the discount policy before deciding. Never promise a "
                 "discount above policy without request_approval.",
)

APPROVALS_FILE = Path(os.getenv("MERIDIAN_APPROVALS_FILE", "approvals.jsonl"))

CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian discount policy (FY 2026-27)
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""

READ_ONLY = ToolAnnotations(read_only_hint=True, open_world_hint=False)


@mcp.tool(annotations=READ_ONLY)
def get_customer(customer_id: str) -> dict:
    """Return the Meridian customer record for an id such as 'C-101'."""
    record = CUSTOMERS.get(customer_id.strip().upper())
    if record is None:
        raise ToolError(f"No customer with id {customer_id}")
    return record


@mcp.tool(annotations=READ_ONLY)
def find_customer(name: str) -> dict:
    """Find a Meridian customer by (part of) their name, e.g. 'Sahyadri'."""
    hits = [c for c in CUSTOMERS.values() if name.lower() in c["name"].lower()]
    if len(hits) != 1:
        raise ToolError(f"{len(hits)} matches for '{name}': "
                         f"{[c['name'] for c in hits]}")
    return hits[0]


@mcp.tool(annotations=READ_ONLY)
def get_discount_policy() -> str:
    """Return Meridian's discount policy text."""
    return POLICY


@mcp.tool(annotations=READ_ONLY)
def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % left after a discount (simplified: margin minus discount)."""
    return round(current_margin_pct - discount_pct, 2)


@mcp.tool(annotations=ToolAnnotations(read_only_hint=False, destructive_hint=False,
                                      idempotent_hint=False, open_world_hint=False))
def request_approval(customer_id: str, discount_pct: float, approver: str,
                     reason: str) -> str:
    """Raise an approval ticket for an out-of-policy discount.
    approver must be 'Sales Manager' or 'Regional Head' (above 15%).
    Returns a PENDING ticket: do not promise the discount to the customer."""
    if approver not in ("Sales Manager", "Regional Head"):
        raise ToolError("approver must be 'Sales Manager' or 'Regional Head'")
    if discount_pct > 15 and approver != "Regional Head":
        raise ToolError("Discounts above 15% need the Regional Head")
    ticket = f"APR-{datetime.now(timezone.utc):%Y%m%d%H%M%S}"
    entry = {"ticket": ticket, "customer_id": customer_id, "discount_pct": discount_pct,
             "approver": approver, "reason": reason, "status": "PENDING"}
    with APPROVALS_FILE.open("a", encoding="utf-8") as f:
        f.write(json.dumps(entry) + "\n")
    log.info("Approval requested: %s", entry)
    return f"{ticket} PENDING with {approver}. Tell the salesperson it is under review."


@mcp.resource("policy://meridian/discounts", mime_type="text/plain")
def discount_policy() -> str:
    """Meridian's current discount policy."""
    return POLICY


@mcp.prompt()
def deal_check(customer_name: str, discount_pct: float) -> str:
    """Check a discount request against Meridian policy."""
    return (f"{customer_name} has asked for {discount_pct}% off their next order. "
            "Look up the customer, read the discount policy, compute the margin "
            "after discount, and either approve within policy with a two-line "
            "reply I can send, or raise request_approval with the right approver. "
            "Show the numbers you used.")


if __name__ == "__main__":
    mcp.run(transport="stdio")
  3. Test it in the Inspector

    uv run mcp dev meridian_server.py opens the MCP Inspector in your browser. Open the Tools tab, call find_customer with "Kite", call get_customer with "C-999" to see an error, read the resource, and fill in the deal_check prompt. If something fails here, it will fail in every host.

  4. Connect Claude Desktop

    Open claude_desktop_config.json (on macOS in ~/Library/Application Support/Claude/, on Windows in %APPDATA%\Claude\), add the server and restart Claude Desktop. Use absolute paths; you may need the full path to uv.

    {
  "mcpServers": {
    "meridian-deal-desk": {
      "command": "uv",
      "args": [
        "--directory",
        "/ABSOLUTE/PATH/TO/meridian-mcp",
        "run",
        "meridian_server.py"
      ],
      "env": { "MERIDIAN_APPROVALS_FILE": "/ABSOLUTE/PATH/TO/approvals.jsonl" }
    }
  }
}

What this code does, in plain English

  • MCPServer("meridian-deal-desk", instructions=...) creates the server. The instructions travel to every host that connects, so the house rules go with the tools.
  • logging.basicConfig sends logs to standard error, keeping standard output clean for the protocol.
  • @mcp.tool() turns a typed Python function into a tool. The SDK reads the name, the type hints and the docstring to build the description the model sees. Whatever the function returns goes back to the host; a dict arrives as JSON text.
  • ToolAnnotations label the four lookup tools as read-only and request_approval as a write that isn't destructive. Hosts use these hints to decide what to ask the user about. They are hints, not enforcement: the code is what actually stops bad calls.
  • ToolError sends a clear message back to the model ("No customer with id C-999"). In version 2 of the SDK, any other exception is reported only as a generic failure, so internal details such as database errors don't leak to the model or the user.
  • request_approval checks the approver is valid, enforces the 15% Regional Head rule in code, writes a PENDING ticket to a file and tells the model not to promise anything. In production this writes to your ticketing system.
  • @mcp.resource publishes the policy at a URI. @mcp.prompt publishes a template that a user can pick and fill with a customer name and discount.
  • mcp.run(transport="stdio") starts the server in local mode.

Taking it to production

Going remote over Streamable HTTP

Cloud hosts can't launch a program on your laptop, so a shared server must run as a web service. Three changes: attach a token verifier and auth settings to the server, switch the transport, and put it behind HTTPS. This version rejects any request without a valid bearer token (HTTP 401) and publishes the metadata that tells MCP clients where to get a token:

import hmac
import os

from mcp.server import MCPServer
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings


class SharedSecretVerifier:
    """Pilot only: accepts one bearer token kept in a secrets manager.
    In production, validate JWTs from your identity provider (Entra ID, Okta,
    Google) and check the audience is this server."""

    async def verify_token(self, token: str) -> AccessToken | None:
        if hmac.compare_digest(token, os.environ["MERIDIAN_MCP_TOKEN"]):
            return AccessToken(token=token, client_id="deal-desk-pilot",
                               scopes=["deals:read", "deals:approve"])
        return None   # -> HTTP 401


mcp = MCPServer(
    "meridian-deal-desk",
    token_verifier=SharedSecretVerifier(),
    auth=AuthSettings(
        issuer_url="https://login.meridian.example",           # your IdP
        resource_server_url="https://mcp.meridian.example/mcp",
        required_scopes=["deals:read"],
    ),
)

# ... the same @mcp.tool / @mcp.resource / @mcp.prompt functions as before ...

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8000)

In plain English: SharedSecretVerifier is the bouncer. Every request's bearer token goes through verify_token; a match returns who the caller is and what scopes they hold, anything else returns None and the request is refused. AuthSettings names your identity provider and this server's public URL, and requires the deals:read scope. The shared secret is a pilot shortcut. For production, verify JWTs issued by your identity provider (Microsoft Entra ID, Okta, Google) and check that each token was issued for this server.

Identity, data access and hosting

Run the server as a container on Cloud Run, Azure Container Apps, AWS App Runner or your Kubernetes cluster, with TLS at the load balancer. The server talks to the CRM with its own service account, read-only, scoped to the fields the tools return. Pass the end user's identity through from the token so tools can apply row-level rules (a salesperson sees their own accounts) and so every approval ticket records who asked.

Cost, monitoring and approvals

MCP itself costs nothing to run beyond hosting; model tokens are paid by the host. Watch tool-result size, though, because every byte a tool returns becomes tokens in someone's bill. Log every call with caller, tool, arguments and outcome, and alert on unusual volume. Keep approvals in your workflow system: the server raises tickets, managers decide in the tool they already use, and the agent checks status with another tool.

Security checklist for MCP servers

Drawn from the MCP security best-practices guide and hard experience. Go through it before any server leaves a laptop.

  • Remote servers require authentication; no anonymous endpoints, ever.
  • Accept only tokens issued for this server (check the audience); never pass a client's token through to downstream APIs. The spec forbids token passthrough.
  • Use narrow scopes (read versus approve) and ask for more only when a privileged tool is first used.
  • Bind any state handle (cart id, ticket id) to the authenticated user; possession of an id is not proof of identity.
  • Validate every input in code: ids, percentages, approver names. The model is not a validation layer.
  • Return only the fields the use case needs. Mask personal data covered by the DPDP Act 2023.
  • Treat tool descriptions and results as prompt-injection surfaces. Never put instructions from external data into descriptions; sanitise text you return from documents or emails.
  • Keep write tools few and explicit, annotate them honestly, and enforce limits server-side.
  • For local servers, prefer stdio; if you must use HTTP locally, require a token and bind to localhost. The v2 SDK turns on DNS-rebinding protection for localhost by default.
  • Pin SDK versions, review third-party servers before installing them, and only install servers from sources you trust; a local server runs with your user's permissions.
  • Log every call and review the logs. Rate-limit per user.

Practice

  1. Add a resource template

    Add a resource at customer://{customer_id}/summary that returns a one-paragraph summary of a customer. Test it in the Inspector. Why might a host prefer this over the get_customer tool?

    Hint / model answer

    Decorate a function with @mcp.resource("customer://{customer_id}/summary") taking customer_id: str; the placeholder becomes a parameter. Resources are read-only and attached by the user or host, so they suit "put this context in front of the model" without granting an action. Tools suit "let the model decide to fetch".

  2. Find the leak

    A colleague's version of get_customer returns the full CRM record, including contact person, mobile number and credit notes. List what's wrong and fix the tool's return value.

    Hint / model answer

    Personal data (contact name, mobile) isn't needed for a discount decision, so returning it breaks data minimisation under the DPDP Act and puts it into model context and host logs. Credit notes may be confidential. Return only id, name, tier, late payments and margin, which is what the policy needs.

  3. Plan the remote rollout

    Write a one-page plan to make the Meridian server available to Copilot Studio agents in customer service. Cover hosting, identity, scopes, DLP and logging.

    Hint / model answer

    Host on a container platform with HTTPS; register the server as an app in Entra ID; issue tokens with a read-only scope for service agents (no request_approval); connect through the Copilot Studio MCP wizard with OAuth 2.0; check your Power Platform DLP policy allows the connector; log caller and tool for every call; review logs weekly for the first month.

In MCP terms, what is Claude Desktop when it uses the Meridian server?

  1. A server
  2. A resource
  3. A host, containing an MCP client
  4. A transport

The host is the AI app the user sees; it runs one client per server connection. Your code is the server.

Why does the server log to standard error instead of using print()?

  1. With stdio transport, standard output carries the protocol messages; printing corrupts them
  2. print() is slower
  3. Standard error is encrypted
  4. MCP forbids logging

The MCP docs warn that writing to stdout breaks a stdio server. Log to stderr or a file.

You want Copilot Studio agents to use the Meridian server. What must be true?

  1. The server runs over stdio on each user's laptop
  2. The server uses the SSE transport
  3. The server has no authentication, so Copilot can reach it
  4. The server is reachable over Streamable HTTP, with an auth option Copilot Studio supports

Copilot Studio supports the Streamable transport (SSE is no longer supported) with none, API key or OAuth 2.0 auth. Choosing "none" for a CRM server would be a serious mistake.

What does "token passthrough" mean, and what does the MCP spec say about it?

  1. Caching tokens to save cost; recommended
  2. Forwarding a client's token, not issued for your server, to downstream APIs; forbidden
  3. Sharing one token across users; optional
  4. Putting tokens in tool descriptions; required

Servers must accept only tokens issued for them and must not pass client tokens through. It breaks audit trails and invites confused-deputy attacks.

You marked get_customer with read_only_hint=True. What does that guarantee?

  1. The host will block any write it attempts
  2. The tool can never return personal data
  3. Nothing by itself; it's a hint to hosts, and your code must actually be read-only
  4. The tool is hidden from the model

Annotations describe behaviour so hosts can decide what to confirm. Enforcement lives in your server code and the permissions of its service account.

Key takeaways

  • An MCP server exposes tools, resources and prompts once, for every MCP-capable host and framework.
  • In the Python SDK v2, FastMCP is now MCPServer; decorators work as before.
  • Use stdio for local, single-user servers and Streamable HTTP with OAuth for anything shared.
  • Test in the MCP Inspector first, then connect hosts; each host supports a different subset of features.
  • A shared server concentrates risk: authenticate, scope narrowly, validate in code, minimise data and log every call.
