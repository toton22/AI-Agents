CrewAI is an open-source Python framework, from the company CrewAI Inc., built around a simple metaphor: you hire a small team. Each agent has a role, a goal and a backstory. Each task has a description and an expected output, and is given to an agent. A crew puts agents and tasks together and runs them under a process: sequential (task one, then two, then three) or hierarchical (a manager agent hands out the work and checks it).

The metaphor is why CrewAI is popular with business users. "An analyst, a policy officer and a writer" maps onto how a manager already thinks about a job. You can read a CrewAI file and understand who does what without knowing much Python.

The second half of CrewAI is Flows: event-driven workflows where ordinary Python methods run in a defined order, with routers for branching and a shared, typed state. Flows are how you get deterministic control, and you can call a crew or a single agent from inside any step. As of 2026, CrewAI also offers a @human_feedback decorator for Flows and a commercial platform, CrewAI AMP (Agent Management Platform), for deploying and monitoring crews.

Manager's lens

The org-chart metaphor is a gift and a trap. It makes agents easy to explain to stakeholders. It also tempts teams to build three agents where one would do, because that is how the human team is organised. Every extra agent is extra model calls, extra cost and one more place for a misunderstanding. Ask "would one competent person do this alone?" before approving a crew.

When to pick it

CrewAI shines when the work genuinely splits into different skills with different tools: one agent researches with web search, another analyses numbers, a third writes. Market scans, content pipelines, due-diligence first drafts and report generation are the classic fits. It is also a fast way to prototype: a working crew takes an afternoon.

Pick Flows (or a Flow that calls a crew) when the process has rules that must hold every time, such as the Deal Desk's discount policy. Flows give you the same predictability as a LangGraph graph with less ceremony.

Skip a multi-agent crew when the job is a short chain of lookups and one decision. Skip CrewAI altogether if you need fine-grained control over every model message, or long pauses for approval across days; LangGraph is stronger there.

Strengths

  • Easy to read: roles, goals and tasks in plain English
  • Fast prototyping of multi-step, multi-skill work
  • Flows add deterministic routing and typed state
  • Works with most model providers
  • Optional YAML config separates prompts from code

Watch-outs

  • Multi-agent setups multiply model calls and cost
  • Agents passing text to agents can drift from the facts
  • Hierarchical process adds a manager model that can misroute work
  • Console-based human input needs rework for a web app
  • Fast release cadence: pin versions and re-test

How it works

Here are the two ways this page builds the Deal Desk.

Agents, tasks, crews

An agent's role, goal and backstory become part of its prompt. They shape tone and focus, but they are not controls: a backstory saying "you never bend the policy" is a request, like any prompt. Tools are attached per agent, so the Account Analyst can read the CRM and nobody else can. That per-agent tool list is a real control, and it is one of the better arguments for splitting work across agents.

Tasks carry the actual instructions. context=[...] passes earlier task outputs into a later task, which is how the Policy Officer sees the Analyst's record. human_input=True on a task makes CrewAI ask a person to review the agent's answer before the crew moves on; the agent revises using the feedback.

Processes

Sequential runs tasks in the order listed. Hierarchical adds a manager (either a model you name with manager_llm or an agent you define with manager_agent) that decides which agent does which task, reviews the outputs and decides when the job is done. Hierarchical is flexible, and that flexibility is exactly what you do not want for a discount policy.

Flows

A Flow is a Python class. @start() marks the first step, @listen(...) runs a method after another finishes, and @router(...) returns a label that picks which listeners run next. State is a Pydantic model, so every step reads and writes typed fields. Inside any step you can call plain code, one agent or a whole crew.

Step 2: the tools (meridian_tools.py)

"""meridian_tools.py - the Deal Desk agent's tools, in plain Python.

In a real company these functions would call the CRM and the ERP.
Here they read a small in-memory table so the whole agent runs on a laptop.
"""
import difflib
from datetime import datetime

CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian Supplies discount policy (FY 2026-27)
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""

TIER_CAP = {"Bronze": 5, "Silver": 8, "Gold": 12}
MARGIN_FLOOR = 12
APPROVALS = []  # stands in for your ticketing system


def get_customer(customer_id: str) -> dict:
    """Return the customer record for an id such as C-101."""
    record = CUSTOMERS.get(customer_id.strip().upper())
    return record or {"error": f"No customer with id {customer_id}"}


def find_customer(name: str) -> dict:
    """Fuzzy lookup by customer name. Returns the best-matching record."""
    by_name = {c["name"].lower(): c for c in CUSTOMERS.values()}
    query = name.strip().lower()
    for full_name, record in by_name.items():
        if query and (query in full_name or full_name in query):
            return record
    close = difflib.get_close_matches(query, list(by_name), n=1, cutoff=0.5)
    return by_name[close[0]] if close else {"error": f"No customer matching '{name}'"}


def get_discount_policy() -> str:
    """Return the current discount policy text."""
    return POLICY


def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % left after the discount (simplified: margin minus discount)."""
    return round(current_margin_pct - discount_pct, 2)


def request_approval(customer_id: str, discount_pct: float, approver: str, reason: str) -> str:
    """Log an approval request for a discount above policy. A named person must decide."""
    ticket = f"APR-{len(APPROVALS) + 1:04d}"
    APPROVALS.append({"ticket": ticket, "customer_id": customer_id, "discount_pct": discount_pct,
                      "approver": approver, "reason": reason,
                      "raised_at": datetime.now().isoformat(timespec="seconds")})
    return f"{ticket} logged with {approver} for {discount_pct}% on {customer_id}."


def evaluate_request(customer: dict, discount_pct: float) -> dict:
    """The policy written as code: the same rules, checked the same way every time."""
    cap = 3 if customer["late_payments_fy"] >= 2 else TIER_CAP[customer["tier"]]
    margin_after = margin_after_discount(customer["gross_margin_pct"], discount_pct)
    problems = []
    if discount_pct > cap:
        problems.append(f"{discount_pct}% is above the {cap}% cap")
    if margin_after < MARGIN_FLOOR:
        problems.append(f"margin after discount would be {margin_after}%, below the {MARGIN_FLOOR}% floor")
    approver = None
    if problems:
        approver = "Regional Head" if discount_pct > 15 else "Sales Manager"
    return {"within_policy": not problems, "cap_pct": cap, "margin_after_pct": margin_after,
            "problems": problems, "approver": approver}

What this does: the customer table and discount policy from the course case, five plain functions the agents can call, and evaluate_request, the policy expressed as code, which the Flow version uses to make the decision without a model.

Step 3: the crew (crew_deal_desk.py)

"""crew_deal_desk.py - Deal Desk as a three-agent CrewAI crew."""
import os

from crewai import LLM, Agent, Crew, Process, Task
from crewai.tools import tool

import meridian_tools as mt

llm = LLM(model=os.getenv("CREW_MODEL", "anthropic/claude-sonnet-5-5"))   # provider/model-id

# Plain Python functions become CrewAI tools; the docstring is what the agent reads.
find_customer = tool("find_customer")(mt.find_customer)
get_customer = tool("get_customer")(mt.get_customer)
get_discount_policy = tool("get_discount_policy")(mt.get_discount_policy)
margin_after_discount = tool("margin_after_discount")(mt.margin_after_discount)

analyst = Agent(
    role="Account Analyst",
    goal="Pull the exact customer record the deal depends on, with no guesswork",
    backstory="You have run Meridian's CRM for years. You quote records, never memory.",
    tools=[find_customer, get_customer], llm=llm, verbose=True)

policy_officer = Agent(
    role="Policy Officer",
    goal="Decide whether the discount is within policy and, if not, who must approve it",
    backstory="You apply Meridian's discount policy word for word. You never bend it.",
    tools=[get_discount_policy, margin_after_discount], llm=llm, verbose=True)

writer = Agent(
    role="Deal Writer",
    goal="Write a short, warm, accurate reply the salesperson can send",
    backstory="You write for B2B buyers in hospitals, schools and logistics firms.",
    llm=llm, verbose=True)

lookup_task = Task(
    description="Find the customer in this request and return their full record: {request}",
    expected_output="The customer record as JSON: id, name, tier, revenue, late payments, margin.",
    agent=analyst)

policy_task = Task(
    description=("Using the record, check the discount asked for in '{request}' against the "
                 "policy. Compute the margin with the tool. State WITHIN POLICY or ESCALATE, "
                 "the cap, the margin after discount, and the approver if any."),
    expected_output="Verdict, cap %, margin after discount %, approver (or none), one-line reason.",
    agent=policy_officer, context=[lookup_task],
    human_input=True)   # a person reviews the verdict before the writer starts

reply_task = Task(
    description=("Draft the reply. If the verdict was ESCALATE, do not promise the discount: "
                 "say it is with the approver and give the human reviewer's decision if stated."),
    expected_output="A reply of under 120 words.",
    agent=writer, context=[lookup_task, policy_task])

crew = Crew(agents=[analyst, policy_officer, writer],
            tasks=[lookup_task, policy_task, reply_task],
            process=Process.sequential)

if __name__ == "__main__":
    result = crew.kickoff(inputs={"request": input("Salesperson: ")})
    print(result.raw)

What this does:

  • tool("find_customer")(mt.find_customer) wraps an ordinary function as a CrewAI tool. The docstring becomes the tool description the agent reads. (You will usually see the same thing written as @tool("...") above a function.)
  • Three agents, each with a role, goal and backstory. Only the Analyst gets CRM tools; only the Policy Officer gets the policy and margin tools; the Writer gets none. Least privilege, applied to agents.
  • Three tasks. {request} is filled in from kickoff(inputs=...). context chains the outputs: the Policy Officer sees the record, the Writer sees both.
  • human_input=True on the policy task pauses the crew in the terminal after the verdict. A Sales Manager can type "Approved at 4%" or "Agreed, escalate", and the Policy Officer folds that into its final answer before the Writer starts.
  • Process.sequential runs the tasks in order. result.raw is the Writer's reply.

Notice that request_approval is not given to any agent here. In this design the human review is the approval, and the escalation ticket is better raised by your app after a person has seen the verdict. If you do hand an agent an action tool, put the human review on that agent's task.

For a hierarchical version, drop the agent= from each task, add process=Process.hierarchical and manager_llm=llm to the Crew, and a manager model will assign the tasks. Try it once to see how it behaves, then keep the sequential version for anything involving money.

Step 4: the Flow (crew_flow.py)

"""crew_flow.py - the same job as a CrewAI Flow: code makes the decision, one agent writes."""
from crewai import Agent
from crewai.flow.flow import Flow, listen, router, start
from pydantic import BaseModel

import meridian_tools as mt
from crew_deal_desk import llm


class DealState(BaseModel):
    customer_name: str = ""
    discount_pct: float = 0
    customer: dict = {}
    verdict: dict = {}
    decision: str = ""
    reply: str = ""


class DealDeskFlow(Flow[DealState]):

    @start()
    def lookup(self):
        self.state.customer = mt.find_customer(self.state.customer_name)

    @router(lookup)
    def check_policy(self):
        if "error" in self.state.customer:
            return "not_found"
        self.state.verdict = mt.evaluate_request(self.state.customer, self.state.discount_pct)
        return "within_policy" if self.state.verdict["within_policy"] else "escalate"

    @listen("escalate")
    def ask_approver(self):
        v, c = self.state.verdict, self.state.customer
        print(mt.request_approval(c["id"], self.state.discount_pct, v["approver"],
                                  "; ".join(v["problems"])))
        self.state.decision = input(f"{v['approver']}, your decision (e.g. 'approve 4%' or 'reject'): ")
        self.write_reply()

    @listen("within_policy")
    def approve(self):
        self.state.decision = "approved within policy"
        self.write_reply()

    @listen("not_found")
    def report_missing(self):
        self.state.reply = f"Could not find '{self.state.customer_name}'. Please check the name."

    def write_reply(self):
        writer = Agent(role="Deal Writer", goal="Write a short, accurate reply to the customer",
                       backstory="You write for Meridian's B2B buyers.", llm=llm)
        result = writer.kickoff(
            f"Facts: {self.state.customer}, asked {self.state.discount_pct}%, "
            f"verdict {self.state.verdict}, decision '{self.state.decision}'. "
            "Draft a reply under 120 words. Offer only what the decision allows.")
        self.state.reply = result.raw

if __name__ == "__main__":
    flow = DealDeskFlow()
    flow.kickoff(inputs={"customer_name": "Bluewave Logistics", "discount_pct": 6})
    print(flow.state.reply)

What this does:

  • DealState is the typed state the whole Flow shares.
  • lookup is the @start() step: plain code calling find_customer. In practice the salesperson fills a small form in the CRM, so the Flow receives the customer name and percentage as structured inputs and no model is needed to parse them.
  • check_policy is a @router: it runs evaluate_request and returns "within_policy", "escalate" or "not_found". Those labels pick the next step.
  • ask_approver raises the ticket and asks the named approver for a decision. The demo uses input() so you can see the mechanism; CrewAI's @human_feedback decorator (CrewAI 1.8 and later) is the built-in alternative, with outcomes such as "approved" or "rejected" routed to different listeners.
  • write_reply is the only model call: one Deal Writer agent, given the facts and the decision, asked to offer nothing beyond them.
Watch out

A Flow method cannot listen to a label with its own name (CrewAI rejects it as an infinite loop). That is why the "not_found" route is handled by a method called report_missing.

Now the Flow for the same request: lookup (code) → check_policy returns "escalate" (code) → ask_approver raises APR-0001 and the Sales Manager types "approve 4%" → write_reply (one model call). Sahyadri at 10% routes to approve; Kite at 5% routes to escalate because the margin would be 11%.

Does the Deal Desk need three agents?

To be honest, no. Count the model work. The crew runs three agents, each with its own reasoning loop, and the Policy Officer applies the rules from prose, so it can still get Kite wrong. The Flow makes one model call, applies the rules in code and can never approve Kite at 5%. It is cheaper, faster and easier to audit.

The crew is still a useful exercise. It shows how roles and per-agent tools work, and it is the right shape for jobs that really need different skills. But for a rule-bound decision with one approval, the single-agent or Flow design wins. A good test: if your agents mostly pass a record from one to the next without adding judgement, you have built a relay race, not a team.

Manager's lens

When a vendor or an internal team shows you a multi-agent design, ask for the single-agent baseline and the cost per request for both. If they have not built the baseline, they do not know whether the extra agents add anything.

Taking it to production

Hosting

A crew or Flow is a Python program, so it runs anywhere Python runs: behind a FastAPI endpoint on your cloud, in a container, or as a scheduled job. CrewAI AMP is the managed alternative. As of 2026 it deploys crews to managed infrastructure, exposes them through a REST API, records execution traces and logs, and includes Crew Studio, a low-code builder. Check the AMP docs for current hosting regions and plans.

Identity and SSO

Put the endpoint behind company login and pass the user id in the Flow's inputs so it appears in logs. The console-based human_input and input() do not survive the move to a web app: replace them with an approval card in Teams or Slack, and have the Flow wait for or resume on the decision. Take the approver's identity from SSO.

Data access

Give each agent only the tools its role needs, and give the tools a read-only service account. Keep customer data minimal in task descriptions, because everything in them is sent to the model. Review what your traces store against the DPDP Act 2023 and your customer contracts.

Cost control

Multi-agent crews are the most expensive design on this site for the same job. Set max_iter on agents and max_rpm to cap request rates, use a smaller model for the Analyst, and prefer Flows with code for the deterministic steps. Track tokens per request; CrewAI reports usage metrics on the crew after a run.

Monitoring and approvals

Turn on tracing (Crew(tracing=True) or AMP's traces) during the pilot and review a sample weekly. Watch for drift between agents: the Writer offering a number the Policy Officer did not approve is the failure to look for. Approval rules stay the same as on every page: named approver, expiry, no self-approval.

  • Rules in Flow code, not only in backstories
  • Per-agent tool lists reviewed by security
  • Console human input replaced with an approval service
  • max_iter, rate limits and token tracking set
  • Versions pinned; regression tests on every upgrade

Practice

  1. Count the calls

    For the Bluewave request, estimate the number of model calls in the crew version and in the Flow version. What does that imply for cost at 2,000 requests a month?

    Hint / model answer

    The crew: each agent runs its own loop, typically two to four calls each, so roughly six to twelve calls. The Flow: one call (the writer). At 2,000 requests a month, the crew uses several times more tokens for the same outcome, and has more chances to get the policy wrong.

  2. Write the backstory, then distrust it

    Rewrite the Policy Officer's backstory to make it stricter. Then list two things the backstory cannot guarantee, and where in the code you would enforce them.

    Hint / model answer

    A backstory cannot guarantee the margin rule is applied, or that a discount above cap is never promised. Enforce the first with evaluate_request in a Flow router, and the second by routing every failed check through ask_approver before write_reply can run.

  3. When a crew is right

    Describe one task in your own organisation where a three-agent crew would beat a single agent. What makes the roles genuinely different?

    Hint / model answer

    Good answers have roles with different tools and different judgement: for example, a researcher with web search, a financial analyst with spreadsheet tools, and a writer with the house style guide. If the roles share the same tools and data, one agent is probably enough.

What does human_input=True on a CrewAI task do?

  1. Lets the salesperson type the request
  2. Forces the agent to ask the user a clarifying question first
  3. Asks a person to review the agent's answer for that task before the crew continues
  4. Sends the final reply to a human for sending

It adds a human review of the task's final answer; the agent can revise using the feedback before later tasks run.

Which design guarantees that Kite Fintech at 5% is escalated, whatever the model thinks?

  1. A Flow whose router calls evaluate_request
  2. A crew with a stricter Policy Officer backstory
  3. A hierarchical crew with a manager LLM
  4. Giving the Deal Writer the policy tool

Only code-based routing is deterministic. Backstories and manager models are prompts and can still miss the 11% margin.

What does a hierarchical process add to a crew?

  1. A database for state
  2. Parallel execution of all tasks
  3. A human approver for every task
  4. A manager (manager_llm or manager_agent) that assigns tasks and reviews outputs

The manager plans, delegates and validates. Flexible, but less predictable than a fixed sequence.

Why is per-agent tool assignment a genuine benefit of splitting work across agents?

  1. It makes the agents faster
  2. It limits which agent can touch which system, a real access control
  3. It removes the need for a human checkpoint
  4. It reduces token usage to zero for tool-less agents

Roles and backstories are prompts; tool lists are enforced by the framework. Only the Analyst can read the CRM.

The honest verdict on a three-agent crew for the Deal Desk is:

  1. Essential, because three roles exist in the human team
  2. Better, because more agents means more checking
  3. Unnecessary: a Flow with code rules and one writing agent is cheaper and more reliable
  4. Impossible, because CrewAI needs at least four agents

The job is lookups plus one rule-bound decision. More agents add cost and drift without adding judgement.

Key takeaways

  • CrewAI models work as a team: agents with roles, tasks with expected outputs, crews with a process.
  • Per-agent tool lists are a real control; roles and backstories are only prompts.
  • Flows give deterministic routing and typed state; call agents or crews inside steps.
  • For the Deal Desk, a Flow with code rules and one writer beats a three-agent crew.
  • Always compare a multi-agent design against a single-agent baseline on cost and accuracy.
