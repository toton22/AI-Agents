The OpenAI Agents SDK is a small, open-source Python library (there is a TypeScript twin) for building agents with very few concepts. OpenAI released it in March 2025 as the production-ready successor to its experimental Swarm project. As of October 2026 it is at version 0.23: still a 0.x number, but widely used and updated almost weekly.

The whole SDK fits on an index card. An Agent is a model with instructions and tools. The Runner runs the agent loop for you (the same loop you would write by hand on the raw API page). @function_tool turns a Python function into a tool. Handoffs let one agent pass the conversation to another. Guardrails check inputs and outputs and can stop a run. Sessions remember earlier turns. Tracing records every step and is on by default. And human-in-the-loop approvals pause a run before a sensitive tool executes.

By default it uses OpenAI's Responses API, but the README describes it as provider-agnostic, supporting Chat Completions-style APIs and many other model providers. In practice, it works best, and traces best, with OpenAI models.

AgentKit and Agent Builder

In October 2025 OpenAI launched AgentKit: a visual canvas called Agent Builder (in beta), ChatKit for embedding chat interfaces, a Connector Registry, and expanded Evals. Agent Builder was the drag-and-drop counterpart to this SDK.

Then the plan changed. OpenAI's deprecations page lists Agent Builder, announced for wind-down on 3 June 2026, as shutting down on 30 November 2026, and recommends continuing with the Agents SDK or ChatGPT Workspace Agents. The Evals platform becomes read-only from 31 October 2026 and also shuts down on 30 November 2026. ChatKit remains available. If anyone in your company built on Agent Builder, the Agents SDK is the code path forward; check the deprecations page for the current dates and migration guides.

Manager's lens

The Agent Builder story is a lesson worth more than any feature list. A visual builder from the biggest name in AI lasted about fourteen months. Code you own, on an open-source SDK, kept working. When you choose a platform, ask what happens to your agents if the vendor changes direction, and keep the business logic (your tools and policies) in plain code you can move.

When to pick it

Pick the Agents SDK when you want the shortest path from idea to a working, well-traced agent on OpenAI models, with the safety features a business needs (guardrails, approvals) already built. It is the easiest framework on this site to read: the Deal Desk below is under 80 lines including the approval loop.

Handoffs make it a natural fit for "front desk plus specialists" designs: a triage agent that routes to a policy specialist, a returns specialist, or a credit specialist, each with its own tools and instructions.

Look elsewhere if your process needs explicit, auditable branching with business rules in code (a LangGraph graph or a CrewAI Flow suits that better), if your company has standardised on Azure and Entra ID (Microsoft Agent Framework), or if your data rules require a provider other than OpenAI and you want first-class tracing for it.

Strengths

  • Very few concepts; quick to learn and to read
  • Handoffs, guardrails, sessions and approvals built in
  • Tracing on by default, with a dashboard in the OpenAI platform
  • Paused runs can be saved and resumed later (RunState)
  • Open source (MIT), Python and TypeScript

Watch-outs

  • Still 0.x: expect API changes; pin and re-test
  • Business rules live in prompts unless you add code checks
  • Hosted tracing is unavailable to Zero Data Retention organisations
  • No managed runtime: hosting, auth and storage are yours
  • Its visual counterpart, Agent Builder, is being shut down

How it works

Function tools. function_tool(fn) reads the function's name, type hints and docstring and builds the JSON schema for you, in strict mode by default. Pass needs_approval=True and the tool will not run until someone approves the call.

Handoffs. Listing policy_agent in the triage agent's handoffs gives the triage model an extra tool, transfer_to_policy_agent. When it calls that tool, the Runner switches agents and the Policy agent continues the same conversation with its own instructions and tools. That is different from agents as tools (agent.as_tool()), where a manager agent calls a specialist like a function and stays in charge. Use handoffs when the specialist should own the rest of the conversation.

Guardrails. An input guardrail checks the first agent's input and can trip a wire that stops the run with an exception. By default it runs in parallel with the agent, which is fast, but the agent may already have spent tokens or called tools before the wire trips. Set run_in_parallel=False and the check finishes before the agent starts; for anything that guards actions, that is the safer choice. Output guardrails check the final answer, and tool guardrails check individual tool calls. A guardrail does not have to call a model. The one below is a cheap keyword check.

Approvals and RunState. When a gated tool is called, the run stops and result.interruptions lists the pending calls. You convert the result to a RunState, call approve or reject on each item, and run again from that state. The state can be saved as JSON and resumed hours later, even in another process.

Sessions and tracing. A session stores the conversation, so a salesperson can follow up with "and what about 3%?" without repeating themselves. Tracing wraps every run; the trace shows each model call, tool call, handoff and guardrail with timings.

Step 2: the tools (meridian_tools.py)

"""meridian_tools.py - the Deal Desk agent's tools, in plain Python.

In a real company these functions would call the CRM and the ERP.
Here they read a small in-memory table so the whole agent runs on a laptop.
"""
import difflib
from datetime import datetime

CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian Supplies discount policy (FY 2026-27)
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""

TIER_CAP = {"Bronze": 5, "Silver": 8, "Gold": 12}
MARGIN_FLOOR = 12
APPROVALS = []  # stands in for your ticketing system


def get_customer(customer_id: str) -> dict:
    """Return the customer record for an id such as C-101."""
    record = CUSTOMERS.get(customer_id.strip().upper())
    return record or {"error": f"No customer with id {customer_id}"}


def find_customer(name: str) -> dict:
    """Fuzzy lookup by customer name. Returns the best-matching record."""
    by_name = {c["name"].lower(): c for c in CUSTOMERS.values()}
    query = name.strip().lower()
    for full_name, record in by_name.items():
        if query and (query in full_name or full_name in query):
            return record
    close = difflib.get_close_matches(query, list(by_name), n=1, cutoff=0.5)
    return by_name[close[0]] if close else {"error": f"No customer matching '{name}'"}


def get_discount_policy() -> str:
    """Return the current discount policy text."""
    return POLICY


def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % left after the discount (simplified: margin minus discount)."""
    return round(current_margin_pct - discount_pct, 2)


def request_approval(customer_id: str, discount_pct: float, approver: str, reason: str) -> str:
    """Log an approval request for a discount above policy. A named person must decide."""
    ticket = f"APR-{len(APPROVALS) + 1:04d}"
    APPROVALS.append({"ticket": ticket, "customer_id": customer_id, "discount_pct": discount_pct,
                      "approver": approver, "reason": reason,
                      "raised_at": datetime.now().isoformat(timespec="seconds")})
    return f"{ticket} logged with {approver} for {discount_pct}% on {customer_id}."


def evaluate_request(customer: dict, discount_pct: float) -> dict:
    """The policy written as code: the same rules, checked the same way every time."""
    cap = 3 if customer["late_payments_fy"] >= 2 else TIER_CAP[customer["tier"]]
    margin_after = margin_after_discount(customer["gross_margin_pct"], discount_pct)
    problems = []
    if discount_pct > cap:
        problems.append(f"{discount_pct}% is above the {cap}% cap")
    if margin_after < MARGIN_FLOOR:
        problems.append(f"margin after discount would be {margin_after}%, below the {MARGIN_FLOOR}% floor")
    approver = None
    if problems:
        approver = "Regional Head" if discount_pct > 15 else "Sales Manager"
    return {"within_policy": not problems, "cap_pct": cap, "margin_after_pct": margin_after,
            "problems": problems, "approver": approver}

What this does: the customer table and discount policy from the course case, and five plain functions. Nothing here knows about OpenAI, which is the point: if you ever move frameworks, this file moves unchanged. (evaluate_request, the policy in code, is not used on this page; exercise 2 asks you to put it to work.)

Step 3: the agents (oai_deal_desk.py)

"""oai_deal_desk.py - Deal Desk on the OpenAI Agents SDK: triage hands off to a Policy agent."""
import asyncio
import os

from agents import (Agent, GuardrailFunctionOutput, InputGuardrailTripwireTriggered, Runner,
                    SQLiteSession, function_tool, input_guardrail, trace)
from agents.extensions.handoff_prompt import RECOMMENDED_PROMPT_PREFIX

import meridian_tools as mt

MODEL = os.getenv("OPENAI_MODEL", "gpt-5.5")      # use a model id your account has

policy_agent = Agent(
    name="Policy agent",
    handoff_description="Decides whether a discount is within Meridian's policy.",
    instructions=f"""{RECOMMENDED_PROMPT_PREFIX}
You are Meridian Supplies' Policy agent. The customer record is already in the conversation.
Read the policy and compute the margin with the tool. If the request meets every rule,
approve it and draft a short reply. If not, call request_approval with the right approver
and never promise the discount. request_approval only runs after the approver says yes;
if it is rejected, say so and offer the within-policy maximum. Quote the numbers you used.""",
    tools=[function_tool(mt.get_discount_policy),
           function_tool(mt.margin_after_discount),
           function_tool(mt.request_approval, needs_approval=True)],   # the human gate
    model=MODEL,
)


@input_guardrail(run_in_parallel=False)        # finish this check before the agent starts
async def no_policy_override(ctx, agent, user_input) -> GuardrailFunctionOutput:
    """Cheap check before any model call: block attempts to talk the agent out of the policy."""
    text = str(user_input).lower()
    hit = any(p in text for p in ("ignore the policy", "ignore previous", "skip approval"))
    return GuardrailFunctionOutput(output_info={"override_attempt": hit}, tripwire_triggered=hit)


triage_agent = Agent(
    name="Deal Desk triage",
    instructions=f"""{RECOMMENDED_PROMPT_PREFIX}
You take questions from Meridian's salespeople. For a discount request, first look the
customer up with find_customer, then hand off to the Policy agent. For anything else,
say politely that the Deal Desk only handles discount requests.""",
    tools=[function_tool(mt.find_customer), function_tool(mt.get_customer)],
    handoffs=[policy_agent],
    input_guardrails=[no_policy_override],
    model=MODEL,
)


async def main():
    session = SQLiteSession("salesperson-anita", "deal_desk.db")   # remembers past turns
    request = input("Salesperson: ")
    with trace("Meridian Deal Desk", group_id="salesperson-anita"):
        try:
            result = await Runner.run(triage_agent, request, session=session, max_turns=10)
        except InputGuardrailTripwireTriggered:
            print("Blocked: the Deal Desk cannot set the policy aside. Ask your Sales Manager.")
            return
        while result.interruptions:                      # paused at the approval gate
            state = result.to_state()
            for item in result.interruptions:
                print(f"\nAPPROVAL NEEDED: {item.name} {item.arguments}")
                if input("Approve? (y/n): ").strip().lower() == "y":
                    state.approve(item)
                else:
                    state.reject(item, rejection_message="The Sales Manager declined this discount.")
            result = await Runner.run(triage_agent, state, session=session)
    print(f"\n[{result.last_agent.name}] {result.final_output}")


if __name__ == "__main__":
    asyncio.run(main())

What this does, block by block:

  • Policy agent. Instructions start with RECOMMENDED_PROMPT_PREFIX, the SDK's standard text explaining handoffs to the model. Its tools are the policy, the margin calculator and request_approval wrapped with needs_approval=True. handoff_description tells the triage agent when to hand over.
  • Guardrail. no_policy_override scans the request for phrases like "ignore the policy" and trips the wire if it finds one. No model call, no cost, and run_in_parallel=False makes it finish before the triage agent starts. A keyword list is a first line of defence only; determined users rephrase, which is why the approval gate still matters.
  • Triage agent. It can look customers up and hand off to the Policy agent; it has no policy or approval tools at all, so it cannot approve anything even if it wanted to.
  • Session. SQLiteSession("salesperson-anita", "deal_desk.db") stores the conversation in a local file, keyed by salesperson.
  • Trace. with trace("Meridian Deal Desk", group_id=...) names the workflow and groups this salesperson's runs together in the dashboard.
  • Run and approve. Runner.run(..., max_turns=10) runs the loop with a step limit. If a guardrail trips, the exception is caught and the salesperson gets a plain message. While there are interruptions, each pending call is shown; approval or rejection is recorded on the RunState and the run resumes. A rejection carries a custom message the model sees.
  • Output. result.last_agent.name shows which agent answered (here, usually the Policy agent) and result.final_output is the reply.

Tip

Open the Traces dashboard in the OpenAI platform after a run. You will see the guardrail, both agents, the handoff, each tool call and the pause, with timings. It is the fastest way to explain to a stakeholder what the agent actually did.

Taking it to production

Hosting

The SDK is a library, not a hosting service, so you run it yourself: a FastAPI service in a container on your cloud is the usual pattern. For a chat interface, ChatKit remains available. The approval loop changes shape on a server. Save state.to_json() to your database when a run pauses, send the approver a card, and when they answer, rebuild with RunState.from_json(...) and resume. The SDK's own docs warn that a stored state is not authenticated, so keep it on your server and never let a browser send one back to you.

Identity and SSO

Authenticate salespeople and approvers through your company SSO. Use the authenticated user id as the session id and the trace group_id, so every conversation and trace is attributable. Check the approver's role before calling state.approve.

Data access

Tools reach your systems with a least-privilege service account; the model only sees what tools return. Review OpenAI's data controls for your organisation (retention, data residency options) against the DPDP Act 2023 and your customer contracts. If your organisation uses Zero Data Retention, hosted tracing is not available, so send traces to your own processor instead (the SDK supports custom trace processors).

Cost control

Set max_turns on every run, keep tool outputs short, and give the triage agent a smaller, cheaper model than the Policy agent; it only looks things up and routes. Sessions grow with each turn, so trim or summarise long histories. Watch tokens per request in your usage dashboard.

Monitoring and approvals

Traces cover the "what happened". Add business metrics on top: escalation rate, rejection rate, guardrail trips, time-to-approval. A rising guardrail trip rate means someone is testing the system. Approval rules are the same as on every page: named approver, expiry, no self-approval.

  • Version pinned; upgrade tests on Sahyadri, Bluewave and Kite
  • RunState stored server-side for paused approvals
  • Approver role checked before approve()
  • max_turns and per-agent model choice set
  • Tracing destination matches your data policy
  • No dependency on Agent Builder or the Evals platform after 30 Nov 2026

Practice

  1. Add an output guardrail

    Write, in plain English or code, an output guardrail that blocks any final reply offering a discount above the customer's cap unless an approval was recorded in this run.

    Hint / model answer

    Use @output_guardrail. Parse the percentage from the reply, look up the customer's cap with evaluate_request, and check mt.APPROVALS for a ticket from this run. Trip the wire if the offer exceeds the cap without an approval. Catch OutputGuardrailTripwireTriggered and route to a person.

  2. Make Kite impossible to miss

    The Policy agent decides from the policy text. Change the design so the margin rule is enforced in code, without removing the model.

    Hint / model answer

    Give the Policy agent a check_policy function tool that wraps evaluate_request and returns the verdict, and use a dynamic needs_approval callable on a tool that would grant a discount, returning True whenever the verdict fails. The model can still write the reply, but the decision comes from code.

  3. Plan an Agent Builder migration

    A colleague built an internal FAQ agent in Agent Builder last year. List the steps to move it before 30 November 2026.

    Hint / model answer

    Document the workflow, its prompts and its tools (screenshots of the canvas help); rebuild it with the Agents SDK (or ChatGPT Workspace Agents if it is a simple internal assistant); move any reusable prompt objects into code; replace Evals with your own test set; re-point any ChatKit front end to the new backend; test, then switch over before the shutdown date.

What is the difference between a handoff and an agent used as a tool?

  1. There is none; they are two names for the same thing
  2. A handoff passes the conversation to the specialist, which answers; as a tool, the specialist returns a result to the calling agent, which stays in charge
  3. Handoffs only work with OpenAI models
  4. Agents as tools cannot use function tools

Handoffs transfer control; agents-as-tools are called like functions. Here the Policy agent owns the reply, so a handoff fits.

What happens when the Policy agent calls request_approval, defined with needs_approval=True?

  1. The tool runs and an email goes to the manager
  2. The SDK raises InputGuardrailTripwireTriggered
  3. The run pauses with an interruption; you approve or reject on a RunState and run again
  4. The model is told the tool does not exist

Interruptions list pending calls; state.approve() or state.reject() records the decision and Runner.run(agent, state) resumes.

Why does the keyword guardrail on this page not call a model?

  1. A cheap code check runs every time at no cost; model-based guardrails are for fuzzier judgements
  2. Guardrails are not allowed to call models
  3. It makes tracing work
  4. The triage agent already checks for overrides

Guardrails can run an agent, but simple checks are faster and deterministic in code.

According to OpenAI's deprecations page, what is the recommended path for workflows built in Agent Builder?

  1. Move them to the Assistants API
  2. Keep using Agent Builder; it becomes read-only
  3. Rebuild them in ChatKit
  4. Continue with the Agents SDK or ChatGPT Workspace Agents

Agent Builder shuts down on 30 November 2026; the page points to the Agents SDK or Workspace Agents. ChatKit remains, but it is a UI toolkit, not a workflow builder.

The triage agent has no policy or approval tools. Why is that a good design?

  1. It makes the triage agent's prompt shorter
  2. An agent can only do what its tools allow, so triage cannot approve anything even if it misreads the request
  3. Handoffs fail if both agents share tools
  4. It is required for sessions to work

Tool lists are hard limits. Giving each agent only the tools its role needs is least privilege for agents.
