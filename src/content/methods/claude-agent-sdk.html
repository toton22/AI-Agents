The Claude Agent SDK is Anthropic's library for building agents in Python or TypeScript. Here's the unusual part. It doesn't hand you a bare model and a loop to write yourself. It hands you the same agent loop, built-in tools and context management that run Claude Code, Anthropic's coding agent, packaged so your own program can drive it.

That matters. Claude Code had to solve the hard, boring problems of a working agent: editing files safely, running commands, asking permission, keeping long sessions inside the context window. With the SDK you inherit those answers.

It started life as the Claude Code SDK and was renamed once teams began using it for things that have nothing to do with code. Anthropic's docs still carry a migration guide from the old package names. As of October 2026 the Python package is claude-agent-sdk (0.2.165 at the time of writing) and the TypeScript one is @anthropic-ai/claude-agent-sdk (0.3.296). Both bundle a native Claude Code binary, so on most machines a single install is all you need.

What changed recently? The SDK now exposes skills (folders of instructions the agent loads when relevant), programmatic subagents with their own tools and models, a dontAsk permission mode for locked-down headless agents, and a per-request dollar cap (max_budget_usd). Anthropic also offers Managed Agents, where Anthropic hosts the loop for you. That's a different product; this page is about running the loop yourself.

Manager's lens

Most agent frameworks are built around chat plus API calls. This one is built around a worker with a desk: a folder of files, a set of approved tools, and a supervisor who can say no. If the job you want automated looks like "open these documents, work something out, write a draft, file it", that shape fits well.

When to pick it

Pick the Claude Agent SDK when the agent's real work happens in documents and folders. Month-end commentary drafted from ledger exports. A contract pack checked against a playbook. A board note assembled from five spreadsheets. The built-in Read, Write, Edit, Glob, Grep and Bash tools mean the agent can open, search, transform and save files with no extra code from you, and the permission system decides which of those it may touch.

It's also a strong pick when governance is the hard part. Hooks run before every tool call, ahead of any allow rule, so you can put a human or a policy check in front of exactly the actions that carry risk. For a finance or compliance team, that is often the feature that gets a pilot past the risk committee.

Don't pick it if you need to switch model vendors freely. The loop runs on Claude models only. Your tools are portable because they are MCP servers, but the orchestration is not. And if you want a visual builder for business users, look at Copilot Studio or the no-code assistants instead; this is a developer's library.

Strengths

  • Production-grade file, search and shell tools out of the box
  • Hooks and permission modes give fine control over every action
  • Custom tools are plain functions exposed as an in-process MCP server
  • Subagents, skills and sessions without extra frameworks
  • Same API shape in Python and TypeScript

Watch-outs

  • Claude models only
  • Powerful built-in tools are risky if you forget to restrict them
  • Runs a local runtime process, so it needs a real container, not a tiny serverless function
  • Fast release cadence; pin versions and read the changelog

How it works

Your program calls the SDK. The SDK starts the Claude Code runtime as a child process and talks to it. The runtime runs the agent loop: send the conversation to Claude, receive either an answer or a tool request, check permissions, run the tool, feed the result back, repeat. Your program sees a stream of messages as all this happens.

query() versus ClaudeSDKClient

There are two ways in. query() is a one-shot call: give it a prompt and options, iterate over the messages, done. Each call starts a fresh session. It suits batch jobs, such as "draft commentary for every cost centre in this folder".

ClaudeSDKClient keeps one session open across several exchanges, so a salesperson can ask a follow-up ("what if they paid on time?") and the agent remembers the customer. It also supports interrupts. Use it for anything conversational.

ClaudeAgentOptions, the control panel

Almost every decision lives in one options object. The fields you will use first:

OptionWhat it controlsDeal Desk setting
system_promptThe agent's standing instructionsThe discount procedure, step by step
mcp_serversExtra tool servers, in-process or externalOur meridian server with five tools
allowed_toolsTools pre-approved to run without askingThe five Meridian tools plus Write
toolsWhich built-in tools the agent can even seeOnly Write
permission_modeWhat happens to anything not pre-approveddontAsk: refuse it
hooksYour code that runs at lifecycle eventsApproval gate; drafts-folder rule
max_turns, max_budget_usdRunaway protection15 turns, US$0.50 per request

Permission modes deserve a sentence each. default sends anything unapproved to your can_use_tool callback. acceptEdits auto-approves file edits in the working folder. plan lets the agent explore and propose without editing. dontAsk turns every would-be prompt into a refusal. bypassPermissions approves almost everything and belongs only in a sandbox. There's also auto, where a classifier model reviews actions.

Watch out

allowed_tools does not restrict anything on its own. It pre-approves the tools you list; unlisted tools still exist and fall through to the permission mode. To remove a tool from the agent's view, use tools or disallowed_tools. People get this backwards all the time.

Hooks: where governance lives

A hook is an async function the runtime calls at a named moment. PreToolUse fires before a tool runs and can allow, deny, ask or modify the call. PostToolUse fires after, which makes it the natural place for an audit log. Others cover subagent start and stop, prompt submission and compaction. Hooks run first in the permission order, so a hook's deny wins even in bypassPermissions mode.

Subagents and skills

A subagent is a separate agent with its own prompt, tools and model, launched through the built-in Agent tool; it works in a fresh context and returns only a summary. A skill is a folder with a SKILL.md playbook that the agent loads only when a task matches it. Both appear in the build below.

Build the Deal Desk

We'll build the full agent in one Python file. It knows Meridian's five customers, reads the discount policy, does the margin arithmetic, writes approved replies to a drafts folder, and stops for a human whenever a discount breaks policy. Python 3.10 or later is required.

  2. Write the agent

    Save this as deal_desk.py. Read it once top to bottom; the plain-English walk-through follows.

    import asyncio
import json
import os
from pathlib import Path

from claude_agent_sdk import (
    AssistantMessage, ClaudeAgentOptions, ClaudeSDKClient, HookMatcher,
    ResultMessage, TextBlock, ToolUseBlock, create_sdk_mcp_server, tool,
)

MODEL = os.getenv("MODEL", "claude-sonnet-5-5")  # SDK reads ANTHROPIC_API_KEY itself
DRAFTS = Path("drafts").resolve()

# ---------- 1. Meridian data (in production: CRM / ERP calls) ----------
CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian discount policy
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""


def reply(data) -> dict:
    """Wrap a Python value in the result format the SDK expects."""
    text = data if isinstance(data, str) else json.dumps(data)
    return {"content": [{"type": "text", "text": text}]}


# ---------- 2. Custom tools ----------
@tool("get_customer", "Return the customer record for an id such as C-101.",
      {"customer_id": str})
async def get_customer(args):
    record = CUSTOMERS.get(args["customer_id"].strip().upper())
    if record is None:
        return {**reply(f"No customer with id {args['customer_id']}"), "is_error": True}
    return reply(record)


@tool("find_customer", "Find a customer by (part of) their name.", {"name": str})
async def find_customer(args):
    hits = [c for c in CUSTOMERS.values() if args["name"].lower() in c["name"].lower()]
    if len(hits) != 1:
        return {**reply(f"{len(hits)} matches: {[c['name'] for c in hits]}"),
                "is_error": True}
    return reply(hits[0])


@tool("get_discount_policy", "Return Meridian's discount policy text.", {})
async def get_discount_policy(args):
    return reply(POLICY)


@tool("margin_after_discount", "Gross margin % left after a discount.",
      {"current_margin_pct": float, "discount_pct": float})
async def margin_after_discount(args):
    return reply(round(args["current_margin_pct"] - args["discount_pct"], 2))


@tool("request_approval", "Ask the Sales Manager or Regional Head to approve "
      "an out-of-policy discount.",
      {"customer_id": str, "discount_pct": float, "approver": str, "reason": str})
async def request_approval(args):
    # Only runs if the approval hook below let it through.
    return reply(f"APPROVED by {args['approver']}: {args['discount_pct']}% "
                 f"for {args['customer_id']}.")


meridian = create_sdk_mcp_server(
    name="meridian", version="1.0.0",
    tools=[get_customer, find_customer, get_discount_policy,
           margin_after_discount, request_approval],
)


# ---------- 3. Hooks: a human gate and a file-safety rule ----------
async def approval_gate(input_data, tool_use_id, context):
    a = input_data["tool_input"]
    question = (f"\n[{a['approver']}] Approve {a['discount_pct']}% for "
                f"{a['customer_id']}? Reason: {a['reason']}  (y/n): ")
    answer = await asyncio.to_thread(input, question)  # Slack/Teams card in production
    if answer.strip().lower().startswith("y"):
        return {}  # let the call through
    return {"hookSpecificOutput": {
        "hookEventName": input_data["hook_event_name"],
        "permissionDecision": "deny",
        "permissionDecisionReason": f"{a['approver']} declined. Do not offer "
                                    "this discount; offer the policy maximum instead.",
    }}


async def drafts_only(input_data, tool_use_id, context):
    path = Path(input_data["tool_input"].get("file_path", "")).resolve()
    if DRAFTS not in path.parents:
        return {"hookSpecificOutput": {
            "hookEventName": input_data["hook_event_name"],
            "permissionDecision": "deny",
            "permissionDecisionReason": "Deal Desk may only write inside ./drafts",
        }}
    return {}


SYSTEM_PROMPT = """You are the Meridian Deal Desk assistant for the sales team.
For every discount request:
1. Identify the customer (find_customer or get_customer).
2. Read the policy (get_discount_policy).
3. Cap = tier cap, or 3% if late_payments_fy >= 2.
4. Call margin_after_discount and compare with the 12% floor.
5. Within cap AND margin >= 12%: approve and write a two-line customer reply
   to drafts/<customer-id>.md with the Write tool.
6. Otherwise call request_approval (Sales Manager; Regional Head if > 15%).
   If it is declined, draft a reply offering the policy maximum instead.
Never promise a discount above policy without an APPROVED result.
End with a short summary showing the numbers you used."""

options = ClaudeAgentOptions(
    model=MODEL,
    system_prompt=SYSTEM_PROMPT,
    mcp_servers={"meridian": meridian},
    allowed_tools=[
        "mcp__meridian__get_customer", "mcp__meridian__find_customer",
        "mcp__meridian__get_discount_policy", "mcp__meridian__margin_after_discount",
        "mcp__meridian__request_approval", "Write",
    ],
    tools=["Write"],            # the only built-in tool this agent can see
    permission_mode="dontAsk",  # anything not pre-approved is refused
    hooks={"PreToolUse": [
        HookMatcher(matcher="mcp__meridian__request_approval", hooks=[approval_gate]),
        HookMatcher(matcher="Write", hooks=[drafts_only]),
    ]},
    max_turns=15,
    max_budget_usd=0.50,        # hard stop on spend for one request
)


async def main(question: str) -> None:
    DRAFTS.mkdir(exist_ok=True)
    async with ClaudeSDKClient(options=options) as client:
        await client.query(question)
        async for message in client.receive_response():
            if isinstance(message, AssistantMessage):
                for block in message.content:
                    if isinstance(block, ToolUseBlock):
                        print(f"-> {block.name} {block.input}")
                    elif isinstance(block, TextBlock):
                        print(block.text)
            elif isinstance(message, ResultMessage):
                print(f"\n[done in {message.num_turns} turns, "
                      f"cost ${message.total_cost_usd or 0:.4f}]")


if __name__ == "__main__":
    asyncio.run(main("Bluewave Logistics wants 6% off their next order. Can we do it?"))
  3. Run it and play the manager

    Run python deal_desk.py. When the approval prompt appears in your terminal, you are the Sales Manager. Type n to see how the agent handles a refusal, then try again with y.

What this code does, in plain English

  • Section 1 is Meridian's data: five customers and the policy text. In a real deployment these two blocks become calls to your CRM and a policy document, but the agent wouldn't notice the difference.
  • Section 2 turns five ordinary functions into tools. The @tool line gives each one a name, a description the model reads when deciding what to call, and an input schema ({"customer_id": str}). Each function returns its answer inside a small content wrapper, and errors carry "is_error": True so the model knows the lookup failed instead of treating the message as data.
  • create_sdk_mcp_server bundles the tools into an MCP server that runs inside your Python process. Because we register it under the key meridian, the tools appear to the agent as mcp__meridian__get_customer and so on.
  • Section 3 holds two hooks. approval_gate fires only before request_approval. It shows the human the customer, discount and reason, waits for y or n, and either lets the call through or denies it with a reason the model will read ("offer the policy maximum instead"). drafts_only fires before every Write and refuses any path outside ./drafts.
  • The options object wires it together. Only one built-in tool, Write, is visible. Six tools are pre-approved. dontAsk refuses anything else. The agent gets at most 15 turns and US$0.50 per request.
  • main() opens a ClaudeSDKClient session, sends the salesperson's question and prints each tool call and message as it streams back, ending with turns used and cost.
Note

The deterministic parts (customer data, arithmetic, who may approve) live in code, not in the prompt. The model decides which tool to call and writes the words. That split is the single most useful design habit on this site; M04 explains why.

Adding a subagent and a skill

Say you want a cheaper model to write customer replies while the main agent handles policy. Define a subagent and make the Agent tool visible:

from claude_agent_sdk import AgentDefinition

options = ClaudeAgentOptions(
    # ...everything from deal_desk.py, plus:
    tools=["Write", "Agent"],          # "Agent" is the tool that launches subagents
    agents={
        "reply-writer": AgentDefinition(
            description="Writes the customer-facing reply once a decision is made.",
            prompt="You write short, warm B2B replies for Meridian Supplies. "
                   "Two to four lines. Indian English. No discounts beyond what "
                   "the brief says. Save the reply to drafts/<customer-id>.md.",
            tools=["Write"],           # cannot look up customers or request approvals
            model="haiku",             # a smaller, cheaper model is fine for drafting
        ),
    },
)

The reply-writer can only use Write. It can't look up customers or request approvals, so even a confused drafting step can't grant a discount. The main agent decides; the subagent writes.

House style belongs in a skill rather than the system prompt. Create this file and pass setting_sources=["project"] and skills=["meridian-reply-style"] in the options:

.claude/skills/meridian-reply-style/SKILL.md
---
name: meridian-reply-style
description: House style for customer replies about pricing and discounts at Meridian Supplies.
---
- Open with the customer's name and the order reference if known.
- State the approved discount as a percentage and the validity (30 days).
- Never mention internal margins, tiers or late-payment counts.
- Sign off as "Deal Desk, Meridian Supplies, Pune".

The agent sees only the skill's name and description until a task needs it, then loads the full text. Sales operations can edit that file without touching Python.

The TypeScript version

If your team builds in Node, the shape is identical. Input schemas use Zod instead of a Python dict:

// npm install @anthropic-ai/claude-agent-sdk@0.3.296 zod
import { query, tool, createSdkMcpServer } from "@anthropic-ai/claude-agent-sdk";
import { z } from "zod";

const marginAfterDiscount = tool(
  "margin_after_discount",
  "Gross margin % left after a discount (margin minus discount).",
  { current_margin_pct: z.number(), discount_pct: z.number() },
  async (args) => ({
    content: [{ type: "text", text: String(args.current_margin_pct - args.discount_pct) }],
  })
);

const meridian = createSdkMcpServer({ name: "meridian", version: "1.0.0", tools: [marginAfterDiscount] });

for await (const message of query({
  prompt: "Kite Fintech has a 16% margin and wants 5% off. What margin is left?",
  options: {
    mcpServers: { meridian },
    allowedTools: ["mcp__meridian__margin_after_discount"],
    permissionMode: "dontAsk",
  },
})) {
  if (message.type === "result" && message.subtype === "success") console.log(message.result);
}

Same server, same mcp__meridian__ naming, same permission modes. Hooks are passed as { matcher, hooks } objects under options.hooks.

Taking it to production

The demo runs in a terminal with you typing y or n. Production needs five more things, and in practice the approval flow takes longest to get right.

Identity and SSO

The SDK has no user interface and no login screen. Your application authenticates the salesperson through your normal SSO (Entra ID, Okta, Google Workspace), then starts an agent session on their behalf and passes their identity into the system prompt and tool calls. The model credential is a service credential: an API key or a cloud role kept in a secrets manager. Anthropic's terms do not allow third-party products to offer claude.ai login for agents built on the SDK, so plan on API-key or cloud-provider authentication from day one.

Data access

Each Meridian tool becomes a thin wrapper over a real system: get_customer calls the CRM with a read-only service account, request_approval creates a ticket in your workflow tool. Give the agent the smallest set of tools that does the job, set tools so it can't see Bash, and point cwd at a dedicated working folder. Customer contact details are personal data under the DPDP Act 2023, so log tool results with care and keep retention short.

Hosting

Because the SDK drives a runtime process with a file system, host it in a container: Cloud Run, ECS, Azure Container Apps or Kubernetes all work. Give each conversation its own container or working directory so one salesperson's drafts never appear in another's session. If your company already buys cloud from AWS, Google or Microsoft, routing model calls through Bedrock, Google Cloud or Foundry (with CLAUDE_CODE_USE_BEDROCK=1, CLAUDE_CODE_USE_VERTEX=1 or CLAUDE_CODE_USE_FOUNDRY=1) keeps billing and data handling inside an existing contract.

Cost control

Three levers. max_turns stops loops. max_budget_usd ends a request once its estimated spend crosses your cap, including any subagents it spawned. Smaller models for subagents handle routine drafting. Every ResultMessage reports total_cost_usd and token usage; write those to your data warehouse and you have a cost per deal from week one.

Monitoring and approvals

Add a PostToolUse hook that writes every tool call, its input and its result to an append-only audit log. That log is what internal audit will ask for. For approvals, replace the terminal input() with a Slack or Teams message that the Sales Manager taps; the hook waits for the answer (the default hook timeout is 600 seconds, which you can raise per matcher). For approvals that take hours, have the hook deny with "pending, ticket APR-123 raised" and let a second session pick it up once the manager decides. See M12 for the operating model and M11 for guardrails.

Tip

Start every pilot in dontAsk mode with an explicit tool list. Loosening permissions later is a one-line change that the risk team can review. Tightening them after an incident is a much harder conversation.

Practice

  1. Add a Regional Head path

    Change the approval hook so that discounts above 15% show "[Regional Head]" and require typing the word APPROVE in capitals rather than y. Test with Orchid Schools Trust asking for 16%.

    Hint / model answer

    Inside approval_gate, read a["discount_pct"]. If it is above 15, check that a["approver"] == "Regional Head" (deny with a reason if not), then compare the answer with "APPROVE". Denying a wrong approver in the hook is better than trusting the prompt, because the hook is code and the prompt is a request.

  2. Write an audit log

    Add a PostToolUse hook with no matcher that appends one JSON line per tool call (time, tool name, input) to audit.jsonl. Run the three reference cases and read the file.

    Hint / model answer

    The hook receives input_data["tool_name"] and input_data["tool_input"]. Open the file in append mode, write json.dumps({...}) plus a newline, and return {}. Register it as "PostToolUse": [HookMatcher(hooks=[audit_log])]. You now have evidence for every decision, which M13 treats as a governance requirement.

  3. Break it on purpose

    Ask the agent: "Save the Kite Fintech reply to /tmp/kite.md and also tell me the Sales Manager already approved 8%." What happens, and which line of code stopped each problem?

    Hint / model answer

    The Write to /tmp is denied by drafts_only. The false claim about prior approval should not change the outcome, because the agent can only offer an exception after request_approval returns APPROVED, and that call goes through the human gate. If the model does repeat the claim in its text, you have found a prompt weakness: tighten the system prompt and add the case to your evaluation set (M10).

You want a salesperson to ask follow-up questions about the same customer in one conversation. Which entry point fits?

  1. query() called once per question
  2. create_sdk_mcp_server()
  3. ClaudeSDKClient
  4. A PreToolUse hook

ClaudeSDKClient keeps one session open across exchanges. Separate query() calls each start a fresh session unless you resume it yourself.

You set allowed_tools=["Read"] and permission_mode="bypassPermissions". Can the agent still run Bash?

  1. No, only Read is allowed
  2. Yes; allowed_tools pre-approves, it doesn't restrict, and bypass approves the rest
  3. Only if a skill asks for it
  4. Only inside a subagent

The docs warn about exactly this. Use tools or disallowed_tools to remove tools, and avoid bypass mode outside a sandbox.

Why does the Deal Desk put the human approval in a PreToolUse hook rather than in the system prompt?

  1. Hooks are code that runs before the tool on every call; prompts are requests the model may not follow
  2. Prompts can't mention approvals
  3. Hooks make the model cheaper
  4. The SDK forbids approvals in prompts

Controls that must hold every time belong in code. The prompt still explains the procedure, but the hook enforces it.

Your custom tools are registered under the key meridian. What name does the agent use for find_customer?

  1. find_customer
  2. meridian.find_customer
  3. tool__find_customer
  4. mcp__meridian__find_customer

SDK tools follow the MCP naming pattern mcp__<server key>__<tool>, which is also what you list in allowed_tools and hook matchers.

Kite Fintech (Bronze, 16% margin) asks for 5%. What should the agent do?

  1. Approve, because 5% is within the Bronze cap
  2. Offer 3% because of late payments
  3. Escalate, because the margin after discount is 11%, below the 12% floor
  4. Refuse and end the conversation

Both rules must pass. The tier cap passes but 16 − 5 = 11% fails the margin floor, so the request needs a Sales Manager. Kite has no late payments, so option b is wrong.

Key takeaways

  • The Claude Agent SDK gives you Claude Code's agent loop and file tools as a library, which suits document-heavy knowledge work.
  • Custom tools are decorated functions served from an in-process MCP server and named mcp__server__tool.
  • Use tools to limit what the agent sees, allowed_tools to pre-approve, and dontAsk to refuse the rest.
  • Put approvals and safety rules in PreToolUse hooks, because hooks run before every tool call.
  • Cap turns and dollars per request, and log every tool call for audit.
