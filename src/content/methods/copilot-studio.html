Copilot Studio is Microsoft's low-code tool for building agents. You describe the agent in plain language, connect knowledge (SharePoint, files, websites), give it tools (connectors, flows, MCP servers), test it in a side pane, and publish it to Teams, Microsoft 365 Copilot, a website and other channels. It sits inside the Power Platform, next to Power Automate and Power Apps, so your IT team already knows how to govern it.

If your company runs on Microsoft 365, this is usually the shortest path from "we should have an agent for that" to an agent your staff can actually open. The customer table is already in Excel on SharePoint. The approver is already in Teams. Identity is already Entra ID. That's the whole pitch, and it's a strong one.

What changed recently (as of October 2026)

The big change is the arrival of harnesses, the engine that runs what you build. Microsoft's documentation now describes three:

  • Standard harness: the established Copilot Studio model. Agents use topics (designed conversation paths), tools, knowledge and agent flows. New agents use generative orchestration by default, where an LLM planner picks topics, tools and knowledge based on their descriptions. Billing starts after you publish.
  • GitHub Copilot harness: generally available since August 2026, built for reasoning-heavy, multi-step work. You give it a goal; it plans, calls tools (connectors, knowledge, MCP servers, other agents), can create Word, Excel, PowerPoint and PDF files, and uses Markdown skills in place of topics. It runs tasks in a sandbox and bills Copilot Credits from the moment you start building, including tests.
  • Copilot chat harness: extends Microsoft 365 Copilot Chat with your organisation's knowledge.

You choose the harness when you create the agent, and Microsoft says you can't convert between the standard and GitHub Copilot harnesses later. So the choice matters. We build the Deal Desk on the standard harness, because a discount policy is exactly the kind of rule you want executed the same way every time.

Manager's lens

Copilot Studio wins on distribution and governance, and loses on portability. If the agent will live in Teams and touch SharePoint, Dataverse or Dynamics data, the time saved on security reviews alone usually justifies it. If you might move off Microsoft in three years, keep the business rules in a place you can carry with you, such as a documented policy and a small API.

When to pick it

Pick Copilot Studio when three things are true: your users live in Teams or Microsoft 365 Copilot, your data sits in SharePoint, Excel, Dataverse or a system with a Power Platform connector, and your IT team wants agents inside the same admin centre and data policies they use for Power Automate. Most large Indian companies on Microsoft 365 tick all three.

It is also a good choice when the process needs a proper approval step. Power Automate approvals have been in production use for years, and an agent can hand off to one cleanly.

Think twice when your stack is Google Workspace or Salesforce-centred (see enterprise platforms), when you need fine control over the reasoning loop (go to code: Microsoft Agent Framework or LangGraph), or when usage will be heavy and external-facing, because consumption billing can surprise you if nobody models it first.

Strengths

  • Publishes straight to Teams and Microsoft 365 Copilot with Entra ID sign-in.
  • Hundreds of prebuilt connectors plus custom connectors and MCP servers.
  • Agent flows give deterministic steps and human approvals next to LLM reasoning.
  • Central governance: environments, data policies, analytics, evaluations.
  • Makers who know Power Automate are productive on day one.

Watch-outs

  • Strong Microsoft lock-in; agents don't export to other platforms.
  • Billing in Copilot Credits takes effort to forecast.
  • Harness choice is permanent per agent.
  • Generative orchestration depends on good descriptions; vague ones cause wrong tool picks.
  • Connection identity (whose account a flow runs as) is easy to get wrong.

How it works

On the standard harness, a user message arrives through a channel such as Teams. The orchestrator reads the agent's instructions and the descriptions of every topic, tool, child agent and knowledge source. With generative orchestration on, it plans: maybe search knowledge, maybe call a tool, maybe call two in sequence. If a tool needs an input the user hasn't given, it asks for it automatically. Microsoft's own guidance is blunt that descriptions are "the most important factor" in what gets chosen.

Tools come in several kinds. A connector action calls one operation in a system (for example, list rows in an Excel table). An agent flow is a Power Automate-style flow with the trigger "When an agent calls the flow"; it runs fixed steps and returns outputs to the agent. An MCP server exposes a set of tools from any system that speaks the Model Context Protocol. Copilot Studio's billing documentation also lists computer-using agents, for screen-level automation of apps without APIs; see computer use for that pattern.

That split is the design idea to take away. Let the model handle language: working out that "Sahyadri" means C-101 and that "ten percent" is 10. Put the policy arithmetic in a flow, where the same input always gives the same output. Microsoft describes agent flows as deterministic for exactly this reason.

Build the Deal Desk agent

You need a Microsoft 365 work account with Copilot Studio access (a trial works for learning) and a SharePoint site you can edit. Screens change often, so the click-paths below name the feature rather than every button.

  1. Put the data and policy on SharePoint

    Create an Excel workbook Meridian-Customers.xlsx in a SharePoint document library. Enter the five customers and format the range as a table named Customers with columns id, name, tier, revenue_lakh, late_payments, margin_pct. Upload the discount policy as a Word or PDF document to the same site. A SharePoint list works as well as Excel; pick whichever your team will actually keep current.

  2. Create the agent

    In Copilot Studio, create a new agent on the standard harness. Name it "Meridian Deal Desk". Give it a description that says who it serves and what it does, because other agents and Microsoft 365 Copilot use that description to decide when to route to it. Paste instructions along these lines:

    You help Meridian Supplies salespeople decide on customer discount requests.
Always use the "Evaluate discount request" tool to check a request. Never do
the policy arithmetic yourself and never approve a discount the tool marks
ESCALATE. If the tool says ESCALATE, offer to raise an approval with the
"Request discount approval" tool and tell the salesperson not to confirm
anything to the customer until it is approved. Use the discount policy
document to explain the rules in plain words when asked. Keep replies short:
decision, the two numbers (cap, margin after), next step.

    What this does: it tells the orchestrator which tool owns the decision and forbids the model from overriding it. That one sentence ("never approve a discount the tool marks ESCALATE") is your human-in-the-loop rule in writing.

  3. Add the policy as knowledge

    In the agent's Knowledge section, add the SharePoint site or the policy file. Knowledge from SharePoint respects the user's own permissions, so salespeople only get answers from documents they can open.

  4. Build the "Evaluate discount request" agent flow

    From the agent's Tools section, add a new agent flow. Trigger: When an agent calls the flow, with inputs CustomerName (text) and DiscountPct (number). Then add these actions:

    • Excel Online (Business) List rows present in a table on Customers, with a filter query name eq '@{triggerBody()?['text']}' (use the dynamic content picker; the field name depends on your input).
    • Four Compose actions with the expressions below.
    • Respond to the agent with outputs: customer id, tier, cap, margin after, decision, approver.
    Row      = first(body('List_rows_present_in_a_table')?['value'])

Cap      = if(greaterOrEquals(int(outputs('Row')?['late_payments']), 2), 3,
             if(equals(outputs('Row')?['tier'], 'Gold'), 12,
               if(equals(outputs('Row')?['tier'], 'Silver'), 8, 5)))

MarginAfter = sub(float(outputs('Row')?['margin_pct']), DiscountPct)

Decision = if(and(lessOrEquals(DiscountPct, outputs('Cap')),
                  greaterOrEquals(outputs('MarginAfter'), 12)),
              'APPROVE', 'ESCALATE')

Approver = if(greater(DiscountPct, 15), 'Regional Head', 'Sales Manager')

    What this does, in plain English. Row takes the first matching customer from the Excel table. Cap applies the late-payment rule first (two or more late payments means 3%), then the tier caps. MarginAfter subtracts the discount from current margin. Decision approves only if the discount is within the cap and the margin stays at 12% or more. Approver picks the Regional Head above 15%, otherwise the Sales Manager. In the real designer, DiscountPct is a reference to the trigger input, which you insert from dynamic content. Add a condition for "no row found" that responds with an error message, so the agent asks the user to check the name.

  5. Build the "Request discount approval" agent flow

    Second agent flow, same trigger, inputs matching our standard signature: customer_id, discount_pct, approver, reason. Actions in this order:

    1. Respond to the agent straight away with "Approval requested from <approver>".
    2. Approvals Start and wait for an approval (Approve/Reject, first to respond), assigned to the Sales Manager's or Regional Head's mailbox depending on approver, with the reason and numbers in the details.
    3. Post the outcome to the salesperson in Teams, and write a row to a "Discount decisions" SharePoint list as the audit record.

    What this does: the agent gets an answer in seconds while the human takes as long as humans take. The decision lands in Teams and in a list your auditors can read, so the chat transcript is not the system of record. Agent flows also offer built-in human-in-the-loop actions (approvals and requests for information) if you prefer to stay entirely inside Copilot Studio.

  6. Name and describe the tools well

    For each flow, write a description the orchestrator can act on. "Checks a discount request against Meridian's tier caps, late-payment rule and 12% margin floor. Returns APPROVE or ESCALATE." is good. "Discount flow" is not.

  7. Test in the test pane

    Run the three reference cases and watch the activity map to see which tool was chosen and with what inputs. Then publish, and add the Teams and Microsoft 365 Copilot channel so salespeople can find it.

Kite Fintech wants 5% off. OK to give?
Discount request. The instructions say use Evaluate discount request; I have both inputs.
Evaluate discount request(CustomerName="Kite Fintech", DiscountPct=5)
{"id":"C-104","tier":"Bronze","cap":5,"margin_after":11,"decision":"ESCALATE","approver":"Sales Manager"}
Within the Bronze cap, but margin after is 11%, under the 12% floor. Offer the approval request.
Not within policy yet. 5% is inside Kite's Bronze cap, but it would take gross margin to 11% (floor is 12%). Shall I ask the Sales Manager to approve?
Yes, they're a new fintech logo we want.
Request discount approval(customer_id="C-104", discount_pct=5, approver="Sales Manager", reason="Margin after 11% below 12% floor. Rep: strategic new logo.")
"Approval requested from Sales Manager"
Sales Manager approved 5% in Teams with comment: "One order only, review at renewal."
Approved by the Sales Manager for this order only. The decision is logged in Discount decisions. Here's a draft reply to Kite…

Variation: make it autonomous

Some sales teams prefer a form. Add a SharePoint list "Discount requests" and give the agent an event trigger so it runs whenever a new item is created: it evaluates the request, files approvals where needed and writes the result back to the item. No one chats at all. Be careful with this pattern. An autonomous agent acts under the connection identity you configure, so decide deliberately whose account it uses and what that account can touch.

Taking it to production

This is where Copilot Studio earns its keep, because most of the controls already exist. Your job is to switch them on in the right order.

Environments and lifecycle

Build in a development environment, move to test and production as a solution through your normal application lifecycle process. Use connection references so the production flows use production connections. Never let the pilot that started in someone's default environment quietly become the production agent; it happens more often than anyone admits.

Identity and data access

Set the agent to authenticate users with Microsoft Entra ID. Then decide, per tool, whether it runs with the user's credentials or a fixed service connection. For the customer table, user credentials mean salespeople only see what SharePoint already lets them see. For the approval flow, a service connection is usually right, so approvals don't depend on the salesperson's own mailbox permissions.

Data policies

Power Platform data policies (DLP) control which connectors can be used together and which knowledge sources and channels agents may use. A sensible baseline for Meridian: business connectors (SharePoint, Excel, Approvals, Teams) allowed, consumer connectors blocked, public website knowledge reviewed case by case, and publishing to external channels restricted to a named group.

Cost control

Consumption is measured in Copilot Credits. Microsoft's billing documentation (checked September 2026) lists rates such as 1 credit for a classic answer, 2 for a generative answer, 5 for an agent action, 10 for tenant graph grounding and 13 per 100 agent flow actions; a single complex reply can therefore use several credits. Credits are bought as prepaid capacity pooled across the tenant, with pay-as-you-go through an Azure subscription as the overflow. Usage by employees who hold Microsoft 365 Copilot licences can be included under conditions Microsoft spells out (for example, the flow must be triggered by the agent and the agent must act as the signed-in user). Rates and rules change, so model a month of Deal Desk usage with your Microsoft partner before rollout, and set environment-level allocations so one runaway agent can't drain the tenant.

Watch out

If an environment runs out of credits, agents stop answering. Put credit consumption on the same monthly report as Power Automate capacity, and assign a named owner who gets the alert.

Monitoring and approvals

Use the built-in analytics for sessions, outcomes and tool usage, and the evaluation features (test sets with graders) before every republish. Keep the approval record in the SharePoint list, and review it monthly: how many escalations, how many approved, how long approvals took. If the Sales Manager approves 95% of escalations without comment, your policy, not your agent, may need changing. That's a useful finding.

  • Agent built in dev, promoted as a solution to test and prod
  • Entra ID authentication on; tool credentials chosen deliberately
  • DLP policy reviewed for connectors, knowledge sources and channels
  • Credit allocation set per environment; owner gets alerts
  • Evaluation test set with the three reference cases plus edge cases
  • Approval outcomes stored in a list, reviewed monthly

An HR helpdesk at a mid-sized Indian manufacturer

A typical first Copilot Studio project: an HR agent in Teams that answers leave, travel and reimbursement questions from SharePoint policies. The early win is volume, since routine questions stop reaching HR inboxes. The early problem is old documents: three versions of the travel policy sit on SharePoint and the agent quotes the wrong one. The fix is housekeeping, not AI. Practice and quiz

  1. Descriptions experiment

    Build the agent with the evaluate flow described only as "Discount flow". Ask five discount questions and note how often it is called. Then rewrite the description properly and repeat.

    Hint / model answer

    With a vague description the orchestrator may answer from the policy document instead, doing the arithmetic itself, and sometimes getting Kite wrong. A specific description that names the rules and the outputs gets the tool called consistently. Of all the fixes in Copilot Studio, this one pays back fastest.

  2. Choose the harness

    Meridian's CFO wants a second agent that reads the month's discount decisions list and produces a PowerPoint summary for the regional review. Which harness, and why? What does it cost to try?

    Hint / model answer

    The GitHub Copilot harness suits a goal-based, multi-step task that creates Office files. Note that it bills credits from the start of building, including preview and tests, so budget for experimentation. The Deal Desk itself stays on the standard harness because its rules must be deterministic, and agents can't switch harness later.

  3. Write the DLP brief

    Draft a half-page note to the Power Platform admin listing which connectors and channels the Deal Desk needs, and which should be blocked.

    Hint / model answer

    Needed: SharePoint, Excel Online (Business), Approvals, Microsoft Teams; channel Teams and Microsoft 365 Copilot; authentication via Entra ID. Block: consumer storage and social connectors, anonymous web channels, public website knowledge. Ask for a separate production environment and a credit allocation with alerting.

Under generative orchestration, what most influences which tool the agent picks?

  1. The order in which tools were added
  2. The descriptions of the tools, topics and knowledge sources
  3. Trigger phrases on each topic
  4. The number of inputs each tool has

Microsoft's documentation calls descriptions the most important factor. Trigger phrases (c) drive classic orchestration, not generative.

Why does the build put the cap and margin calculation in an agent flow instead of the instructions?

  1. Agent flows are cheaper than generative answers in every case
  2. The model can't read Excel
  3. Flows are deterministic: the same inputs always give the same decision
  4. Instructions can't mention numbers

Policy rules should be applied identically every time. The model handles language; the flow handles rules.

In the approval flow, why respond to the agent before starting the approval?

  1. So the conversation isn't left waiting while a human takes hours to decide
  2. Because approvals can't run inside agent flows
  3. To save credits on the approval action
  4. So the agent can approve on the manager's behalf

Humans are slow and chats are not. Reply quickly, wait for the approver separately, and send the outcome to Teams when it arrives.

Which statement about Copilot Studio harnesses is correct as of 2026?

  1. You can switch an agent between harnesses any time
  2. The standard harness bills from the first minute of building
  3. The GitHub Copilot harness needs a GitHub Copilot licence
  4. The GitHub Copilot harness bills credits during building and testing

Building, preview and evaluations on the GitHub Copilot harness consume credits. The standard harness bills after publish, harnesses can't be converted, and no GitHub Copilot licence is required.

Bluewave Logistics asks for 6%. What does the evaluate flow return?

  1. APPROVE: Silver cap is 8%
  2. ESCALATE to Sales Manager: 2 late payments cap it at 3%
  3. ESCALATE to Regional Head
  4. APPROVE: margin after is exactly 12%

The late-payment rule overrides the Silver cap. Margin after (12%) passes, but the cap fails, so it goes to the Sales Manager. Regional Head is only for discounts above 15%.

Key takeaways

  • Copilot Studio is the default agent builder for Microsoft 365 companies: Teams distribution, Entra identity and Power Platform governance come built in.
  • Choose the harness carefully; it can't be changed later. Use the standard harness for rule-bound processes like discounts.
  • Let the LLM handle language and put policy arithmetic in agent flows.
  • Model Copilot Credit usage before rollout and keep approval records outside the chat.
