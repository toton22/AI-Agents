Tools and function calling

After this page you will be able to explain how a model asks your systems to do things, design tools that are safe to hand to an agent, and run a working Deal Desk agent loop in Python or a no-code builder.

50 min readTracked in your progress

The big idea

A language model on its own can only write. It cannot look up a customer, check stock, raise a ticket or send an email. Every one of those needs something outside the model to actually do the work.

That something is a tool. A tool is a function in your systems, such as "get this customer's record" or "create an approval request", that you describe to the model in a structured way. When the model decides it needs one, it does not run anything itself. It writes a small, structured request: "please call find_customer with name = Sahyadri Hospitals". Your code reads that request, runs the real function, and hands the result back.

This mechanism is called function calling or tool use, and every major model vendor supports it as of 2026.

The single most important idea on this page is in that last paragraph. The model only asks. Your code decides whether to act. That gap between request and action is where you put permissions, validation, logging and human approval. It is the control point that makes agents safe enough for business.

Think of the model as a capable analyst who sits in a glass room without a computer. They can pass notes through a slot: "Please pull Kite Fintech's record." A clerk outside reads each note, checks it is allowed, does the lookup and passes back the result. The analyst never touches the systems. The clerk never makes the judgement. The tool layer is the clerk.

Manager's lens

Tools are where an agent's risk lives. A model with only read tools can give bad advice. A model with write tools can give away discounts, email customers and change records. When you approve an agent, you are really approving its tool list and the permissions behind each tool. Ask to see that list before you look at the demo.

How it works

The request and response cycle

Step by step, in plain English:

  1. You send the request and the tool list

    Along with the system prompt and the user's message, your code sends a list of tool definitions: name, description and the parameters each tool accepts.

  2. The model decides

    It reads everything and either answers directly or decides it needs a tool. If it needs one, it stops and returns a tool-use block instead of a final answer. With the Anthropic API, the response's stop_reason is "tool_use".

  3. The model writes a structured request

    The tool-use block contains a unique ID, the tool name and the input arguments as JSON. It may call several tools in one turn.

  4. Your code runs the function

    You look up the tool name, validate the arguments, check permissions, call the real system and capture the result or error.

  5. You send the result back

    The result goes back as a tool-result block that quotes the original ID, so the model knows which request it answers.

  6. Repeat until done

    The model reads the result and either calls another tool or writes the final answer. That repetition is the agent loop.

Writing tool schemas

A tool definition has three parts. With Anthropic's API they are name, description and input_schema; OpenAI and Google use near-identical shapes with slightly different field names. The parameters are described in JSON Schema, the same standard used for structured outputs in M03.

{
  "name": "margin_after_discount",
  "description": "Compute Meridian's gross margin after a discount, in percentage points: current margin minus discount. Use this for every margin check instead of doing the arithmetic yourself. Returns a single number, e.g. 12.0. Does not apply the 12% floor; you compare against the policy.",
  "input_schema": {
    "type": "object",
    "properties": {
      "current_margin_pct": {
        "type": "number",
        "description": "Customer's current gross margin in percent, from the customer record, e.g. 22"
      },
      "discount_pct": {
        "type": "number",
        "description": "Requested discount in percent, e.g. 10. Not a rupee amount."
      }
    },
    "required": ["current_margin_pct", "discount_pct"]
  }
}

What this does. The name is what the model writes when it wants the tool. The description is, frankly, the most important part: it is the only thing the model knows about the tool, so it says what the tool does, when to use it, what it returns and what it does not do. Each parameter has a type and its own description with an example. required lists the arguments the model must always supply.

Anthropic's documentation calls detailed descriptions "by far the most important factor" in tool performance and suggests at least three or four sentences per tool. Write them the way you would brief a new colleague on an internal system.

Designing good tools

Tool design is product design for a very literal user. A few principles, drawn from vendor guidance and from what tends to go wrong:

Few and clear. Five well-described tools beat thirty overlapping ones. Every extra tool is something the model can pick by mistake, and every definition costs tokens on every call. Anthropic's engineering guidance on writing tools makes the same point: build a few well-scoped tools for high-impact work rather than wrapping every API endpoint you have.

Shaped around the task, not your database. find_customer(name) is better than query_crm(sql). The first matches what the agent is trying to do and limits what it can touch. The second hands it the keys to the CRM.

Return what the model needs, no more. A customer record with six fields beats a dump of ninety columns. Smaller results are cheaper, faster and less confusing.

Idempotent where possible. An idempotent tool gives the same result if called twice. Lookups naturally are. Write tools usually are not: call request_approval twice and you get two tickets. Protect write tools with a check such as "if an open request already exists for this customer and discount, return its ID instead of creating a new one".

Enforce rules inside the tool. The tool is code, so it can refuse. If someone asks for 18% with the Sales Manager as approver, request_approval should reject it and say that discounts above 15% need the Regional Head. The model's good intentions are a bonus, not the control.

Helpful errors. "Error" teaches nothing. "No customer matches 'Kyte'. Did you mean Kite Fintech?" lets the agent recover on its own.

Read tools, write tools and permissions

Two permission ideas matter most. First, least privilege: each tool gets the narrowest access that does the job. The Deal Desk's lookup tool reads six fields of the customer table; it has no access to payroll, and no write access to anything.

Second, act as the user, not as a super-user. If a salesperson in the West region cannot see North region accounts in the CRM, the agent working for that salesperson should not either. Pass the user's identity through to the tool and let your existing access rules apply.

The agent loop

Hands-on

Time to build the real thing: the Meridian Deal Desk agent with all five tools, an approval gate and a step limit. Pick your path.

This is the n8n version, since n8n's AI Agent node maps closely onto the concepts above. Menus change often, so treat this as a map and check the workflow automation page and n8n's docs for the current click path.

  1. Put the data somewhere a tool can read

    Create a Google Sheet called "Meridian customers" with the five rows: id, name, tier, annual revenue, late payments, margin. In a second tab, paste the discount policy text.

  2. Add a chat trigger and an AI Agent node

    Start a workflow with a Chat Trigger so you can test in n8n's chat panel. Add an AI Agent node, attach a chat model sub-node (Anthropic, OpenAI or another provider) with your API key stored as an n8n credential, and paste the M03 version 3 prompt into the agent's system message.

  3. Attach the read tools

    Connect a Google Sheets tool configured to look up rows by name or ID. That covers find_customer and get_customer. Give it a clear description, just as you would in code: "Look up a Meridian customer by name or ID; returns tier, late payments and margin." Add a second Sheets tool reading the policy tab for get_discount_policy.

  4. Attach the calculation tool

    Add a Code tool for margin_after_discount that returns current margin minus discount. Describe its two inputs precisely. n8n lets the model fill tool parameters for you; check that the parameter names and descriptions match what the prompt expects.

  5. Attach the write tool behind human review

    For request_approval, use a Slack (or Microsoft Teams, or email) tool that posts the request to a #discount-approvals channel. Then add n8n's human review step to that tool, so the workflow pauses and shows a reviewer the tool name and the parameters the model chose. If the reviewer denies it, the action does not run and the agent is told it was rejected.

  6. Test the three cases

    In the chat panel, try Sahyadri 10%, Bluewave 6% and Kite 5%. Open each execution log and check which tools were called and in what order. That log is your trace.

In Zapier terms. Zapier Agents expresses the same ideas with different words: you write the agent's instructions, and you give it actions, each connected to an app such as Google Sheets, Slack or your CRM. Those actions are its tools. The design rules do not change: few actions, clear descriptions, read before write, and a person in the path for anything that leaves the company. Check Zapier's current documentation for its approval options before you rely on them.

Block 1: the tools

import os, json, difflib, itertools
import anthropic

CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold", "annual_revenue_lakh": 48, "late_payments": 0, "margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver", "annual_revenue_lakh": 19, "late_payments": 2, "margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold", "annual_revenue_lakh": 31, "late_payments": 0, "margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze", "annual_revenue_lakh": 6, "late_payments": 0, "margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver", "annual_revenue_lakh": 22, "late_payments": 1, "margin_pct": 20},
}
POLICY = ("Max discount by tier: Bronze 5%, Silver 8%, Gold 12%. Customers with 2 or more late "
          "payments this FY are capped at 3%. Margin after discount must stay at or above 12%. "
          "Above the cap needs Sales Manager approval; above 15% needs Regional Head approval.")
_ticket_numbers = itertools.count(1001)
_open_requests = {}

def get_customer(customer_id: str) -> dict:
    return CUSTOMERS.get(customer_id) or {"error": f"No customer with id {customer_id}. Try find_customer."}

def find_customer(name: str) -> dict:
    by_name = {c["name"].lower(): c for c in CUSTOMERS.values()}
    hits = [c for n, c in by_name.items() if name.lower() in n]
    if not hits:
        hits = [by_name[n] for n in difflib.get_close_matches(name.lower(), by_name, n=3, cutoff=0.6)]
    if len(hits) == 1:
        return hits[0]
    if not hits:
        return {"error": f"No customer matches '{name}'. Ask the salesperson for the exact name."}
    return {"error": "Several customers match; ask which one.", "candidates": [c["name"] for c in hits]}

def get_discount_policy() -> str:
    return POLICY

def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    return round(float(current_margin_pct) - float(discount_pct), 2)

def request_approval(customer_id: str, discount_pct: float, approver: str, reason: str) -> str:
    if customer_id not in CUSTOMERS:
        return f"Error: unknown customer_id {customer_id}."
    if discount_pct > 15 and approver != "Regional Head":
        return "Error: discounts above 15% must go to the Regional Head."
    key = (customer_id, discount_pct, approver)
    if key in _open_requests:                       # idempotent: no duplicate tickets
        return f"Request {_open_requests[key]} already exists. Status: pending."
    ticket = f"APR-{next(_ticket_numbers)}"
    _open_requests[key] = ticket                    # in production: create a real ticket here
    return f"Approval request {ticket} created for {approver}. Status: pending."

What this does. CUSTOMERS and POLICY stand in for your CRM and policy store; in production these functions would call real systems. find_customer tries a simple "name contains" match, then a fuzzy match, and returns either one record, an error, or a list of candidates so the agent can ask which one. margin_after_discount does the arithmetic so the model never has to. request_approval is the write tool, and it enforces rules itself: it rejects unknown customers, refuses to send a request above 15% to anyone but the Regional Head, and returns the existing ticket rather than creating a duplicate.

Block 2: the tool definitions

def tool(name, description, properties=None, required=None):
    return {"name": name, "description": description,
            "input_schema": {"type": "object", "properties": properties or {}, "required": required or []}}

TOOLS = [
    tool("find_customer",
         "Find a Meridian customer by name; partial or misspelt names are fine. Returns id, tier, "
         "annual revenue, late payments this FY and current gross margin %. Use this when the "
         "salesperson gives a name. If it returns candidates, ask the salesperson which one.",
         {"name": {"type": "string", "description": "Customer name as written, e.g. 'Sahyadri'"}}, ["name"]),
    tool("get_customer",
         "Get one customer record by exact ID such as 'C-101'. Use only when you already know the ID.",
         {"customer_id": {"type": "string", "description": "Customer ID, e.g. 'C-104'"}}, ["customer_id"]),
    tool("get_discount_policy",
         "Return Meridian's current discount policy. Call it before every decision; never rely on memory."),
    tool("margin_after_discount",
         "Compute gross margin after a discount in percentage points (current margin minus discount). "
         "Use it for every margin check. Returns one number; compare it with the 12% floor yourself.",
         {"current_margin_pct": {"type": "number", "description": "Current margin %, from the customer record"},
          "discount_pct": {"type": "number", "description": "Requested discount %, not a rupee amount"}},
         ["current_margin_pct", "discount_pct"]),
    tool("request_approval",
         "WRITE ACTION: create an approval request for a discount outside policy. Use only when the "
         "discount is above the customer's cap or margin would fall below 12%. Approver is 'Sales Manager' "
         "for up to 15%, 'Regional Head' above 15%. Never use it for discounts within policy.",
         {"customer_id": {"type": "string"},
          "discount_pct": {"type": "number"},
          "approver": {"type": "string", "enum": ["Sales Manager", "Regional Head"]},
          "reason": {"type": "string", "description": "One sentence with the numbers, e.g. cap and margin"}},
         ["customer_id", "discount_pct", "approver", "reason"]),
]

What this does. The small tool() helper builds the three-part definition the API expects, so each tool takes a few lines instead of fifteen. Each description says what the tool does, when to use it and what it returns. The enum on approver means the model can only choose one of the two valid approvers. Note that request_approval announces itself as a write action in its description; that helps the model treat it with care, but the real control is in Block 3.

Block 3: the agent loop

MODEL = os.getenv("MODEL", "claude-sonnet-5-5")
client = anthropic.Anthropic()
SYSTEM = open("deal_desk_prompt_v3.txt", encoding="utf-8").read()
FUNCTIONS = {"find_customer": find_customer, "get_customer": get_customer,
             "get_discount_policy": get_discount_policy,
             "margin_after_discount": margin_after_discount, "request_approval": request_approval}
WRITE_TOOLS = {"request_approval"}
MAX_STEPS = 8

def run_tool(name: str, args: dict) -> tuple[str, bool]:
    """Run one tool. Returns (result_text, is_error)."""
    if name in WRITE_TOOLS:
        print(f"\n[approval gate] The agent wants to call {name} with {args}")
        if input("Allow this action? (y/n) ").strip().lower() != "y":
            return "The user declined this action. Do not retry it; explain what was blocked.", True
    try:
        return json.dumps(FUNCTIONS[name](**args)), False
    except Exception as exc:
        return f"Tool {name} failed: {exc}. Check the arguments and try again.", True

def run_agent(request: str) -> str:
    messages = [{"role": "user", "content": request}]
    for step in range(MAX_STEPS):
        response = client.messages.create(model=MODEL, max_tokens=1500, system=SYSTEM,
                                          tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return "".join(block.text for block in response.content if block.type == "text")
        results = []
        for block in response.content:
            if block.type == "tool_use":
                print(f"  step {step + 1}: {block.name}({block.input})")
                output, is_error = run_tool(block.name, block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": output, "is_error": is_error})
        messages.append({"role": "user", "content": results})
    return "Stopped at the step limit. Please pass this request to the Sales Manager."

if __name__ == "__main__":
    print(run_agent("Kite Fintech wants 5% on the next order. OK?"))

What this does, line by line.

  • The first lines read the model ID and system prompt from outside the code and create the API client. FUNCTIONS maps each tool name the model might write to the real Python function. WRITE_TOOLS lists the tools that change something. MAX_STEPS caps the loop.
  • run_tool is the clerk outside the glass room. For a write tool it first prints what the agent wants to do and asks a person to confirm; a "no" goes back to the model as an error result, with an instruction not to retry. Otherwise it calls the function with the model's arguments, turns the result into text, and catches any failure so a bad call becomes a helpful error message instead of a crash.
  • run_agent is the loop. It sends the conversation, system prompt and tool list to the model and stores the model's reply in the history. If stop_reason is anything other than "tool_use", the model has finished, so we return its text.
  • Otherwise, for every tool-use block in the reply (there may be several), we run the tool and build a tool_result that quotes the block's id. All results go back together in one user message, and the loop goes round again.
  • If eight rounds pass without a final answer, the agent stops and hands over to a person rather than spending more money.

Run python deal_desk_agent.py. You should see the steps printed as the agent works, the approval gate asking you to confirm, and a final message close to the Kite trace above. Change the request to Sahyadri 10% and Bluewave 6% and compare. That is a working Level 4 agent in about 120 lines, and the loop itself is around 40 of them. The rest is business logic and tool descriptions, which is where your effort should go.

Note

In the trace earlier, the salesperson confirms that the approval request may be filed, and the Sales Manager then makes the actual decision in the approval system. Those are two different human checkpoints. The gate in this code protects the action; the approval request routes the decision. For a low-risk internal action like filing a request, many teams later remove the first gate. For anything that reaches a customer, keep it.

In the business

Composite, anonymised examples of tool design choices in real functions.

Case · Sales operations

The CRM tool that could do everything

A sales-ops team at a B2B software firm gave their agent one tool: a general CRM API wrapper that could read or update any object. In testing, the agent "helpfully" updated a deal stage while answering a question about it. They replaced the wrapper with four narrow tools (find account, get open deals, log a note, request a stage change), of which only the note tool writes directly. Stage changes now go to the account owner for a click to confirm.

Case · Customer service

Refunds behind a threshold

An e-commerce service team let its agent issue refunds through a tool. The tool itself checks the amount: below a set rupee limit with a matching order, it processes; above it, it creates a supervisor task instead and tells the agent so. The prompt describes the threshold too, but the team knows the tool is what actually holds the line.

Case · Supply chain

Idempotency saves a duplicate order

A distributor's reorder agent hit a timeout while creating a purchase order, retried, and created a second one. Nobody noticed until two trucks arrived. The fix was a request key on the create-PO tool: the same key twice returns the existing PO. It is a standard pattern in payments and ordering systems, and it belongs on every write tool an agent can retry.

Case · HR

Acting as the employee, not as HR admin

An HR agent that answers "how much leave do I have?" was first built with an admin service account, so in principle it could read anyone's balance. Security review sent it back. The rebuilt tool passes the logged-in employee's identity to the HR system, which returns only that person's data. Same agent, same prompt; very different risk.

Pitfalls

Too many tools. Teams expose every endpoint "in case it's useful". Selection accuracy drops, token costs rise, and the attack surface grows. Start with the five tools the job needs and add only when tests show a gap.

Vague descriptions. "Gets customer data" leaves the model guessing what comes back and when to call it. Most "the agent picked the wrong tool" problems are description problems.

Trusting model arguments. The model can pass a wrong customer ID, a discount as 0.1 instead of 10, or a rupee amount where a percentage was expected. Validate types, ranges and existence in the tool, and return a clear error.

No step limit or timeout. A tool that fails silently can send the agent round in circles, calling the model again and again. Always cap steps, put timeouts on tool calls, and alert on runs that hit the cap.

Ignoring cost and latency. Every round trip costs a model call plus the tool's own time. Tool definitions are sent as input tokens on every call, and Anthropic's pricing page notes that enabling tools also adds a few hundred tokens of system instructions behind the scenes.

A five-step agent with slow tools can easily take 15 to 30 seconds. Keep tool results short, let the model call independent tools in the same turn where your vendor supports it, and use prompt caching for the stable prefix.

Fuzzy matching gone wrong. "Hospital" matches Sahyadri Hospitals today, because Meridian has only one hospital customer. The day it signs a second one, the same lookup quietly picks whichever comes first, unless the tool checks. The find_customer above returns a list of candidates whenever more than one customer matches; make sure your real tool does too, and that the prompt tells the agent to ask.

Write tools without an audit trail. If you cannot answer "which agent run created APR-1001, with what inputs, approved by whom?", you will struggle in your first audit. Log every tool call with its inputs, result, user identity and timestamp.

  • Every tool is classified read or write and low or high impact, with the matching control.
  • Descriptions say what, when, what it returns and what it does not do.
  • Tools validate inputs and enforce hard business rules themselves.
  • Write tools are idempotent or de-duplicated, and external writes need human approval.
  • Tools act with the user's permissions, not a super-user account.
  • The loop has a step limit, tool timeouts and a full log of calls.

Practice

  1. Write a tool description

    Meridian wants a get_order_history(customer_id, months) tool so the agent can see recent order values. Write the description and the parameter descriptions.

    Hint / model answer

    Description: "Return a customer's orders for the last N months: order date, order value in rupees and product categories. Use when the salesperson mentions order size or volume, or when a discount request depends on order value. Read-only. Returns at most 24 months; does not include quotes or cancelled orders." Parameters: customer_id (string, "Customer ID such as C-101"), months (integer, "Number of months back, 1 to 24; default to 6 if unsure").

  2. Classify the tools

    Put these into the read/write and low/high impact grid and name the control for each: get_stock_level, send_quote_to_customer, create_draft_invoice, get_employee_salary, update_customer_credit_limit.

    Hint / model answer

    get_stock_level: read, low; log it. send_quote_to_customer: write, high (external); human approval every time. create_draft_invoice: write, low (internal draft); validate and de-duplicate. get_employee_salary: read, high (personal data); restrict to the user's own access, probably not an agent tool at all. update_customer_credit_limit: write, high (financial exposure); approval by credit control plus limits enforced in the tool.

  3. Trace the Orchid case

    Write the full tool-call trace for "Orchid Schools wants 14% for the new academic year".

    Hint / model answer

    find_customer("Orchid Schools") returns C-103, Gold, 0 late, margin 25. get_discount_policy(). 14% is above the Gold cap of 12% but not above 15%, so the Sales Manager approves. margin_after_discount(25, 14) returns 11, below the floor, which is a second reason. request_approval(customer_id="C-103", discount_pct=14, approver="Sales Manager", reason="14% exceeds Gold cap of 12%; margin after discount would be 11%, below the 12% floor."). Final answer explains both reasons and suggests 12% as the most that is within policy (margin 13%).

  4. Break the loop

    What happens in the Python code if find_customer raises an exception because the CRM is down? Walk through it and suggest one improvement.

    Hint / model answer

    run_tool catches the exception and returns "Tool find_customer failed: ..." with is_error True. The model sees the error and will probably retry or tell the user it cannot reach the customer data. It might retry several times until MAX_STEPS. Improvement: return a specific message such as "CRM unavailable; do not retry; tell the salesperson to try again later", and add a timeout plus an alert when a tool fails repeatedly.

  5. Estimate the latency

    Each model call takes about 2 seconds and each tool about 0.5 seconds. The Kite request needs four tool calls in four separate rounds, then a final answer. Roughly how long does the salesperson wait (ignore the human gate)? How could you cut it?

    Hint / model answer

    Five model calls × 2 s = 10 s, plus four tools × 0.5 s = 2 s, so about 12 seconds. To cut it: let the model request find_customer and get_discount_policy in the same turn (they are independent), put the policy in the cached system prompt so no tool call is needed, use a faster model for this simple task, and stream a "checking..." message so the wait feels shorter.

Quiz

When a model "calls a tool", what actually happens?

  1. The model connects to your database and runs the query
  2. The model returns a structured request; your code decides whether to run the function and sends back the result
  3. The vendor's servers run your Python function
  4. The model guesses the result without running anything

For tools you define, the model only emits a request with a name and arguments. Execution happens in your code, which is exactly why you can add permissions and approvals there.

Which part of a tool definition most affects whether the model uses the tool correctly?

  1. The tool's name length
  2. The order of the tools in the list
  3. Whether parameters are marked required
  4. The description: what it does, when to use it, what it returns

The description is all the model knows about the tool. Vendor documentation singles out detailed descriptions as the most important factor.

Kite Fintech (Bronze, margin 16%, no late payments) asks for 5%. What should the agent do?

  1. Escalate to the Sales Manager, because margin would fall to 11%
  2. Approve, because 5% equals the Bronze cap
  3. Escalate to the Regional Head
  4. Refuse and end the conversation

The cap check passes, but the margin check fails: 16 minus 5 is 11, below the 12% floor. Margin failures go to the Sales Manager. Option (b) is the trap the Kite case is designed to catch.

Why should request_approval check for an existing open request before creating a new one?

  1. To make the tool faster
  2. Because the API requires it
  3. So that retries do not create duplicate tickets, making the write tool idempotent
  4. To hide requests from managers

Agents and networks retry. Without de-duplication, each retry creates another ticket or order. Idempotency makes retries safe.

An HR agent's leave tool runs under an HR admin account. What is the main risk, and the fix?

  1. It will be slow; use a faster model
  2. It could expose any employee's data; pass the user's identity so existing access rules apply
  3. It costs more tokens; shorten the description
  4. There is no risk, because the prompt says to protect privacy

Least privilege and acting as the user keep the agent inside the same access rules as the person it serves. A prompt instruction is not an access control.

In the Python loop, what ends a run?

  1. The first tool call
  2. Any tool error
  3. A response whose stop_reason is not "tool_use", or reaching MAX_STEPS
  4. The approval gate saying yes

The loop keeps going while the model asks for tools. It stops on a final answer or at the step limit. Errors and approval decisions are returned to the model as results so it can respond to them.

Key takeaways

  • The model only requests tool calls. Your code runs them, which makes the tool layer your main control point.
  • A tool is a name, a detailed description and a JSON schema of parameters. The description matters most.
  • Design few, task-shaped tools that return only what is needed, validate inputs and enforce hard rules themselves.
  • Classify tools as read or write and by impact. Write tools need de-duplication; external or irreversible ones need human approval.
  • The agent loop is short: call, check for tool use, run tools, return results, repeat, with a step limit and full logging.
