Evaluation: prove the agent works

Build a golden test set for the Meridian Deal Desk agent, score it with code checks, an LLM judge and human review, and set up the release gates that stop a bad prompt or model change from reaching your sales team.

55 min readTracked in your progress

The big idea

"It worked in the demo." Every agent project hears this sentence, usually a week before something embarrassing happens in production.

A demo is one input, picked by the person who built the agent, run once, on a good day. That is an anecdote. Your sales team will send the agent thousands of messages: typos, half-finished requests, customers it has never heard of, and the occasional salesperson who tries to talk it into a bigger discount. The demo told you almost nothing about any of those.

There is a second problem. Language models are not fully deterministic. Ask the same question twice and you can get two different tool sequences, two different phrasings and, now and then, two different decisions. So "I tried it and it worked" is weaker still: you tried it once.

An evaluation (everyone says "eval") is the fix. It is a repeatable test with three parts: a set of inputs, the answer you expect for each, and a grader that compares what the agent did with what it should have done. Run it, get a score. Change the prompt, run it again, compare scores. That is the whole idea, and it is the single habit that separates teams who ship agents from teams who keep demoing them.

If you have worked in audit or quality, you already know this pattern. An auditor does not certify a process by watching one transaction. They pull a sample, including the awkward ones, and test each against the rule. An eval is a standing audit sample for your agent, re-run every time anything changes.

Manager's lens

You would never approve a new credit policy on the strength of one worked example. Treat an agent the same way. Before you sign off, ask three questions: what is in your test set and who wrote the expected answers, how often does it run, and what is the pass rate on the cases that would hurt us most if they went wrong? If the team cannot answer, the agent is not ready, however good the demo looked.

This module uses the Meridian Deal Desk agent you have been building since M04. By the end you will have a 12-case golden set, a Python eval runner that prints a pass/fail table, a spreadsheet version for teams that do not code, and a release process that uses both.

How it works

Start with a golden test set

A golden set is a fixed list of realistic inputs with agreed correct outcomes. "Agreed" matters. The expected answers should come from the people who own the business rule, here Meridian's sales operations head, and not from whatever the agent happened to say last Tuesday.

Good golden sets mix five kinds of case. Core cases are the everyday requests. Boundary cases sit exactly on a rule's edge, where off-by-one bugs live. Messy cases have typos, missing details or unknown customers. Adversarial cases try to trick the agent. Out-of-scope cases ask for things the agent should decline. Here is the Deal Desk set. The first three come straight from the policy; the rest are edge cases designed to break things.

Notice how many cases sit on a boundary. That is deliberate. Agents rarely fail on the obvious middle of a rule. They fail at "exactly 12%", at "2 late payments, not 1", at "15% versus 15.5%". Twelve cases is a starting point for a classroom; a production agent at a real company usually grows to a few hundred, mostly harvested from real traffic.

Outcome versus trajectory

You can grade an agent in two places. Outcome evaluation checks the end state: was the decision right, was an approval ticket raised for the right person, does the reply say the right thing? Trajectory evaluation checks the path: did it look up the customer, did it actually call the margin tool, did it avoid tools it should never touch?

Outcome checks matter most, because outcomes are what the business feels. But an agent can reach the right answer by luck, and luck does not hold. Here is a run that would pass a lazy outcome check on some days and fail on others.

Kite Fintech wants 5% on the renewal.
Kite is a customer. Let me check their tier.
find_customer(name="Kite Fintech")
{"id":"C-104","tier":"Bronze","margin":16,"late":0}
Bronze cap is 5%, and they asked for 5%. That is within policy.
DECISION: APPROVE. Good news, 5% is within policy for Kite Fintech. Draft reply attached.

The agent never called margin_after_discount, so it never noticed that 16 − 5 = 11% breaks the 12% floor. A trajectory check ("G03 must call margin_after_discount") catches the root cause. An outcome check ("G03 must escalate") catches the damage. You want both: outcome checks to protect the business, trajectory checks to tell the engineers what to fix.

One caution. Do not over-specify the path. If you insist on an exact sequence of five calls, you will fail a perfectly good run that looked up the policy before the customer. Check for required steps and forbidden steps, not a script.

Three kinds of grader

Once you know what to check, you need something to do the checking. There are three options, and serious teams use all three.

GraderGood atWeak atDeal Desk example
Code-based checksFast, cheap, identical every run. Perfect for facts with one right answer.Judging tone, clarity or anything fuzzy.Decision equals "escalate"; request_approval was called with approver "Sales Manager".
LLM-as-judgeGrading open text against a rubric at scale.Can be biased (likes longer answers, likes its own style); needs calibrating against humans."Is the draft reply clear, and does it avoid leaking internal margins?" scored 1 to 5.
Human reviewThe real standard. Catches what nobody thought to test.Slow and expensive; reviewers drift and disagree.Sales ops head reviews 20 sampled replies a week.

The usual pattern: code checks on every case, every run. An LLM judge for the text quality questions. Humans to write the expected answers, to spot-check the judge, and to review a weekly sample from production. Anthropic's engineering guide on agent evals makes the same three-way split, and it is worth reading in full (link at the end).

The judge needs its own test. Before you trust it, have two humans score 30 or so replies, run the judge on the same replies, and see how often they agree. If the judge disagrees with your people more than they disagree with each other, fix the rubric before you use it.

The metrics that matter

MetricPlain-English meaningA sensible Deal Desk bar
Task success rateShare of cases where the outcome was right, on every repeat100% on core and boundary cases before launch
Tool-call accuracyCalled the required tools with sensible arguments, avoided forbidden onesNo missing margin checks, ever
Escalation precisionOf the requests it escalated, how many truly needed a humanHigh, or managers drown in noise
Escalation recallOf the requests that needed a human, how many it escalated100%. A missed escalation is a promise you cannot keep
Hallucination rateReplies that state a fact not supported by a tool result (an invented tier, a made-up customer)Zero on the golden set; sampled weekly in production
LatencySeconds from request to reply, usually reported at the median and the slow end (p95)Under 15 seconds at p95 for a chat tool
Cost per taskModel tokens plus tool calls per completed requestTracked per release; see M12

Precision and recall deserve a sentence each, because managers meet them everywhere from fraud screening to hiring. Recall asks "did we catch everything we should have?" Precision asks "of the things we flagged, how many were real?" For a deal desk, missing an escalation means a salesperson promises a discount the company never approved, so recall comes first. But an agent that escalates everything has perfect recall and is useless. You need both numbers on the scorecard.

Because runs vary, run each case several times. A case "passes" only if it passes every time. A customer-facing agent that is right two times out of three is wrong once in every three conversations, and the salesperson who got the wrong answer will not care about your average.

Offline, online, shadow and A/B

Offline evals run on your golden set before anything reaches a user. They are your unit tests. Online evals run on live traffic after release: automatic checks on every conversation (did a promised discount match an approval?), an LLM judge on a sample, and human review on a smaller sample. Offline tells you whether to ship. Online tells you whether reality agrees.

Between the two sit two release tactics borrowed from software and from marketing. In shadow mode the new agent receives real requests alongside the current process, but its answers go to a log, not to the salesperson. You compare its decisions with what the human deal desk actually did. No customer risk, real inputs. In an A/B test or canary release, a small slice of users, say 10% of the sales team, gets the new version while everyone else stays on the old one, and you compare success rate, escalations, latency and complaints.

Regression testing when anything changes

Here is the bit that usually goes wrong. The agent passes its evals in March, goes live, and everyone moves on. In June someone tweaks the system prompt to make replies friendlier. In August the vendor retires the model version and the platform quietly moves you to a newer one. Each change can fix one thing and break another, and nobody re-ran anything.

A regression test is simply your golden set re-run after a change, with the rule that the score may not go down on any case that previously passed. Wire it into the release process so it runs automatically on every change to the prompt, the tools, the knowledge base or the model version. Pin model versions where your vendor allows it, so upgrades happen when you choose, after the evals pass.

Eval tools, briefly

You can do everything on this page with a spreadsheet and fifty lines of Python. Tools earn their place once you have hundreds of cases, several agents and a team. As of 2026 the commonly used ones include:

  • LangSmith (LangChain): datasets, offline experiments, online evaluators and tracing; works beyond LangChain apps.
  • Langfuse: open-source, self-hostable tracing and evals built on OpenTelemetry. Popular where data must stay in-house.
  • Braintrust: a hosted platform for experiments, scoring and production observability of agents.
  • promptfoo: an open-source command-line tool for test suites and red-teaming, easy to run in a build pipeline.
  • OpenAI Evals: the open-source evals framework on GitHub, plus evals you can configure and run in the OpenAI dashboard.
  • Arize Phoenix: open-source observability and evaluation, built on OpenTelemetry.

Pick on three questions: where does the trace data live (matters under the DPDP Act, see M11), does it work with the framework you already use, and can non-engineers read the results?

Hands-on: golden-set evals

You will run the 12 Deal Desk cases against the agent and get a pass/fail table. The Python path ships with a deliberately buggy stand-in agent so you can run it offline, with no API key, and watch it catch a real mistake. The no-code path does the same job in a spreadsheet.

Many evaluation programmes in companies start exactly like this, and some never need more. Open Excel or Google Sheets and create one row per case.

ColHeaderWhat goes in it
AIDG01 to G12
BInputThe exact message, copied from the table above
CExpected decisionapprove / escalate / clarify
DExpected approverSales Manager, Regional Head or blank
EMust mentionA check word, e.g. "margin" for G03
F, G, HRun 1, 2, 3 decisionWhat the agent decided each time
IApprover givenWho the agent escalated to
JReply (run 1)Paste the agent's reply
KPass?Formula below
LReviewer noteHuman comment on tone and safety
  1. Fill columns A to E with the business owner

    Sit with whoever owns the discount policy and agree the expected answers before anyone runs the agent. This is the most valuable 30 minutes in the whole exercise.

  2. Run each case three times

    Paste each input into your agent (a Copilot Studio test pane, a Custom GPT, or the Agent Lab) in a fresh conversation each time. Record the decision in F, G and H.

  3. Add the pass formula in K2 and fill down

    =IF(AND(F2=C2, G2=C2, H2=C2, OR(D2="", I2=D2), OR(E2="", ISNUMBER(SEARCH(E2, J2)))), "PASS", "FAIL"). A case passes only if all three runs match, the approver is right where one is required, and the check word appears.

  4. Add a summary row

    Success rate: =COUNTIF(K2:K13, "PASS")/COUNTA(K2:K13). Escalation recall: =COUNTIFS(C2:C13, "escalate", F2:F13, "escalate")/COUNTIF(C2:C13, "escalate").

  5. Save a dated copy every time you change the agent

    One tab per release (v1.0, v1.1, …). Comparing tabs is your regression test. Colour any case that went from PASS to FAIL in red and do not release until it is green again.

Honestly, this is slow for more than a few dozen cases, and copy-pasting invites errors. But it gets the business owner involved in defining "correct", which is the part most technical teams get wrong.

2. mock_agent.py: a rule-based stand-in that behaves like the agent and returns the same shape of result. It has one bug planted on purpose. See if you can spot it before running anything.

"""A rule-based stand-in for the Deal Desk agent, with one bug planted on purpose."""
import re

CUSTOMERS = {
    "Sahyadri Hospitals": {"id": "C-101", "tier": "Gold", "late": 0, "margin": 22},
    "Bluewave Logistics": {"id": "C-102", "tier": "Silver", "late": 2, "margin": 18},
    "Orchid Schools Trust": {"id": "C-103", "tier": "Gold", "late": 0, "margin": 25},
    "Kite Fintech": {"id": "C-104", "tier": "Bronze", "late": 0, "margin": 16},
    "Trident Engineering": {"id": "C-105", "tier": "Silver", "late": 1, "margin": 20},
}
CAPS = {"Bronze": 5, "Silver": 8, "Gold": 12}


def run(message):
    calls = ["find_customer"]
    text = message.lower()
    name = next((n for n in CUSTOMERS if n.split()[0].lower() in text), None)
    if name is None:
        return {"decision": "clarify", "approver": None, "tool_calls": calls,
                "reply": "DECISION: CLARIFY\nI could not find that customer. Which account is it?"}
    match = re.search(r"(\d+(?:\.\d+)?)\s*(%|percent)", text)
    if match is None:
        return {"decision": "clarify", "approver": None, "tool_calls": calls,
                "reply": "DECISION: CLARIFY\nHow much discount is the customer asking for?"}
    pct = float(match.group(1))
    c = CUSTOMERS[name]
    calls += ["get_discount_policy", "margin_after_discount"]
    cap = 3 if c["late"] >= 2 else CAPS[c["tier"]]
    margin_after = c["margin"] - pct
    if pct <= cap and margin_after > 12:          # BUG: policy says "at or above 12"
        return {"decision": "approve", "approver": None, "tool_calls": calls,
                "reply": f"DECISION: APPROVE\n{pct:g}% is within policy for {name}."}
    approver = "Regional Head" if pct > 15 else "Sales Manager"
    calls.append("request_approval")
    return {"decision": "escalate", "approver": approver, "tool_calls": calls,
            "reply": f"DECISION: ESCALATE\nNot yet. I have sent {pct:g}% for {name} to the {approver}."}

3. run_evals.py: runs every case three times, grades it, prints a table and saves a CSV.

"""Run the Deal Desk golden set and print a pass/fail table."""
import csv
import json
import sys
import time
from datetime import datetime

REPEATS = 3  # LLMs vary run to run, so each case must pass every time


def load_cases(path="golden_set.json"):
    with open(path, encoding="utf-8") as f:
        return json.load(f)


def check(case, result):
    """Return a list of reasons the result failed. Empty list means pass."""
    exp, why = case["expected"], []
    if result["decision"] != exp["decision"]:
        why.append(f"decision {result['decision']} (wanted {exp['decision']})")
    if "approver" in exp and result.get("approver") != exp["approver"]:
        why.append(f"approver {result.get('approver')} (wanted {exp['approver']})")
    for tool in exp.get("must_call", []):
        if tool not in result["tool_calls"]:
            why.append(f"never called {tool}")
    for tool in exp.get("must_not_call", []):
        if tool in result["tool_calls"]:
            why.append(f"should not call {tool}")
    for phrase in exp.get("reply_must_not_contain", []):
        if phrase.lower() in result["reply"].lower():
            why.append(f"reply says '{phrase}'")
    return why


def run_suite(agent, cases):
    rows = []
    for case in cases:
        reasons, decisions, seconds = [], [], []
        for _ in range(REPEATS):
            start = time.perf_counter()
            result = agent(case["input"])
            seconds.append(time.perf_counter() - start)
            decisions.append(result["decision"])
            reasons += check(case, result)
        rows.append({"id": case["id"], "tag": case["tag"],
                     "expected": case["expected"]["decision"],
                     "actual": max(set(decisions), key=decisions.count),
                     "passed": not reasons,
                     "why": "; ".join(sorted(set(reasons))),
                     "seconds": round(sum(seconds) / len(seconds), 2)})
    return rows


def report(rows):
    print(f"{'ID':<4} {'TAG':<12} {'RESULT':<6} WHY")
    for r in rows:
        print(f"{r['id']:<4} {r['tag']:<12} {'PASS' if r['passed'] else 'FAIL':<6} {r['why']}")
    passed = sum(r["passed"] for r in rows)
    flagged = [r for r in rows if r["actual"] == "escalate"]
    needed = [r for r in rows if r["expected"] == "escalate"]
    hits = [r for r in flagged if r["expected"] == "escalate"]
    print(f"\nTask success rate:     {passed}/{len(rows)} = {passed / len(rows):.0%}")
    print(f"Escalation precision:  {len(hits)}/{len(flagged)}")
    print(f"Escalation recall:     {len(hits)}/{len(needed)}")
    print(f"Mean seconds per case: {sum(r['seconds'] for r in rows) / len(rows):.2f}")


def save(rows):
    name = f"eval_{datetime.now():%Y%m%d_%H%M}.csv"
    with open(name, "w", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=rows[0].keys())
        writer.writeheader()
        writer.writerows(rows)
    print(f"Saved {name}")


if __name__ == "__main__":
    if "--live" in sys.argv:
        from deal_desk_agent import run as agent   # the real agent (see M11)
    else:
        from mock_agent import run as agent        # offline stand-in, no API key
    results = run_suite(agent, load_cases())
    report(results)
    save(results)
    sys.exit(0 if all(r["passed"] for r in results) else 1)

What this does, in plain English:

  • REPEATS = 3 runs each case three times, because a model can answer differently each time. A case passes only if every run passes.
  • check() is the code-based grader. It compares the decision and approver with the expected ones, checks required and forbidden tool calls (the trajectory), and scans the reply for banned phrases. It returns reasons rather than a bare tick, so a failure tells you what to fix.
  • run_suite() loops over the cases, times each run, and records the most common decision.
  • report() prints the table and the headline metrics: success rate, escalation precision and recall, and average seconds per case.
  • save() writes a dated CSV, so you keep a history to compare releases.
  • The last line exits with code 1 if anything failed. Build pipelines treat that as "stop the release", which is how this becomes an automatic regression gate.

If you built your own agent on the raw API page, add a list that records each tool name as it runs, and ask the model to start its final message with DECISION: APPROVE, ESCALATE or CLARIFY so the decision can be read reliably.

Adding an LLM judge for reply quality

Code checks cannot tell you whether a draft reply is clear or whether it leaks Meridian's margin to the customer. A judge can. Install the SDK with pip install "anthropic==1.13.0" and set ANTHROPIC_API_KEY in your environment.

import json
import os

import anthropic

JUDGE_MODEL = os.getenv("JUDGE_MODEL", "claude-sonnet-5-5")
client = anthropic.Anthropic()

RUBRIC = """You grade replies from a sales deal-desk assistant to a Meridian salesperson.
Score 1-5 on each criterion:
- correct: the reply states the same decision as the expected decision.
- clear: a busy salesperson knows exactly what to do next.
- safe: no promise to the customer before approval; no internal margin figures in customer text.
Return only JSON: {"correct": n, "clear": n, "safe": n, "reason": "one sentence"}"""


def judge(case, reply):
    prompt = (f"Salesperson asked: {case['input']}\n"
              f"Expected decision: {case['expected']['decision']}\n"
              f"Assistant reply:\n{reply}")
    msg = client.messages.create(model=JUDGE_MODEL, max_tokens=300, system=RUBRIC,
                                 messages=[{"role": "user", "content": prompt}])
    return json.loads(msg.content[0].text)

What this does: it sends the original request, the expected decision and the agent's reply to a second model with a short rubric, and asks for three 1-to-5 scores plus a one-line reason, as JSON. Call judge(case, result["reply"]) inside run_suite and fail any case that scores below 4 on "safe". Two practical notes. Use a strong model as the judge even if the agent runs on a cheaper one. And calibrate it: compare its scores with your sales ops head's on a sample before trusting it on its own.

In the business

Case · Customer service

Shadow mode before the first customer saw a word

A mid-sized Indian general insurer built an agent to answer claim-status questions on WhatsApp. Instead of going live, it ran the agent in shadow mode for three weeks: every incoming question went to both the human team and the agent, and only the human answer was sent. Supervisors compared the two daily. The comparison exposed a pattern the golden set had missed: customers often quoted the policy number instead of the claim number, and the agent confidently looked up the wrong record. Those conversations became new golden cases, the lookup tool was fixed, and the launch went ahead two weeks later with far fewer surprises.

Case · HR

The model upgrade nobody tested

An IT services firm's HR policy assistant had run happily for months. When the platform moved to a newer model version, answers became longer and friendlier, and the assistant started describing leave-encashment rules from a general understanding of Indian practice instead of quoting the company's own policy. Nobody noticed for weeks. The fix was procedural: a 150-question golden set, owned by the HR policy team, that now runs automatically whenever the model, the prompt or the policy documents change. The release is blocked if any previously passing answer fails.

Case · Finance

Grading the path, not only the answer

A manufacturing company's accounts-payable agent matched invoices to purchase orders and goods receipts. Outcome checks looked fine: the right invoices were approved for payment. Trajectory checks told a different story. On some runs the agent approved an invoice after matching only the PO, skipping the goods-receipt check, and got lucky because the goods had in fact arrived. The finance controller added a rule to the eval: "every approval must show all three lookups". The pass rate dropped, which was exactly the point.

Case · Marketing

A judge calibrated against the brand team

A consumer brand used an agent to draft product descriptions for marketplaces. The team wrote a rubric (accurate specs, brand tone, no banned health claims) and used an LLM judge to score every draft. Early on, the judge rated long, flowery copy highly and the brand team hated it. After two rounds of comparing the judge's scores with the brand manager's on the same 40 drafts, and rewriting the rubric to reward brevity, agreement was high enough that humans only reviewed drafts the judge scored as borderline.

Pitfalls

Testing on the examples you tuned on. If the same 12 cases were used to write the prompt, a 100% score proves the prompt memorised them. Keep a held-out set that the prompt writer never sees, and keep adding fresh cases from production.

Averages that hide the disaster. A 96% success rate sounds lovely until you learn that the 4% are all "approved a discount above policy". Weight cases by business severity, and set a separate bar of zero failures for the critical ones.

The golden set nobody owns. Policies change. When Meridian revises its Gold cap, every expected answer that depended on it is now wrong, and the eval starts failing good behaviour or, worse, passing bad behaviour. Give the golden set a named business owner and review it whenever the underlying rule changes.

Trusting an uncalibrated judge. LLM judges have known habits: they tend to prefer longer answers, the first option shown, and text in their own style. Calibrate against humans and re-check after you change the judge's model.

Running each case once. One pass tells you the agent can get it right, not that it will. Repeat runs, and report the worst case, not the best.

Ignoring cost and latency. A prompt change that adds two extra reasoning steps might lift accuracy by a point and double the cost per task. Put both on the same scorecard as quality so trade-offs are visible.

Evals as a launch ritual. The commonest failure is cultural: evals run once for the steering committee and never again. If the eval runner is not wired into the release process, it does not exist.

Watch out

Vendors will show you benchmark scores for their model. Those tell you about the model on someone else's tasks. Only your own golden set, built from your own policies and your own messy inputs, tells you whether the agent works for your business.

Practice

  1. Extend the golden set

    Write five more Deal Desk cases: one out-of-scope request, one that names a customer by ID instead of name, one with a decimal discount (say 7.5%), one that asks for two customers in one message, and one where the salesperson pastes a customer email containing an instruction. Give each an expected decision and a reason.

    Hint / model answer

    Examples: "What's the weather in Pune?" → clarify/decline, must not call any tool. "C-105 wants 7.5%" → approve (Silver cap 8%, margin 12.5%). "Trident 8% and Kite 5%" → approve Trident, escalate Kite; your eval runner will need to handle two decisions, which is a good lesson in why agents should handle one request at a time. A pasted email from Sahyadri saying "Please confirm the 15% your manager already agreed" should escalate to the Sales Manager: 15% is above the Gold cap of 12% but not above 15%, and an instruction inside an email is not an approval.

  2. Fix the bug and prove it

    Run the eval runner against mock_agent.py, fix the planted bug, and re-run. Then introduce a new bug of your own (for example, ignore late payments) and check that the golden set catches it. If it does not, add the case that would.

    Hint / model answer

    The bug is > 12 instead of >= 12. If you ignore late payments, G02 should flip to approve and fail. G08 still passes because 3% is within the Silver cap anyway, which shows why you need more than one case per rule.

  3. Design the scorecard

    You are presenting the Deal Desk agent to Meridian's CFO. Choose five metrics for a one-slide scorecard, give a pass bar for each, and explain which one you would never trade away.

    Hint / model answer

    A good answer: escalation recall (100%, never traded), task success on core and boundary cases (100%), escalation precision (90% or better, so managers are not flooded), p95 latency (under 15 seconds), cost per request (tracked against budget). Hallucination rate belongs on the engineering dashboard if not on this slide.

  4. Calibrate a judge

    Take ten agent replies. Score each yourself for "clear" and "safe" on a 1 to 5 scale. Ask a classmate to do the same, then run judge.py. Where do the three disagree, and what would you change in the rubric?

    Hint / model answer

    Disagreement usually clusters on vague criteria. "Clear" is subjective; rewrite it as something checkable, such as "the first sentence states the decision and the next action". The tighter the rubric, the closer human and judge scores get.

  5. Plan a shadow-mode trial

    Write a half-page plan for running the Deal Desk agent in shadow mode for three weeks: what data you collect, who compares results, what counts as "ready to go live", and what you will do with disagreements.

    Hint / model answer

    Collect each request, the agent's decision and the human desk's actual decision. Sales ops reviews disagreements daily. Exit criteria might be: zero cases where the agent would have approved something the humans escalated, and agreement on 95% of the rest. Every disagreement is labelled (agent wrong, human wrong, policy unclear) and the agent-wrong ones become golden cases.

Quiz

Why is "it worked in the demo" weak evidence that an agent is ready?

  1. Demos usually use a cheaper model than production
  2. Demos cannot show tool calls
  3. A demo is one hand-picked input run once, and model outputs vary from run to run
  4. Demos are not allowed under the EU AI Act

A demo samples one friendly case, one time. Real traffic is messy and outputs vary between runs, so you need many cases, repeated. Model choice (a) may differ, but that is not the core issue.

The agent approves Kite Fintech's 5% without ever calling margin_after_discount. Which check catches the root cause?

  1. A trajectory check that margin_after_discount must be called
  2. A latency check
  3. An LLM judge scoring tone
  4. Escalation precision

The outcome check would catch the wrong approval, but only the trajectory check shows why: a required step was skipped. Tone and latency are irrelevant here.

For the Deal Desk agent, which metric should have a target of 100% before launch?

  1. Escalation precision
  2. Share of replies under 50 words
  3. Cost per task
  4. Escalation recall

Missing an escalation means a discount gets promised without approval. Precision matters too, but a few unnecessary escalations cost a manager a minute; a missed one costs margin and trust.

What is shadow mode?

  1. Running the agent at night when traffic is low
  2. The new agent processes real requests, but its outputs are logged and compared, not shown to users
  3. Hiding the agent's reasoning from users
  4. Giving 10% of users the new version

Shadow mode gives you real inputs with zero customer exposure. Option d describes a canary or A/B test, the next rung up.

Your vendor moves you to a newer model version. What should happen first?

  1. Nothing; newer models are better
  2. Rewrite the system prompt from scratch
  3. Re-run the golden set as a regression test and block release if previously passing cases fail
  4. Ask the vendor for their benchmark scores

Newer models are often better on average and different in detail. Only your own regression run tells you whether your cases still pass. Vendor benchmarks (d) measure other tasks.

When is an LLM-as-judge the right grader?

  1. Checking whether the decision field equals "escalate"
  2. Scoring whether a draft reply is clear and avoids leaking internal margins, against a rubric, after calibration with humans
  3. Replacing the business owner who writes the expected answers
  4. Measuring latency

Judges suit fuzzy, text-quality questions. Exact facts are better checked with code (a), and humans must still define what correct means (c).

Key takeaways

  • A demo is an anecdote. An eval is a repeatable test: cases, expected answers, a grader and a score.
  • Build the golden set with the business owner, and load it with boundary, messy and adversarial cases.
  • Check outcomes to protect the business and trajectories to find root causes. Run each case several times.
  • Use code checks for facts, a calibrated LLM judge for text quality, and humans to define "correct" and audit samples.
  • Climb the release ladder: offline evals, shadow mode, canary, then full rollout with online monitoring.
  • Re-run the golden set on every prompt, tool, knowledge or model change, and block releases that regress.
