When one agent is not enough

After this page you will be able to decide when a team of agents beats a single agent, design that team the way you would design an org chart, anticipate its costs and failure modes, and build a three-agent market entry research crew.

50 min readTracked in your progress

The big idea

A single agent with good tools goes a long way. Then you give it fifteen tools, a 40-page brief, three different jobs and access to four systems, and it starts to wobble. It picks the wrong tool. It forgets the brief halfway through. It writes the analysis in the tone of a search query.

Human organisations hit the same wall and solved it the same way: specialise, then coordinate. A multi-agent system splits the work across several agents, each with a narrow role, its own instructions, its own tools and often its own model, plus a way to hand work between them. A researcher who only searches and takes notes. An analyst who only turns notes into numbers. A writer who only writes. Someone, human or agent, who coordinates.

Here is the catch. Every extra agent is another model reading, thinking and writing, so costs multiply. Every handoff is a place where context gets lost. Anthropic's engineering team, describing its own multi-agent research system in June 2025, reported that agents typically use about 4 times more tokens than chat interactions, and multi-agent systems about 15 times more. The same write-up reported that the multi-agent setup beat a single agent by a wide margin on its internal research evaluation. Both facts matter. Multi-agent can be much better, and it is always much more expensive.

So the question is never "can we use multiple agents?" It is "does this job have parts that genuinely need separate expertise, separate context or separate permissions, and is the value high enough to pay for the extra runs?"

Manager's lens

You already know how to do this. Designing a multi-agent system is org design: deciding roles, writing job descriptions, setting spans of control, defining handoffs and assigning accountability. The same mistakes show up too. Overlapping roles cause duplicate work. Vague handoffs cause dropped balls. A team with no single accountable owner produces a report nobody stands behind. If you would not hire three people for this job, do not deploy three agents.

How it works

When one agent isn't enough

There are four honest reasons to split work across agents. If none applies, stay with one.

  • Context overload. The job needs more reading than one context window handles well. A research task across 30 sources is the classic case: separate agents each read a slice and report back a summary.
  • Tool overload. Past a dozen or so tools, agents choose worse. Giving each specialist three or four tools keeps choices sharp.
  • Different permissions. The agent that reads the web should not be the agent that can write to the ERP. Separate agents give separate access, which is a security control, not just tidiness.
  • Parallel work. Independent subtasks can run at the same time, which cuts elapsed time even as total cost rises.

Anthropic's same write-up is candid about where the approach fits badly: tasks where all agents need to share the same context, and most coding tasks, which have fewer truly parallel parts than research does. A useful rule of thumb follows. Multi-agent works best on "breadth" problems (survey many sources, compare many options) and worst on "depth" problems (one tightly connected piece of reasoning).

Topologies: how agents are arranged

A topology is the shape of who talks to whom. Five shapes cover almost everything you will see.

Supervisor (manager). One coordinating agent receives the task, delegates pieces to specialists, checks what comes back and assembles the answer. Specialists do not talk to each other. Easy to reason about, easy to log, and the most common shape in production.

Hierarchical. Here, supervisors manage other supervisors. Useful when the job is big enough that one coordinator would have too many specialists to track. Costs and latency climb with every layer, so most business systems stop at two.

Sequential pipeline. Agent A's output is agent B's input, and so on. No coordinator, because the order is fixed. It is prompt chaining (Module 07) where each step is a full agent with tools. Our market entry crew below is a pipeline.

Network or swarm. Any agent can hand off to any other, based on the conversation. Flexible, and good for customer service where a chat moves from sales to billing to support. Also the easiest shape to get lost in: without rules, agents pass the parcel in circles.

Debate. Two or more agents argue positions and a judge (an agent or a person) decides. Du and colleagues (2023) found that having several model instances debate improved reasoning and factual accuracy on their benchmarks. In business, debate suits decisions with real trade-offs: build versus buy, which supplier, whether a clause is risky.

Role design is org design

This is where managers have an advantage over most engineers. A good agent role is a good job description: a clear title, an objective, the background that shapes judgement, the tools (access rights) it has, the output it owns, and who it hands to. CrewAI even uses the words: every agent has a role, a goal and a backstory.

Write roles so they do not overlap. If both the researcher and the analyst are told to "assess the market", both will, and you will pay twice for two inconsistent answers. Make each role own a distinct artefact: the researcher owns sourced notes, the analyst owns the numbers, the writer owns the memo.

Then assign accountability. A RACI chart works surprisingly well for agent teams, with one firm rule: the A (accountable) is always a named human. Agents can be responsible for doing work. They cannot be accountable for it.

Communication and handoffs

Agents coordinate in one of two ways. In message passing, one agent sends another a message or a handoff: "here are my notes, your turn". In a shared workspace (sometimes called a blackboard), agents read and write a common state object, such as a research file everyone can see.

Either way, the handoff is where quality leaks. Three choices matter:

  • What travels. Pass the full history and the next agent has to wade through all of it. Pass a one-line summary and it loses the evidence. Pass a structured artefact: notes with sources, a table with assumptions, a list of open questions.
  • Who controls. In a handoff (the OpenAI Agents SDK's term), control moves to the next agent, which takes over the conversation. In "agent as tool", the caller stays in charge and just asks a specialist for a result. Agent-as-tool is easier to reason about; handoffs suit conversations that genuinely change department.
  • What "done" means. Each agent needs an expected output it can be checked against. CrewAI calls it expected_output; it is the most underrated field in the framework.

Shared state

Multi-agent systems need one place where the facts of the job live: the inputs, each agent's artefacts, decisions made, and what is still open. Without it, two agents work from different versions of the truth. LangGraph makes this explicit as a typed state object that every node reads and updates, with checkpoints (Module 06). CrewAI passes task outputs forward through context. Whatever the framework, the rule is the same as in a project team: one source of truth, written down, versioned.

Cost multiplication

Do the arithmetic before you build. Every agent reads its instructions, the inputs it was handed and its own tool results, then writes. A supervisor reads the reports of every specialist. A debate reads each side's arguments several times. A three-agent pipeline is rarely three times the cost of one agent; with re-reading and retries it is often more. Anthropic's figures (about 4 times chat for an agent, about 15 times for multi-agent) are a sensible order of magnitude to plan with, and the same write-up reports that token usage by itself explained 80% of the variance in performance on the BrowseComp benchmark. In plain terms: much of the quality gain comes from spending more.

That is fine for a ₹50-lakh market entry decision. It is not fine for answering "what's our leave policy?" ten thousand times a month. Price the run, multiply by volume, and compare it with the value of a better answer.

Failure modes

A 2025 study by Cemri and colleagues analysed failed multi-agent runs across several popular frameworks and grouped the causes into three families: problems with how the system and roles were specified, misalignment between agents (ignoring each other's input, withholding information, drifting off task), and weak verification and termination (stopping too early, or never checking the result). In company terms, these show up as:

  • Loops. Two agents keep handing work back and forth ("please clarify", "please confirm"). Cap turns per agent and per run.
  • Blame diffusion. The memo is wrong and every agent's log shows it did its part. Without a named accountable owner and per-step checks, nobody can say where it broke.
  • Compounding errors. If each of three steps is right 95% of the time and errors pass straight through, the whole chain is right about 86% of the time (0.95 × 0.95 × 0.95). Five steps at 90% each gives about 59%. Add checks between steps, not just at the end.
  • Groupthink. Agents built on the same model, with similar prompts, agree with each other's mistakes. Use different models or deliberately adversarial roles for review.
  • Context loss at handoff. The analyst never learns that the researcher marked a key number "unconfirmed". Make uncertainty a required field in every artefact.

Hands-on: a research crew

Meridian's leadership is considering expanding into Hyderabad's private hospital segment. We will build a three-agent crew that researches the market, sizes the opportunity and writes a board memo: a researcher, an analyst and a writer, in a sequential pipeline. The output is a draft for humans to challenge, not a decision.

Two no-code routes. The first needs nothing but chat assistants and teaches the most about handoffs. The second automates it.

Route 1: three assistants and you as the handoff

  1. Create three assistants

    In Claude Projects, Custom GPTs or Gemini Gems, create "Researcher", "Analyst" and "Writer". Paste each one's role, goal and backstory (copy them from the Python tab) into its instructions. Turn on web search for the Researcher only.

  2. Run the researcher

    Ask: "Research the market for office and facility supplies among private hospitals in Hyderabad. Bullet-point notes; every fact has a source URL; mark anything unconfirmed." Read the notes and check two sources yourself.

  3. Hand off to the analyst

    Paste the notes into the Analyst with: "Estimate the annual revenue opportunity for Meridian with low, base and high cases. List assumptions and the three biggest risks." Notice how much depends on what you chose to paste.

  4. Hand off to the writer

    Paste both outputs into the Writer: "Write a board memo under 900 words: recommendation, opportunity size, risks, next 90 days, open questions."

  5. Review as the accountable owner

    Check that every number in the memo traces back to a source or a stated assumption. This is the job the agents cannot do for you.

Route 2: automate it in n8n

Create a workflow with a form trigger (fields: segment, city), then three AI Agent nodes in a row. Give the first a web search tool node and the researcher instructions; pass its output into the second agent's prompt; pass both into the third. End with a Google Docs or email node that sends the memo to the strategy manager for review. Set a maximum-iterations limit on the research agent. See n8n, Zapier, Make and Power Automate.

CrewAI supports Python 3.10 to 3.13 at the time of writing. You need an Anthropic key for the model and a Serper key for web search (Serper is a Google-search API with a free tier; any search tool works).

pip install "crewai[anthropic]==1.15.27" "crewai-tools==1.15.27"
export ANTHROPIC_API_KEY="your-key-here"
export SERPER_API_KEY="your-serper-key"
# market_entry_crew.py  -  researcher -> analyst -> writer
import os
from crewai import Agent, Task, Crew, Process
from crewai_tools import SerperDevTool

MODEL = os.getenv("CREW_MODEL", "anthropic/claude-sonnet-5-5")   # any provider/model CrewAI supports
search = SerperDevTool()                                            # needs SERPER_API_KEY

researcher = Agent(
    role="Market Researcher",
    goal="Find current, sourced facts about {segment} buyers in {city}",
    backstory="You worked in Meridian's strategy team. You never state a number without a source URL.",
    tools=[search],
    llm=MODEL,
    max_iter=8,                 # stop runaway searching
    verbose=True,
)

analyst = Agent(
    role="Commercial Analyst",
    goal="Turn research notes into a go / no-go view for Meridian entering {city}",
    backstory="Ex-consultant. You size markets with explicit assumptions and flag weak evidence.",
    llm=MODEL,
    allow_delegation=False,
)

writer = Agent(
    role="Board Memo Writer",
    goal="Write a two-page memo the Meridian leadership team can decide on",
    backstory="You write plainly for busy directors. Recommendation first, evidence after.",
    llm=MODEL,
    allow_delegation=False,
)

research = Task(
    description=("Research the market for office and facility supplies among {segment} in {city}. "
                 "Cover: number and size of likely buyers, current suppliers, buying process, price sensitivity."),
    expected_output="Bullet-point notes. Every fact has a source URL. Mark anything you could not confirm.",
    agent=researcher,
)

analysis = Task(
    description=("Using the research notes, estimate the annual revenue opportunity for Meridian in {city} "
                 "with low / base / high cases. List assumptions and the three biggest risks."),
    expected_output="A small table of cases, an assumptions list and a risk list.",
    agent=analyst,
    context=[research],
)

memo = Task(
    description="Write the board memo: recommendation, opportunity size, risks, next 90 days, open questions.",
    expected_output="A markdown memo under 900 words.",
    agent=writer,
    context=[research, analysis],
    output_file="market_entry_memo.md",
)

crew = Crew(
    agents=[researcher, analyst, writer],
    tasks=[research, analysis, memo],
    process=Process.sequential,
    verbose=True,
)

if __name__ == "__main__":
    result = crew.kickoff(inputs={"segment": "private hospitals", "city": "Hyderabad"})
    print(result.raw)
    print(result.token_usage)

What this does, in management terms:

  • Agents are job descriptions. role, goal and backstory shape how each agent behaves. The {segment} and {city} placeholders are filled in at kickoff, so the same crew can study a different city tomorrow.
  • Tools are access rights. Only the researcher gets search. The analyst and writer work only from what they are handed. allow_delegation=False stops them passing work sideways.
  • Tasks are deliverables. Each has a description (the brief) and an expected_output (the definition of done). context=[research] is the handoff: the analyst receives the researcher's output. The writer gets both.
  • The crew is the operating model. Process.sequential runs tasks in order. Switching to Process.hierarchical with a manager_llm makes a manager agent delegate instead, the supervisor topology.
  • Guardrails on cost. max_iter=8 caps the researcher's reasoning loop. result.token_usage prints what the run consumed, so you can price it before scaling.
  • The output is saved to market_entry_memo.md for a human to review.

We checked that this crew builds against CrewAI 1.15.27. To use another model provider, change CREW_MODEL and install the matching extra; the CrewAI method page has details.

In the business

Case · Marketing

A campaign crew with a compliance reviewer

A D2C brand runs a small crew for festive campaigns: a planner agent drafts the brief from last year's results, a copy agent writes variants per channel, and a reviewer agent on a different model checks claims, brand voice and platform ad policies. The reviewer has no ability to edit, only to approve or return with reasons. The team found the separation useful mostly for accountability: when a claim slips through, the log shows exactly which check missed it.

Case · Finance

Month-end close with a supervisor

A shared-services centre trialled a supervisor with three specialists: bank reconciliation, intercompany matching and accruals review. Each specialist has read-only access to its own systems and produces an exceptions list. The supervisor compiles the close checklist and flags blockers to the controller. No agent can post journals. Elapsed time for the first pass dropped because the specialists run in parallel; the controller still signs every entry.

Case · Supply chain

Supplier selection by debate

A manufacturer's category team uses a debate setup for single-source decisions above a set value. One agent argues for the incumbent, one for the challenger, both working from the same tender pack; a judge agent summarises the strongest points on each side for the sourcing committee. The committee reported that the format surfaced risks (single-plant dependence, payment-term creep) that a single summary had glossed over. The judge never picks the winner; the committee does.

Case · Customer service

Handoffs that respect the customer

A broadband provider's chat assistant hands customers between sales, billing and technical agents. Early versions passed the full transcript at every handoff, which was slow and occasionally exposed payment details to the technical agent. The redesign passes a structured case summary plus only the fields each agent needs, caps handoffs at three per chat, and offers a human after the second.

Pitfalls

  • Multi-agent because it demos well. A crew of agents chatting looks impressive in a meeting. Ask for the single-agent baseline and the cost per run before approving.
  • Overlapping roles. Two agents both "analyse", producing two answers. Give each role one owned artefact.
  • No turn limits. Agents politely bounce work between them until the budget runs out. Cap turns per agent, per handoff and per run.
  • Uncertainty lost in transit. "Unconfirmed" in the researcher's notes becomes a confident number in the memo. Make confidence and sources required fields in every handoff.
  • Same model everywhere. Reviewers built on the same model as the makers share their blind spots. Mix models for high-stakes checks.
  • Permissions sprawl. Every agent gets every tool "for flexibility". Give tools to the one role that needs them.
  • No accountable human. If the RACI has no human A, you do not have a process; you have a liability.
  • Testing only the end result. Evaluate each agent's artefact as well as the final output, so you can tell which step broke.

Practice

  1. One agent or three?

    For each, decide single agent or multi-agent and justify in two lines: (a) answer employee questions on the leave policy; (b) produce a quarterly competitor review across 12 competitors; (c) handle a customer chat that may touch sales, billing and tech support; (d) approve discounts for the Deal Desk.

    Hint / model answer

    (a) Single agent with retrieval. (b) Multi-agent (orchestrator or parallel researchers): breadth problem, high value. (c) Multi-agent with handoffs, or one agent with routing; handoffs help if each department needs different tools and permissions. (d) Single agent with tools and human approval; depth problem, low tolerance for drift.

  2. Write the job descriptions

    Design a three-agent crew for Meridian's annual customer review of Sahyadri Hospitals (account history, satisfaction signals, renewal proposal). Write role, goal, backstory, tools and expected output for each.

    Hint / model answer

    Account historian (tools: CRM, order history; output: dated timeline), Voice-of-customer analyst (tools: support tickets, survey results; output: themes with counts and quotes), Proposal writer (no tools; output: two-page renewal proposal citing both). Check that no two roles own the same artefact.

  3. Build the RACI

    Extend the RACI table on this page with two new activities: "Check sources" and "Approve sharing with the board". Who is R and A for each?

    Hint / model answer

    Check sources: R could be a reviewer agent or the strategy manager, A is the strategy manager. Approve sharing: R and A are humans (strategy manager R, Head of Sales A). Agents can be R for doing work, never A.

  4. Price the crew

    Run the CrewAI crew (or the no-code version) once, note the token usage, and estimate monthly cost if the strategy team runs it for 20 cities a quarter. Compare with the cost of a single analyst-day.

    Hint / model answer

    Use result.token_usage and your provider's current price list. Multiply per-run cost by runs per month, add a margin for retries. The point is the comparison: for a decision worth lakhs, the crew is cheap; for a high-volume FAQ it would not be.

  5. Switch the topology

    Change the crew to Process.hierarchical with a manager_llm. Run both versions on the same inputs. What changed in cost, order of work and quality?

    Hint / model answer

    Expect higher token usage (the manager reads and delegates), less predictable ordering, and sometimes better coverage if the manager sends the researcher back for gaps. If quality did not clearly improve, keep the sequential version.

  1. 95%
  2. 99%
  3. 75%
  4. About 86%

In a RACI for an agent team, who should be "Accountable"?

  1. The supervisor agent
  2. A named human
  3. Whichever agent produced the final output
  4. The framework vendor

Agents can do the work (Responsible) but cannot carry accountability. Without a human A, nobody stands behind the result.

In the CrewAI code, what does context=[research] on the analysis task do?

  1. Gives the analyst web search
  2. Makes the analyst the manager
  3. Passes the research task's output to the analyst: the handoff
  4. Saves the output to a file

context lists the tasks whose outputs this task receives. Tools come from the agent's tools; files from output_file.

A customer chat moves from sales to billing to tech support. Which topology fits most naturally?

  1. Debate
  2. Network with handoffs (with limits)
  3. Hierarchical with three layers
  4. A fixed sequential pipeline

The conversation's path is not known in advance, so agents need to hand off to whichever department is relevant, with caps on handoffs and a route to a human.

Key takeaways

  • Split work across agents only for separate context, tools, permissions or parallel work; otherwise one agent is better.
  • Multi-agent can be markedly better on breadth problems, and is always more expensive. Price runs before scaling.
  • Five topologies: supervisor, hierarchical, sequential pipeline, network/swarm and debate.
  • Design agent teams like org charts: non-overlapping roles, one owned artefact each, and a human who is accountable.
  • Handoffs leak quality; pass structured artefacts with sources and confidence, and define "done" for every task.
  • Expect loops, blame diffusion, compounding errors and groupthink; counter them with turn limits, step checks and mixed models.
