Build the agent loop yourself

Write the Meridian Deal Desk agent with nothing but the Anthropic or OpenAI API and plain Python, so you can see exactly what every agent framework does on your behalf: the loop, the stop reasons, parallel tool calls, the step limit, the approval gate and the audit log.

Every agent framework on this site, from LangGraph to CrewAI to the OpenAI Agents SDK, sits on top of one feature that the model vendors sell directly: tool use, also called function calling. You describe your functions to the model. The model replies either with an answer or with a request to call one of them. Your code runs the function and sends the result back. Repeat until the model says it is done.

That is the whole trick. A loop, a list of tool descriptions, and some discipline about what happens when things go wrong.

This page builds the Meridian Deal Desk agent with no framework at all. The main version uses Anthropic's Messages API. A tab shows the same loop on OpenAI's Responses API. Both use the same plain Python tools, the same approval gate and the same audit log, so you can see that the vendor is the least interesting part of the design.

Why bother, when frameworks exist? Because once you have seen the loop, you ask better questions in every vendor demo. What happens when a tool fails? Who sees the request before a discount goes out? What stops it looping forever? Here you write those answers yourself, in about 150 lines.

What changed recently (as of 2026)

Three things matter for this method. First, both big vendors now let the model ask for several tools in one turn (parallel tool use), and your loop has to handle that properly. Second, both support a strict mode where the model's tool arguments are checked against your JSON schema, which cuts down on malformed calls. Third, vendors now also run some tools on their own servers (web search, code execution). Those "server tools" add new stop reasons, such as Anthropic's pause_turn, that a home-made loop must not mistake for a final answer. Check the current details in the Claude tool use docs and OpenAI's function calling guide.

Manager's lens

Think of this page as the "show me the engine" visit before you buy the car. You may never ship a hand-written loop to production. But once you have read one, vendor claims about "autonomous agents" become concrete: it is a loop with a step limit, a list of permitted actions, and a log. If a vendor cannot tell you their step limit or show you their log, that is your answer.

When to pick it

Pick the raw API when the job is small, the rules are clear, and you want every line to be readable by an auditor. The Deal Desk is a good example: five tools, one approval rule, one user type. A framework would add dependencies and abstractions without adding much.

It also suits learning, security teams wary of large dependency trees, and agents that must live inside an existing Python service.

Skip it when the work runs across hours or days and must survive restarts, when several agents need to coordinate, or when you need a visual debugger and hosted deployment. You can build all of that yourself. Frankly, you will end up rebuilding a worse version of LangGraph, and someone in your team will have to maintain it.

Strengths

  • Nothing hidden: you can read every step the agent takes
  • Tiny dependency footprint (one vendor SDK)
  • Full control over approvals, logging and error handling
  • Easy to port: tools are plain Python functions
  • Cheapest way to learn what frameworks do

Watch-outs

  • You own pause-and-resume, retries and persistence
  • No built-in tracing UI; you build dashboards from logs
  • Message formats differ between vendors
  • Easy to forget edge cases (refusals, truncation, server tools)
  • Multi-agent coordination gets messy fast

How it works

Here is the shape of every tool-using agent, drawn for the Deal Desk.

Read the figure from left to right. The salesperson's message goes into your loop. The loop sends the conversation so far, plus the list of tools, to the model. The model replies with a stop reason that tells the loop what to do next.

Stop reasons are the steering wheel

Most bugs in home-made agents come from treating every reply as a final answer. Anthropic's API returns one of these in stop_reason:

stop_reasonWhat it meansWhat your loop should do
tool_useThe model wants one or more tools runRun every requested tool, return all results in one message, call the model again
end_turnThe model has finishedReturn the text to the user and log it
max_tokensThe reply hit your token limitTreat as incomplete; stop or retry with a higher limit
refusalThe model declinedStop and route to a person; do not retry blindly
pause_turnA server-side tool loop needs to continueSend the assistant content back to let it finish (only if you use server tools)
stop_sequence, model_context_window_exceededYour stop string appeared, or the context filled upTreat as finished-but-check, or truncated

OpenAI's Responses API takes a slightly different route. Instead of a stop reason, the output list contains items, and if any of them are function_call items you run them and send back function_call_output items. No function calls means a final answer. Same loop, different labels.

Parallel tool calls

When a salesperson asks about Bluewave Logistics, the model can see straight away that it needs two things: the customer record and the policy. Modern models will ask for both in a single turn. Your loop must run both, then send both results back in one message, each tagged with the id of the call it answers. Anthropic's docs are explicit: one tool_result per tool_use, all together in the next user message, results before any text. Send them in separate messages and the conversation breaks.

The step limit

A model can get stuck: calling the same lookup again, or bouncing between two tools. The fix is boring and essential. Count the turns and stop at a limit (eight is plenty for the Deal Desk). When the limit hits, hand the request to a person with a clear message. Frameworks have the same guard under names like max_turns or max_iter.

The approval gate

The rule "never promise a discount above policy without approval" cannot live only in the prompt. Prompts are requests, not controls. So the loop itself checks the tool name: any call to request_approval is paused until a named person decides. The model gets the person's decision back as the tool result and has to draft a reply that matches it.

Step 2: the tools (meridian_tools.py)

"""meridian_tools.py - the Deal Desk agent's tools, in plain Python.

In a real company these functions would call the CRM and the ERP.
Here they read a small in-memory table so the whole agent runs on a laptop.
"""
import difflib
from datetime import datetime

CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian Supplies discount policy (FY 2026-27)
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""

TIER_CAP = {"Bronze": 5, "Silver": 8, "Gold": 12}
MARGIN_FLOOR = 12
APPROVALS = []  # stands in for your ticketing system


def get_customer(customer_id: str) -> dict:
    """Return the customer record for an id such as C-101."""
    record = CUSTOMERS.get(customer_id.strip().upper())
    return record or {"error": f"No customer with id {customer_id}"}


def find_customer(name: str) -> dict:
    """Fuzzy lookup by customer name. Returns the best-matching record."""
    by_name = {c["name"].lower(): c for c in CUSTOMERS.values()}
    query = name.strip().lower()
    for full_name, record in by_name.items():
        if query and (query in full_name or full_name in query):
            return record
    close = difflib.get_close_matches(query, list(by_name), n=1, cutoff=0.5)
    return by_name[close[0]] if close else {"error": f"No customer matching '{name}'"}


def get_discount_policy() -> str:
    """Return the current discount policy text."""
    return POLICY


def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % left after the discount (simplified: margin minus discount)."""
    return round(current_margin_pct - discount_pct, 2)


def request_approval(customer_id: str, discount_pct: float, approver: str, reason: str) -> str:
    """Log an approval request for a discount above policy. A named person must decide."""
    ticket = f"APR-{len(APPROVALS) + 1:04d}"
    APPROVALS.append({"ticket": ticket, "customer_id": customer_id, "discount_pct": discount_pct,
                      "approver": approver, "reason": reason,
                      "raised_at": datetime.now().isoformat(timespec="seconds")})
    return f"{ticket} logged with {approver} for {discount_pct}% on {customer_id}."


def evaluate_request(customer: dict, discount_pct: float) -> dict:
    """The policy written as code: the same rules, checked the same way every time."""
    cap = 3 if customer["late_payments_fy"] >= 2 else TIER_CAP[customer["tier"]]
    margin_after = margin_after_discount(customer["gross_margin_pct"], discount_pct)
    problems = []
    if discount_pct > cap:
        problems.append(f"{discount_pct}% is above the {cap}% cap")
    if margin_after < MARGIN_FLOOR:
        problems.append(f"margin after discount would be {margin_after}%, below the {MARGIN_FLOOR}% floor")
    approver = None
    if problems:
        approver = "Regional Head" if discount_pct > 15 else "Sales Manager"
    return {"within_policy": not problems, "cap_pct": cap, "margin_after_pct": margin_after,
            "problems": problems, "approver": approver}

What this does, in plain English:

  • CUSTOMERS and POLICY are the exact customer table and discount policy from the course case. In real life these come from your CRM and your policy document.
  • margin_after_discount does the arithmetic. Models are decent at sums but not reliable enough for money, so the model is told to call this instead of calculating.
  • request_approval only logs a ticket. It cannot grant anything. The decision comes from a person.
  • evaluate_request is the whole policy as code. The raw loop does not use it (the model reasons over the policy text), but the LangGraph and CrewAI pages do. Keep it: it is also your test oracle.

Step 3: descriptions, gate and log (deal_desk_common.py)

"""deal_desk_common.py - prompt, tool schemas, approval gate and audit log, shared by both loops."""
import json
import time

import meridian_tools as mt

SYSTEM = """You are the Deal Desk assistant at Meridian Supplies Pvt Ltd, Pune.
A salesperson asks whether a customer can have a discount.
1. Look the customer up. 2. Read the discount policy. 3. Compute the margin with the tool.
If the request is within every rule, approve it and draft a short reply to the customer.
If it breaks any rule, do NOT promise it. Call request_approval with the right approver
and a one-line reason, then draft the reply that matches the approver's decision.
Never invent customer data. Quote the numbers you used."""

TOOLS = [
    {"name": "find_customer",
     "description": "Find a customer by name (spelling can be loose). Returns id, tier, "
                    "annual revenue in lakh, late payments this FY and gross margin %.",
     "input_schema": {"type": "object",
                      "properties": {"name": {"type": "string"}},
                      "required": ["name"], "additionalProperties": False}},
    {"name": "get_customer",
     "description": "Get a customer record by id, for example C-101.",
     "input_schema": {"type": "object",
                      "properties": {"customer_id": {"type": "string"}},
                      "required": ["customer_id"], "additionalProperties": False}},
    {"name": "get_discount_policy",
     "description": "Return Meridian's current discount policy. Read it before deciding.",
     "input_schema": {"type": "object", "properties": {}, "required": [],
                      "additionalProperties": False}},
    {"name": "margin_after_discount",
     "description": "Gross margin % left after a discount. Use this; do not do the sum yourself.",
     "input_schema": {"type": "object",
                      "properties": {"current_margin_pct": {"type": "number"},
                                     "discount_pct": {"type": "number"}},
                      "required": ["current_margin_pct", "discount_pct"],
                      "additionalProperties": False}},
    {"name": "request_approval",
     "description": "Escalate a discount that breaks policy. A person decides; "
                    "the result tells you their decision.",
     "input_schema": {"type": "object",
                      "properties": {"customer_id": {"type": "string"},
                                     "discount_pct": {"type": "number"},
                                     "approver": {"type": "string",
                                                  "enum": ["Sales Manager", "Regional Head"]},
                                     "reason": {"type": "string"}},
                      "required": ["customer_id", "discount_pct", "approver", "reason"],
                      "additionalProperties": False}},
]

FUNCTIONS = {
    "find_customer": mt.find_customer,
    "get_customer": mt.get_customer,
    "get_discount_policy": mt.get_discount_policy,
    "margin_after_discount": mt.margin_after_discount,
    "request_approval": mt.request_approval,
}
NEEDS_HUMAN = {"request_approval"}


def log(event, **data):
    """Append one line per event to an audit file you can open in Excel or ship to a SIEM."""
    with open("deal_desk_audit.jsonl", "a", encoding="utf-8") as f:
        f.write(json.dumps({"ts": time.strftime("%Y-%m-%dT%H:%M:%S"), "event": event, **data}) + "\n")


def human_gate(args):
    """Pause and let the approver decide. In production: a Teams/Slack card or a ticket."""
    print(f"\n[APPROVAL NEEDED] {args['approver']}: {args['discount_pct']}% for "
          f"{args['customer_id']}. Reason: {args['reason']}")
    answer = input("Decision - y to approve, n to reject, or a number to counter-offer: ").strip().lower()
    if answer == "y":
        return f"APPROVED by {args['approver']} at {args['discount_pct']}%"
    try:
        return f"COUNTER-OFFER from {args['approver']}: {float(answer):g}% maximum"
    except ValueError:
        return f"REJECTED by {args['approver']}. Do not offer any discount above policy."


def run_tool(name, args):
    """Run one tool safely. Returns (text for the model, is_error)."""
    if name not in FUNCTIONS:
        return f"Unknown tool: {name}", True
    try:
        result = FUNCTIONS[name](**args)
        if name in NEEDS_HUMAN:
            result = f"{result} Decision: {human_gate(args)}"
        return (result if isinstance(result, str) else json.dumps(result)), False
    except Exception as exc:                     # a broken tool must not crash the agent
        return f"Tool error: {exc}", True

What this does:

  • SYSTEM is the agent's job description. Note the order of work and the hard rule: do not promise, escalate.
  • TOOLS is the menu the model sees. Each entry has a name, a description in plain English, and a JSON schema for the inputs. The descriptions matter more than people expect; "use this, do not do the sum yourself" changes behaviour. The enum on approver means the model can only pick one of two real roles.
  • FUNCTIONS maps names to real Python functions. If the model asks for a tool that is not on this list, run_tool refuses.
  • human_gate is the approval step. In the demo the approver types y, n or a counter-offer in the terminal. In a company it would be an approval card in Teams or Slack, or a ticket.
  • run_tool turns a broken CRM call into an error message the model can read, not a crash. log writes one JSON line per event: your audit trail.

Step 4: the loop

"""deal_desk_claude.py - the Meridian Deal Desk agent on the raw Anthropic Messages API."""
import os

import anthropic
from deal_desk_common import SYSTEM, TOOLS, run_tool, log

MODEL = os.getenv("MODEL", "claude-sonnet-5-5")   # use a model id your account has
MAX_STEPS = 8                                    # hard stop against runaway loops
client = anthropic.Anthropic()                   # reads ANTHROPIC_API_KEY from the environment


def run_agent(request):
    messages = [{"role": "user", "content": request}]
    log("request", text=request)
    for step in range(1, MAX_STEPS + 1):
        response = client.messages.create(
            model=MODEL, max_tokens=1024, system=SYSTEM, tools=TOOLS, messages=messages)
        log("model_turn", step=step, stop_reason=response.stop_reason,
            input_tokens=response.usage.input_tokens, output_tokens=response.usage.output_tokens)
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "tool_use":
            results = []
            for block in response.content:          # may hold several calls at once
                if block.type == "tool_use":
                    output, is_error = run_tool(block.name, block.input)
                    log("tool_call", step=step, tool=block.name, args=block.input,
                        output=output, is_error=is_error)
                    results.append({"type": "tool_result", "tool_use_id": block.id,
                                    "content": output, "is_error": is_error})
            messages.append({"role": "user", "content": results})   # all results, one message
            continue

        if response.stop_reason == "end_turn":
            answer = "".join(b.text for b in response.content if b.type == "text")
            log("final", text=answer)
            return answer

        log("stopped", reason=response.stop_reason)  # max_tokens, refusal, anything else
        return f"Stopped ({response.stop_reason}). Routing this request to the Deal Desk team."

    log("stopped", reason="max_steps")
    return "Stopped after too many steps. Routing this request to the Deal Desk team."


if __name__ == "__main__":
    print(run_agent(input("Salesperson: ")))

What this does, line by line in spirit:

  • The conversation starts as a single user message: the salesperson's request.
  • Each turn sends the whole conversation, the system prompt and the tool list to messages.create.
  • The model's reply is appended to the history as it came back, including any tool requests. Skipping this breaks the next turn, because every tool result must point at a tool request the model made.
  • On tool_use, the inner loop runs every tool block in the reply (there may be several), and all the results go back together in one user message.
  • On end_turn, the text is the answer.
  • Anything else, and anything that runs past eight steps, stops and hands the request to a person. Failing safe is a design choice, not an afterthought.
"""deal_desk_openai.py - the same loop on the OpenAI Responses API."""
import json
import os

from openai import OpenAI
from deal_desk_common import SYSTEM, TOOLS, run_tool, log

MODEL = os.getenv("OPENAI_MODEL", "gpt-5.5")     # use a model id your account has
MAX_STEPS = 8
client = OpenAI()                                # reads OPENAI_API_KEY from the environment

# Same tools, OpenAI's wrapping: "parameters" instead of "input_schema".
OPENAI_TOOLS = [{"type": "function", "name": t["name"], "description": t["description"],
                 "parameters": t["input_schema"], "strict": True} for t in TOOLS]


def run_agent(request):
    items = [{"role": "user", "content": request}]
    log("request", text=request)
    for step in range(1, MAX_STEPS + 1):
        response = client.responses.create(
            model=MODEL, instructions=SYSTEM, tools=OPENAI_TOOLS, input=items)
        if response.status == "incomplete":           # hit a token limit or was cut short
            log("stopped", reason="incomplete")
            return "Stopped (incomplete reply). Routing this request to the Deal Desk team."
        items += response.output                       # keep the model's own items in history
        calls = [item for item in response.output if item.type == "function_call"]
        if not calls:                                  # no tool calls means a final answer
            log("final", text=response.output_text)
            return response.output_text
        for call in calls:                             # parallel calls arrive together
            args = json.loads(call.arguments)
            output, is_error = run_tool(call.name, args)
            log("tool_call", step=step, tool=call.name, args=args, output=output, is_error=is_error)
            items.append({"type": "function_call_output", "call_id": call.call_id, "output": output})
    log("stopped", reason="max_steps")
    return "Stopped after too many steps. Routing this request to the Deal Desk team."


if __name__ == "__main__":
    print(run_agent(input("Salesperson: ")))

What this does: the same loop with OpenAI's vocabulary. Tools are wrapped as {"type": "function", ...} with parameters instead of input_schema, and "strict": True asks the API to hold arguments to the schema (which is why every schema in the shared file sets additionalProperties: false). The reply's output list is added to the history as-is, which also carries any reasoning items the model produced. Each function_call item gets a matching function_call_output with the same call_id. When a reply has no function calls, output_text is the answer.

Tip

Run python deal_desk_claude.py, type a request, then open deal_desk_audit.jsonl in a text editor. Seeing the token counts and tool calls for one request teaches you more about cost than any pricing page.

Step 5: a run, step by step

Here is what a Bluewave request looks like with the Claude loop. The wording of the model's reasoning and reply will vary from run to run; the tool calls and numbers should not.

Bluewave Logistics wants 6% off their next order. Can we do it?
I need the customer record and the policy. I can ask for both at once.
find_customer(name="Bluewave Logistics") + get_discount_policy() [step 1, two calls in parallel]
{"id":"C-102","tier":"Silver","annual_revenue_lakh":19,"late_payments_fy":2,"gross_margin_pct":18} · policy text
Silver cap is 8%, but 2 late payments cap them at 3%. 6% breaks the cap. Check the margin anyway.
margin_after_discount(current_margin_pct=18, discount_pct=6) [step 2]
12
Margin is exactly at the 12% floor, but the late-payment cap fails. This needs the Sales Manager.
request_approval(customer_id="C-102", discount_pct=6, approver="Sales Manager", reason="2 late payments this FY; cap is 3%") [step 3]
Loop pauses. Sales Manager types 4: counter-offer at 4% maximum. Result returned: "APR-0001 logged ... Decision: COUNTER-OFFER from Sales Manager: 4% maximum"
Not within policy as asked: Bluewave has 2 late payments this FY, which caps them at 3%. The Sales Manager has approved a counter-offer of 4% (margin after discount 14%). Draft reply: "Thank you for your continued business. We can offer 4% on your next order..." [step 4, end_turn]

Run the other two cases yourself. Sahyadri at 10% should end in one or two steps with an approval and a draft: Gold cap 12%, margin 22 − 10 = 12%, exactly at the floor. Kite at 5% is the tricky one. The discount is inside the Bronze cap, so a careless agent approves it. But 16 − 5 = 11%, below the 12% floor, so it must escalate.

Watch out

Kite is your best test case. If your agent approves Kite at 5%, it read the tier cap and stopped thinking. Fix the prompt or, better, move the decision into code (as the LangGraph page does with evaluate_request).

Taking it to production

The demo runs in a terminal. A company version needs the same loop with grown-up plumbing around it. Here is what changes, and the bit that usually goes wrong in each.

Identity and SSO

Put the loop behind your existing login (Microsoft Entra ID, Google Workspace, Okta) as a small web service, for example FastAPI. Pass the salesperson's identity into every log line. The approver's identity must come from SSO too, not from a name typed into a box. What usually goes wrong: the approval card is sent to a shared mailbox, so you cannot prove who approved.

Data access

The model never gets database credentials. Only your tool functions do, through a service account with read-only access to exactly the fields the Deal Desk needs. Customer revenue and payment history are personal or commercially sensitive data, so check your obligations under India's DPDP Act 2023 and your customer contracts before sending them to any external API. Send the minimum: the model does not need the customer's contact person or bank details to apply a discount rule.

Hosting

A VM, a container or a serverless function all work. If data must stay in a region, check which cloud regions offer your model (Claude is also sold through AWS Bedrock and Google Cloud Vertex AI; OpenAI models through Azure). The approval step changes shape: a web service cannot wait on input(). Save the conversation when the gate fires, send the approval card, and resume when the decision arrives.

Cost control

Every loop turn resends the whole conversation, so cost grows with steps. Your levers: the step limit, max_tokens, short tool outputs (return the five fields needed, not the whole CRM record), and a smaller model for simple requests. Log input and output tokens per request, as the code does, and set a monthly budget alert in the vendor console.

Monitoring

The JSONL log feeds a simple dashboard: requests, escalation rate, steps per request, tool errors, step-limit hits. A jump in escalations usually means the policy changed and nobody updated the tool.

Approvals and governance

Add timeouts (an approval not answered in 24 hours expires), segregation of duties (the requester cannot approve their own discount), and a weekly sample review by the commercial team. Keep the policy text in one place that the tool reads, so legal or finance can change it without a code release.

  • Loop behind SSO, user id in every log line
  • Tools use a least-privilege service account
  • Approval decisions tied to a verified approver identity
  • Step limit, token limit and budget alert set
  • Paused conversations stored, not held in memory
  • Audit log retained per your records policy
  • Regression tests for Sahyadri, Bluewave and Kite before every change

Practice

  1. Add a new rule

    Finance adds a rule: any customer with annual revenue under ₹10 lakh cannot get more than 3% without approval. Where do you change the code, and which test case changes its outcome?

    Hint / model answer

    Update POLICY text so the model sees it, and update evaluate_request so your test oracle agrees. Kite Fintech (₹6 lakh) is affected: a 4% request that was inside the Bronze cap now escalates. Add Kite at 4% to your regression tests.

  2. Break the loop on purpose

    Set MAX_STEPS = 2 and run the Bluewave request. What does the salesperson see, and what does the log show?

    Hint / model answer

    The agent stops after two model calls, before it can escalate, and returns "Stopped after too many steps. Routing this request to the Deal Desk team." The log shows two model_turn events and a stopped event with reason max_steps. That is a safe failure: no discount was promised.

  3. Make the gate asynchronous

    Sketch, in plain English or pseudo-code, how you would change human_gate so the approver answers from Teams an hour later instead of the terminal.

    Hint / model answer

    When request_approval is called: save messages and the pending tool_use_id to a database, post an approval card with the ticket id, and end the request with "awaiting approval". When the card is answered, load the saved messages, append the tool_result containing the decision, and call the loop again from that point. Frameworks such as LangGraph do exactly this with a checkpointer.

The model's reply has stop_reason "tool_use" with two tool_use blocks. What should your loop send back?

  1. Two separate user messages, one per result
  2. Only the first result; the model will ask for the second again
  3. One user message containing both tool_result blocks, each with its tool_use_id
  4. A text message summarising both results

All results go back together in the next user message, matched by id. Separate messages (a) break the required pairing between the assistant's tool requests and their results.

Kite Fintech (Bronze, 16% margin) asks for 5%. What should the Deal Desk do?

  1. Approve: 5% is within the Bronze cap
  2. Escalate: margin after discount would be 11%, below the 12% floor
  3. Escalate to the Regional Head
  4. Reject outright without escalation

The tier cap passes but the margin rule fails, so it needs approval. The Regional Head (c) is only needed above 15%. (a) is the classic shortcut error.

Why is the approval rule enforced in the loop's code rather than only in the system prompt?

  1. Prompts cost more tokens
  2. The API does not accept long prompts
  3. Code runs faster than prompts
  4. A prompt is a request the model usually follows; code is a control it cannot skip

Models follow instructions most of the time, which is not good enough for money. The loop checks the tool name and pauses regardless of what the model intends.

What is the main purpose of MAX_STEPS?

  1. Stop runaway loops and cap cost, failing safe to a person
  2. Make the model answer faster
  3. Limit how many customers can be looked up per day
  4. Satisfy the vendor's rate limits

A stuck model can keep calling tools. The step limit bounds cost and hands the request to a human with a clear message.

In the OpenAI Responses API version, how does the loop know the model has finished?

  1. stop_reason equals "end_turn"
  2. The response contains a "done" flag set by your tools
  3. The output list contains no function_call items
  4. The model returns an empty string

The Responses API signals tool requests as function_call items in output. None means the text in output_text is the answer. (a) is Anthropic's vocabulary.

Key takeaways

  • An agent is a loop: the model asks for tools, your code runs them, results go back, repeat.
  • Handle every stop reason explicitly; only end_turn (or no function calls) is a final answer.
  • Return all parallel tool results together, each matched to its call id.
  • Put the step limit, the approval gate and the audit log in code, not in the prompt.
  • Once you have written this loop, every framework becomes easier to evaluate.
