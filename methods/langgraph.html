Build the Deal Desk as a graph with LangGraph

Build the Meridian Deal Desk twice with LangChain v1 and LangGraph v1: a 30-line agent with create_agent, then an explicit graph where code makes the policy decision, a person approves through interrupt(), and a checkpointer lets the run pause and resume. Then trace it in LangSmith and see how it deploys.

LangChain is the best-known open-source toolkit for building with language models, from the company of the same name. LangGraph is its lower-level sibling for agents that need real control flow: steps, branches, loops, memory, and the ability to stop halfway and wait for a person.

The two were reorganised with their 1.0 releases in October 2025, and the split is now clean. LangChain v1 gives you create_agent, a ready-made tool-calling agent with "middleware" you switch on for things like human approval, summarising long chats or redacting personal data. LangGraph v1 is the engine underneath: you draw your agent as a graph of nodes and edges, and it handles state, checkpoints and resumption. You can start with the first and drop down to the second when you need more control.

Around them sit two commercial products. LangSmith records traces of every run and runs evaluations. LangSmith Deployment, renamed from LangGraph Platform in October 2025, hosts graphs as APIs. Studio (formerly LangGraph Studio) is the visual debugger. The libraries are MIT-licensed and work fine without any of the paid pieces.

Manager's lens

LangGraph's selling point for a business is not cleverness. It is that you can draw the process on a whiteboard, with the approval step as a box, and the code has the same shape. Your process owner, your auditor and your developer can all point at the same diagram. That is rare in AI projects, and it is worth a lot when something goes wrong.

When to pick it

Pick LangGraph when the process has a shape you care about. "Look up, check policy, if it fails get approval, then draft" is a shape. So is "draft, review, revise up to three times, then send". If you can draw the steps and the branches, LangGraph lets you enforce them, rather than hoping a model follows a long prompt.

It is especially strong when a person has to step in partway through. A Deal Desk approval might take ten minutes or two days. LangGraph saves the state at every step, so the run can stop at the approval, the server can restart overnight, and the run resumes from exactly that point when the Sales Manager clicks approve.

Skip it for a five-tool assistant with no branching; create_agent, or the raw API loop, is enough. Skip it too if your team does not write Python or TypeScript; look at Copilot Studio or n8n instead. And be ready for a learning curve: state schemas, reducers and checkpointers are new ideas for most teams.

Strengths

  • The process is explicit: nodes, edges and branches you can draw
  • Pause and resume built in, with durable checkpoints
  • Human-in-the-loop via interrupt() at any node
  • Works with almost any model provider
  • Strong tracing and debugging with LangSmith and Studio

Watch-outs

  • Steeper learning curve than a simple agent loop
  • Older tutorials use pre-1.0 APIs that no longer match
  • Nodes before an interrupt re-run on resume (see the build)
  • The managed platform is where cost and lock-in creep in
  • Easy to over-engineer a graph for a simple job

How it works

A LangGraph agent has three ingredients. State is a typed dictionary that travels through the run: the request, the customer record, the verdict, the decision, the reply. Nodes are plain Python functions that read the state and return updates. Edges connect nodes, and conditional edges choose the next node based on the state.

Look at where the model sits. In the quick create_agent version, the model decides everything: which tool to call, when to escalate, what to write. In the explicit graph, the model reads the salesperson's message and writes the reply. The policy decision in the middle is ordinary Python. This is the most useful design idea on this page: let the model do language, let code do rules.

Interrupts and checkpoints

When a node calls interrupt(payload), the graph stops and hands the payload to whoever is running it. Your app shows it to the approver. When the approver answers, you call the graph again with Command(resume=answer) and the same thread_id. The answer becomes the return value of interrupt(), and the run carries on.

That only works because of the checkpointer, which saves the state after every node under the thread id. In the demo it is InMemorySaver, which forgets everything when the script ends. In production you swap in a database-backed saver (Postgres is the usual choice) and the pause can last days.

One quirk catches everybody. When a run resumes, the node that called interrupt() restarts from its first line. Anything before the interrupt runs again. If that "anything" is raising an approval ticket, you get two tickets. The fix, used below, is to raise the ticket in its own node (escalate) and keep the approval node to nothing but the interrupt.

Step 2: the tools (meridian_tools.py)

"""meridian_tools.py - the Deal Desk agent's tools, in plain Python.

In a real company these functions would call the CRM and the ERP.
Here they read a small in-memory table so the whole agent runs on a laptop.
"""
import difflib
from datetime import datetime

CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian Supplies discount policy (FY 2026-27)
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""

TIER_CAP = {"Bronze": 5, "Silver": 8, "Gold": 12}
MARGIN_FLOOR = 12
APPROVALS = []  # stands in for your ticketing system


def get_customer(customer_id: str) -> dict:
    """Return the customer record for an id such as C-101."""
    record = CUSTOMERS.get(customer_id.strip().upper())
    return record or {"error": f"No customer with id {customer_id}"}


def find_customer(name: str) -> dict:
    """Fuzzy lookup by customer name. Returns the best-matching record."""
    by_name = {c["name"].lower(): c for c in CUSTOMERS.values()}
    query = name.strip().lower()
    for full_name, record in by_name.items():
        if query and (query in full_name or full_name in query):
            return record
    close = difflib.get_close_matches(query, list(by_name), n=1, cutoff=0.5)
    return by_name[close[0]] if close else {"error": f"No customer matching '{name}'"}


def get_discount_policy() -> str:
    """Return the current discount policy text."""
    return POLICY


def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % left after the discount (simplified: margin minus discount)."""
    return round(current_margin_pct - discount_pct, 2)


def request_approval(customer_id: str, discount_pct: float, approver: str, reason: str) -> str:
    """Log an approval request for a discount above policy. A named person must decide."""
    ticket = f"APR-{len(APPROVALS) + 1:04d}"
    APPROVALS.append({"ticket": ticket, "customer_id": customer_id, "discount_pct": discount_pct,
                      "approver": approver, "reason": reason,
                      "raised_at": datetime.now().isoformat(timespec="seconds")})
    return f"{ticket} logged with {approver} for {discount_pct}% on {customer_id}."


def evaluate_request(customer: dict, discount_pct: float) -> dict:
    """The policy written as code: the same rules, checked the same way every time."""
    cap = 3 if customer["late_payments_fy"] >= 2 else TIER_CAP[customer["tier"]]
    margin_after = margin_after_discount(customer["gross_margin_pct"], discount_pct)
    problems = []
    if discount_pct > cap:
        problems.append(f"{discount_pct}% is above the {cap}% cap")
    if margin_after < MARGIN_FLOOR:
        problems.append(f"margin after discount would be {margin_after}%, below the {MARGIN_FLOOR}% floor")
    approver = None
    if problems:
        approver = "Regional Head" if discount_pct > 15 else "Sales Manager"
    return {"within_policy": not problems, "cap_pct": cap, "margin_after_pct": margin_after,
            "problems": problems, "approver": approver}

What this does: holds the customer table and the policy from the course case, plus five tool functions and evaluate_request, the whole discount policy written as code. LangChain reads each function's name, type hints and docstring to describe it to the model, so plain functions work as tools with no decorators. The explicit graph below calls evaluate_request directly; the model never gets a vote on the rules.

Step 3: the quick version (lg_quick.py)

"""lg_quick.py - Deal Desk in about 30 lines with LangChain v1 create_agent."""
import os

from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

import meridian_tools as mt

MODEL = os.getenv("MODEL", "anthropic:claude-sonnet-5-5")   # provider:model-id

agent = create_agent(
    model=MODEL,
    tools=[mt.find_customer, mt.get_customer, mt.get_discount_policy,
           mt.margin_after_discount, mt.request_approval],
    system_prompt=(
        "You are the Deal Desk assistant at Meridian Supplies, Pune. Look the customer up, "
        "read the policy, compute the margin with the tool. Approve only within every rule "
        "and draft a short reply. Otherwise call request_approval and never promise the discount. "
        "request_approval only runs after the approver says yes; if it is rejected, say so and "
        "offer the within-policy maximum instead."),
    middleware=[HumanInTheLoopMiddleware(interrupt_on={"request_approval": True})],
    checkpointer=InMemorySaver(),          # remembers the paused run
)

config = {"configurable": {"thread_id": "deal-0001"}}
result = agent.invoke(
    {"messages": [{"role": "user", "content": "Bluewave Logistics wants 6% off. Can we do it?"}]},
    config=config)

if "__interrupt__" in result:              # paused at the approval gate
    print(result["__interrupt__"][0].value)
    ok = input("Sales Manager - approve this discount? (y/n): ").strip().lower() == "y"
    decision = {"type": "approve"} if ok else {"type": "reject", "message": "Manager declined."}
    result = agent.invoke(Command(resume={"decisions": [decision]}), config=config)

print(result["messages"][-1].content)

What this does:

  • create_agent builds the standard model-calls-tools loop for you, the same loop you would write by hand on the raw API page.
  • HumanInTheLoopMiddleware says: whenever the model tries to call request_approval, stop before running it. Other tools run freely.
  • InMemorySaver is the checkpointer that remembers the paused run. The thread_id names this conversation, so you can resume the right one.
  • If the result contains __interrupt__, the run is paused. The payload lists the tool call and what the reviewer may do (approve, edit, reject or respond). Resuming with Command(resume={"decisions": [...]}) continues the run.

This is a good first agent. Its weakness is that the model still decides whether a request needs approval. If it misreads the policy and approves Kite Fintech at 5%, nothing in the code stops it.

Step 4: the explicit graph (lg_graph.py)

"""lg_graph.py - Deal Desk as an explicit LangGraph StateGraph with a human approval gate."""
import os
from typing import TypedDict

from langchain.chat_models import init_chat_model
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt
from pydantic import BaseModel, Field

import meridian_tools as mt

llm = init_chat_model(os.getenv("MODEL", "anthropic:claude-sonnet-5-5"))


class DealRequest(BaseModel):
    customer_name: str = Field(description="Customer name as written by the salesperson")
    discount_pct: float = Field(description="Discount asked for, in percent")


class DealState(TypedDict, total=False):
    request: str          # what the salesperson typed
    customer: dict        # record from find_customer
    discount_pct: float
    verdict: dict         # output of the policy check
    ticket: str           # approval ticket reference
    decision: str         # what the human approver said
    reply: str            # the drafted reply


def lookup(state: DealState) -> dict:
    parsed = llm.with_structured_output(DealRequest).invoke(
        f"Extract the customer and the discount asked for: {state['request']}")
    return {"customer": mt.find_customer(parsed.customer_name),
            "discount_pct": parsed.discount_pct}


def policy_check(state: DealState) -> dict:
    if "error" in state["customer"]:
        return {"verdict": {"within_policy": False, "problems": [state["customer"]["error"]],
                            "approver": "Sales Manager"}}
    return {"verdict": mt.evaluate_request(state["customer"], state["discount_pct"])}


def decide(state: DealState) -> str:
    return "draft" if state["verdict"]["within_policy"] else "escalate"


def escalate(state: DealState) -> dict:
    v, c = state["verdict"], state["customer"]
    ticket = mt.request_approval(c.get("id", "unknown"), state["discount_pct"],
                                 v["approver"], "; ".join(v["problems"]))
    return {"ticket": ticket}


def approval(state: DealState) -> dict:
    answer = interrupt({"ticket": state["ticket"], "approver": state["verdict"]["approver"],
                        "question": f"Allow {state['discount_pct']}% for {state['customer'].get('name')}?",
                        "problems": state["verdict"]["problems"]})     # the graph pauses here
    return {"decision": answer}


def draft(state: DealState) -> dict:
    facts = {"customer": state["customer"], "asked_pct": state["discount_pct"],
             "verdict": state["verdict"], "approver_decision": state.get("decision", "not needed")}
    msg = llm.invoke(
        "You write for Meridian Supplies' sales team. Draft a short, polite reply to the customer "
        "that matches these facts exactly. Never offer more than the policy or the approver allows.\n"
        f"{facts}")
    return {"reply": msg.content}


builder = StateGraph(DealState)
builder.add_node("lookup", lookup)
builder.add_node("policy_check", policy_check)
builder.add_node("escalate", escalate)
builder.add_node("approval", approval)
builder.add_node("draft", draft)
builder.add_edge(START, "lookup")
builder.add_edge("lookup", "policy_check")
builder.add_conditional_edges("policy_check", decide, ["draft", "escalate"])
builder.add_edge("escalate", "approval")
builder.add_edge("approval", "draft")
builder.add_edge("draft", END)
graph = builder.compile(checkpointer=InMemorySaver())


if __name__ == "__main__":
    config = {"configurable": {"thread_id": "deal-0002"}}
    result = graph.invoke({"request": input("Salesperson: ")}, config=config)
    if "__interrupt__" in result:
        print("\nAPPROVAL NEEDED:", result["__interrupt__"][0].value)
        answer = input("Approver decision (e.g. 'approve 4%' or 'reject'): ")
        result = graph.invoke(Command(resume=answer), config=config)
    print("\n" + result["reply"])

What this does, node by node:

  • DealState lists everything the run carries. Each node returns only the fields it changes.
  • lookup asks the model for one small, checkable thing: the customer name and the percentage, returned as a typed DealRequest. Then it calls find_customer.
  • policy_check runs evaluate_request. No model involved. Same input, same answer, every time.
  • decide is the routing function for the conditional edge: within policy goes straight to draft, anything else to escalate.
  • escalate raises the ticket. It sits in its own node so it runs once, even though the next node will be resumed.
  • approval contains only the interrupt(). The approver's answer, for example "approve 4%", lands in decision.
  • draft gives the model the facts and the decision and asks for a reply that offers nothing beyond them.
  • The builder lines wire the graph exactly as in the figure, and compile(checkpointer=...) makes it pausable.
Tip

Because policy_check is pure Python, you can unit-test it without any API key: assert that Sahyadri at 10% passes, Bluewave at 6% fails on the cap and Kite at 5% fails on margin. Put those three tests in your build pipeline and the policy can never quietly drift.

Step 5: a run, step by step

Bluewave Logistics wants 6% off their next order. Can we do it?
lookup: model extracts {"customer_name":"Bluewave Logistics","discount_pct":6.0} → find_customer("Bluewave Logistics")
{"id":"C-102","tier":"Silver","late_payments_fy":2,"gross_margin_pct":18}
policy_check: evaluate_request(customer, 6.0)
{"within_policy":false,"cap_pct":3,"margin_after_pct":12.0,"problems":["6.0% is above the 3% cap"],"approver":"Sales Manager"}
decide → "escalate" (rule broken, so the graph cannot reach draft without passing approval)
escalate: request_approval("C-102", 6.0, "Sales Manager", "6.0% is above the 3% cap")
APR-0001 logged with Sales Manager for 6.0% on C-102.
approval: interrupt({...}) · graph paused, state checkpointed under thread "deal-0002"
Sales Manager replies "approve 4%". App calls graph.invoke(Command(resume="approve 4%"), config)
draft: model receives facts + decision "approve 4%"
"Thank you for the request. We're able to offer 4% on your next order, approved by our Sales Manager. We'd be glad to process it as soon as you confirm..."

Try Sahyadri at 10%: the graph goes lookup, policy_check, draft and never pauses. Try Kite at 5%: policy_check catches the 11% margin and the graph escalates, whatever the model might have thought.

Step 6: see it in Studio and LangSmith

Tracing needs only environment variables. Add a langgraph.json next to your code and the local Agent Server can serve the graph to Studio.

{
  "dependencies": ["."],
  "graphs": {"deal_desk": "./lg_graph.py:graph"},
  "env": ".env"
}
# .env - read by `langgraph dev`; never commit this file
ANTHROPIC_API_KEY=your-key
MODEL=anthropic:claude-sonnet-5-5
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=your-langsmith-key
LANGSMITH_PROJECT=meridian-deal-desk

# then, in the project folder (pin the CLI version you test with):
pip install "langgraph-cli[inmem]"
langgraph dev        # starts a local Agent Server and prints a Studio link

What this does: langgraph.json tells the server which graph to load (deal_desk, from lg_graph.py) and where the environment file is. The LANGSMITH_* variables switch on tracing, so every run appears in LangSmith with each node, model call, token count and the interrupt. langgraph dev runs the graph locally and gives you a link to Studio, where you see the graph drawn, can submit a request, watch it stop at approval, and type the resume value. The server keeps its own state, so the in-memory checkpointer in the file only matters when you run the script directly.

Note

Tracing sends prompts, tool inputs and outputs to LangSmith. For customer data, check where your LangSmith workspace is hosted and whether a self-hosted option is required by your data protection review.

Taking it to production

Hosting

You have two routes. Run the graph inside your own service (a FastAPI app on your cloud) with a Postgres checkpointer from the langgraph-checkpoint-postgres package. Or use LangSmith Deployment, which as of 2026 offers a fully managed cloud, a hybrid model (LangChain runs the control plane, your servers run the agents and hold the data), self-hosting on your own Kubernetes, and a standalone server you run with Docker. For Indian firms with data residency questions, the hybrid and self-hosted options are usually the ones that pass review. Check current terms in the deployment docs.

Identity and SSO

Put the agent API behind your company login and pass the user's identity into the graph's config, so it reaches every trace. Approvals must come from an authenticated approver, not from whoever holds the thread id. A common mistake: the resume endpoint has no authorisation check, so anyone with a thread id can "approve".

Data access

Nodes call your systems through tool functions using a least-privilege service account. Pass the model only the fields it needs. Under the DPDP Act 2023, the customer data in state and in traces is still data you are responsible for, so set retention for both the checkpointer tables and LangSmith traces.

Cost control

The explicit graph is cheaper than the quick agent: two small model calls per request (extract, draft) instead of a loop of four to six. That is a general lesson. Every decision you move from the model into code saves tokens and removes a failure mode. Add recursion_limit in the run config as a step cap for graphs with loops.

Monitoring and approvals

LangSmith dashboards show latency, errors, tokens and cost per run; build an escalation-rate view from the traces. For approvals, connect the interrupt to the tool your managers already use: a Teams or Slack card, a CRM task, or an email with approve and reject links. Add expiry: a pending approval older than two working days is closed and the salesperson told.

  • Postgres (or equivalent) checkpointer, not in-memory
  • Resume endpoint checks the approver's identity and role
  • Unit tests on the policy node for all five customers
  • Trace and checkpoint retention set
  • Step cap and per-request token budget
  • Approval expiry and notification

Practice

  1. Add a Regional Head path

    Orchid Schools Trust asks for 18%. Trace the graph by hand. Which approver does it reach, and what would you change so that the Regional Head's approval also requires the Sales Manager's first?

    Hint / model answer

    evaluate_request returns approver "Regional Head" because 18% is above 15% (and the margin would be 7%). For a two-level approval, add a second approval node: escalate → approval_sm → (if approved and above 15%) approval_rh → draft. Each approval node holds only its own interrupt().

  2. Spot the double ticket

    A colleague moves the request_approval call into the approval node, just above interrupt(). What happens when the Sales Manager approves?

    Hint / model answer

    On resume, the approval node restarts from its first line, so request_approval runs again and creates a second ticket (APR-0002) for the same request. Keep side effects in a separate node, or make them idempotent (check whether a ticket already exists for this thread).

  3. Decide what stays with the model

    List each step of the Deal Desk and say whether it should be done by the model or by code, with one reason each.

    Hint / model answer

    Model: reading free-text requests (names and numbers in messy language), writing the reply (tone, clarity). Code: customer lookup, policy rules, margin arithmetic, choosing the approver, enforcing the approval. Rule of thumb: if two analysts would always reach the same answer, it belongs in code.

What does the checkpointer make possible in the Deal Desk graph?

  1. Faster model responses
  2. Pausing at the approval and resuming later from the same point
  3. Calling several tools in parallel
  4. Encrypting customer data

The checkpointer saves state after each node under a thread id, which is what lets interrupt() pause a run and Command(resume=...) continue it, even after a restart with a database-backed saver.

A node calls request_approval() and then interrupt(). The approver approves. What happens?

  1. The run continues after interrupt() and the ticket is created once
  2. The graph restarts from START
  3. The run fails with an error
  4. The node re-runs from its first line, so request_approval() runs a second time

On resume, LangGraph restarts the interrupted node from the beginning. Side effects before interrupt() repeat, which is why the ticket belongs in its own node.

In the explicit graph, why does policy_check call evaluate_request instead of asking the model?

  1. Rules applied in code give the same answer every time and can be unit-tested
  2. LangGraph does not allow model calls in nodes
  3. The model cannot read numbers
  4. It is required for tracing to work

Models usually apply rules correctly, but "usually" is not good enough for discounts. Code is deterministic and testable; nodes can call models, they just should not decide policy here.

In the quick create_agent version, what does HumanInTheLoopMiddleware(interrupt_on={"request_approval": True}) do?

  1. Makes a person approve every tool call
  2. Sends every reply to a manager for review
  3. Pauses before request_approval runs and waits for a decision; other tools run freely
  4. Stops the model from calling request_approval at all

Only the listed tool is gated. Tools not in interrupt_on are auto-approved.

Key takeaways

  • LangChain v1's create_agent gets you a working agent fast; LangGraph v1 gives you explicit control.
  • Draw the process as nodes and edges; let the model do language and code do rules.
  • interrupt() plus a checkpointer gives you real pause-and-resume approvals.
  • Nodes restart on resume, so keep side effects out of the interrupting node.
  • LangSmith traces every step; LangSmith Deployment (formerly LangGraph Platform) hosts graphs.
