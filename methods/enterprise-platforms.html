Enterprise agent platforms

Compare the big vendor agent platforms (Salesforce, ServiceNow, SAP, AWS, Google, Microsoft, OpenAI) by the question that actually decides it, where your data already lives, and sketch the Meridian Deal Desk on Agentforce and on Bedrock AgentCore.

Every large enterprise software vendor now sells an agent platform. They fall into two groups, and the difference matters more than any feature list.

Application platforms put agents inside the system where your business data and workflows already live: Salesforce (Agentforce) for customer data, ServiceNow for IT and employee workflows, SAP (Joule) for ERP. The agent inherits the platform's records, permissions and processes on day one.

Cloud platforms give you managed infrastructure to build and run your own agents: AWS (Bedrock Agents and Bedrock AgentCore), Google (Gemini Enterprise Agent Platform, formerly Vertex AI, plus the Gemini Enterprise app), Microsoft (Foundry Agent Service), and OpenAI's developer platform. You bring the data and the logic; they bring hosting, identity, memory, observability and security controls.

Where things stand (as of October 2026)

Names change fast here, so check the vendor's docs before quoting any of this in a proposal.

  • Salesforce Agentforce: agents built from topics, actions and instructions, run by the Atlas Reasoning Engine. A new Agentforce Builder (February 2026) adds Agent Script, mixing deterministic steps with LLM reasoning ("hybrid reasoning"). Grounding comes from Salesforce data and Data 360 (renamed from Data Cloud in October 2025); the Einstein Trust Layer wraps model calls.
  • ServiceNow: AI agents on the ServiceNow AI Platform. At Knowledge 2026 (May) it expanded AI Control Tower into a governance layer that can discover, observe and govern agents including other vendors', announced Action Fabric to expose ServiceNow workflows to any agent over MCP, and launched "AI specialists" under the Autonomous Workforce banner.
  • SAP: Joule, SAP's assistant, plus agents built in Joule Studio. At Sapphire in May 2026 SAP announced a managed Joule Studio, an AI Agent Hub for inventorying agents, LLMs and MCP servers, and a unique identity for each agent by default; a June 2026 announcement described Joule Studio 2.0 within a consolidated Business AI Platform.
  • AWS: Bedrock Agents (the original managed agent service) and Bedrock AgentCore, a set of services to run agents built with any framework: Runtime, Memory, Gateway (turns APIs and Lambda functions into MCP tools), Identity, Code Interpreter, Browser, Observability, Evaluations, Policy, Registry and a managed Harness, among others.
  • Google: the Gemini Enterprise Agent Platform, announced April 2026 as the successor to Vertex AI, with Agent Studio, the open-source Agent Development Kit (ADK), a managed runtime, Model Garden, evaluation tools, agent identity and a registry. Employees reach agents through the Gemini Enterprise app, which absorbed Agentspace. Older material calls the build pieces Vertex AI Agent Builder and Agent Engine.
  • Microsoft: Foundry Agent Service (in Microsoft Foundry, formerly Azure AI Foundry) offers prompt agents, workflow agents and hosted code agents, each with an Entra identity, and publishes to Microsoft 365 Copilot and Teams. For low-code, see Copilot Studio.
  • OpenAI: AgentKit launched in October 2025 (Agent Builder, ChatKit, Connector Registry, Evals). In June 2026 OpenAI said Agent Builder and Evals will no longer be available on its platform from 30 November 2026, pointing developers to the Agents SDK and business users to workspace agents in ChatGPT.
Manager's lens

Don't start with "which platform has the best agents?" Start with "where does the data this agent needs already live, and who already governs it?" An agent's value comes from what it can read and change. A beautiful agent that can't see your customer records is a demo. A plain one sitting on top of them is a product.

When to pick it

Pick an application platform when the agent's job happens inside that application. A service agent answering case questions belongs in the CRM that holds the cases. An IT agent resetting access belongs in the ITSM tool that owns the workflow. You get permissions, audit and process integration for free, and your existing admin team can run it.

Pick a cloud platform when the agent spans several systems, when you have engineers, or when you want framework freedom: build with LangGraph, CrewAI, ADK or the Agents SDK and run it on managed infrastructure with enterprise identity and monitoring.

Don't pick either because a vendor's keynote impressed the CEO. Price is usually consumption-based and hard to predict, and every one of these platforms raises switching costs on purpose. Pilot the specific use case on your own data first, with an exit plan written down.

Strengths

  • Agents act on real records with the platform's permission model.
  • Security, audit and compliance controls built in and already reviewed by your IT team.
  • Vendor support, SLAs and roadmaps that procurement understands.
  • Cloud platforms take on the hard infrastructure: scaling, memory, identity, tracing.
  • Growing support for MCP and A2A makes cross-vendor agents more realistic.

Watch-outs

  • Deep lock-in: agent definitions rarely move between vendors.
  • Consumption pricing is difficult to forecast before real usage.
  • Product names and features change several times a year.
  • Application platforms are weak at data outside their walls without integration work.
  • Every vendor wants to be the agent control plane; you will likely end up with several.

How it works

Strip away the branding and every enterprise platform has the same five layers. Knowing them helps you read any vendor's architecture slide in thirty seconds.

The reasoning layer is where vendors differ most in vocabulary. Salesforce speaks of topics (a job the agent can do, with a description used for classification, a scope and instructions) and actions (Flows, Apex, prompt templates). Copilot Studio speaks of topics and tools; AWS of tools behind a gateway. Same idea: the planner reads descriptions and picks.

The governance column is where they differ most in substance. Some enforce policy outside the model, which is the strong version: AgentCore Policy, for instance, intercepts tool calls through the Gateway and checks them against rules before they run. Others mostly rely on instructions and filters on the model's input and output. Ask which one you are buying.

Build the Deal Desk agent

Two sketches: one on an application platform (Agentforce), one on a cloud platform (Bedrock AgentCore). Both implement the same Meridian policy and the same tool names used across this site.

Assume Meridian runs Salesforce Sales Cloud. Accounts carry three custom fields: Tier__c, Late_Payments_FY__c and Gross_Margin_Pct__c, synced from the ERP. The discount policy is a knowledge article.

  1. Model the data first

    Make sure the five Meridian accounts have tier, late payments and margin populated. If late payments live in the ERP, bring them in through your integration or Data 360. Grounding is only as good as these fields.

  2. Create the agent in Agentforce Builder

    In Agentforce Studio, create an employee-facing agent, "Meridian Deal Desk". Write the role and the hard rule: never confirm an out-of-policy discount; always escalate.

  3. Add a topic: Discount requests

    Classification description: "Salesperson asks whether a customer can have a discount on an order." Scope: discount checks and approval requests only. Instructions: the policy rules in order (late-payment cap first, then tier cap, then the 12% margin floor).

  4. Add three actions

    get_customer: a Flow that finds the Account by name and returns the three fields. evaluate_discount: an invocable Apex method or Flow with formulas that returns cap, margin after and APPROVE or ESCALATE; this is deterministic, so put it in Agent Script or code, not in the LLM's hands. request_approval: a Flow that creates a discount request record and submits it to a Salesforce approval process routed to the Sales Manager, or the Regional Head above 15%.

  5. Test in preview and the testing tools

    Agent previews use mock data so the live org isn't touched. Run Sahyadri 10%, Bluewave 6% and Kite 5%, and check the reasoning summary shows the right actions in the right order.

  6. Deploy to the Salesforce console and Slack

    Salespeople use it from the opportunity page or Slack. Approvals appear in the normal Salesforce approval queue.

Assume Meridian's customer data is in an AWS database and engineers prefer Python. AgentCore runs the agent; we write the agent with Strands Agents (AWS's open-source framework), though LangGraph, CrewAI or ADK would also work.

  1. Scaffold the project

    Install the AgentCore CLI and create a Strands project with Bedrock as the model provider.

    npm install -g @aws/agentcore
agentcore create --project-name MeridianDealDesk --name DealDesk \
  --language Python --framework Strands --model-provider Bedrock \
  --memory none --build CodeZip
cd MeridianDealDesk
agentcore dev        # run locally and chat with it

    What this does: installs the CLI, generates a project with an agent entry file, and starts a local test server. These commands follow AWS's 2026 getting-started guide; check it for the current flags.

  2. Write the tools and agent

    In the generated agent file, define the tools and the agent:

    from strands import Agent, tool

# Demo data. In production get_customer queries your database via a Gateway tool.
CUSTOMERS = {
    "sahyadri hospitals": {"id": "C-101", "tier": "Gold", "late": 0, "margin": 22},
    "bluewave logistics": {"id": "C-102", "tier": "Silver", "late": 2, "margin": 18},
    "orchid schools trust": {"id": "C-103", "tier": "Gold", "late": 0, "margin": 25},
    "kite fintech": {"id": "C-104", "tier": "Bronze", "late": 0, "margin": 16},
    "trident engineering": {"id": "C-105", "tier": "Silver", "late": 1, "margin": 20},
}

@tool
def find_customer(name: str) -> dict:
    """Look up a Meridian customer by name. Returns id, tier, late payments, margin %."""
    return CUSTOMERS.get(name.strip().lower(), {"error": "customer not found"})

@tool
def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % after a discount (simplified: current minus discount)."""
    return current_margin_pct - discount_pct

@tool
def request_approval(customer_id: str, discount_pct: float, approver: str, reason: str) -> str:
    """File a discount approval request. Use only when a request is outside policy."""
    # Production: call the approvals service; a human decides.
    return f"Approval request filed for {customer_id} at {discount_pct}% with {approver}."

SYSTEM = (
    "You are the Meridian Deal Desk agent. Cap is 3% if late payments >= 2, "
    "else Bronze 5%, Silver 8%, Gold 12%. Margin after discount must be >= 12%. "
    "Approve only within both rules; otherwise call request_approval "
    "(Regional Head above 15%, else Sales Manager). Never promise unapproved discounts."
)

agent = Agent(system_prompt=SYSTEM,
              tools=[find_customer, margin_after_discount, request_approval])

    What this does, line by line: @tool turns each Python function into a tool the model can call, using the function's name, type hints and docstring as its description. CUSTOMERS is demo data standing in for the real database. find_customer returns the row or a clear "not found". margin_after_discount does the subtraction exactly. request_approval is a stub; in production it calls a real approvals service. The system prompt carries the policy, and the last line creates an agent that can use all three tools.

  3. Move tools behind Gateway

    For production, expose find_customer and request_approval as Lambda functions or APIs registered in AgentCore Gateway, which presents them to the agent as MCP tools. Now the same tools can serve other agents and frameworks too.

  4. Add Policy and Identity

    Use AgentCore Policy to enforce rules on tool calls outside the model, for example that request_approval may only name "Sales Manager" or "Regional Head", and that no tool can write a discount record directly. Use AgentCore Identity with your identity provider (Entra ID, Okta and others) so the agent acts for an authenticated salesperson.

  5. Deploy and observe

    Run agentcore deploy, then agentcore invoke --prompt "Bluewave Logistics wants 6% off". Traces flow to AgentCore Observability (OpenTelemetry-compatible), and Evaluations can score runs against your test set.

Either way, a good run looks the same from the salesperson's side:

Orchid Schools Trust wants 13% for the annual stationery contract.
find_customer(name="Orchid Schools Trust")
{"id":"C-103","tier":"Gold","late":0,"margin":25}
Gold cap is 12%, so 13% is above the cap even though margin after (25 − 13 = 12%) meets the floor. Not above 15%, so Sales Manager.
margin_after_discount(current_margin_pct=25, discount_pct=13)

request_approval(customer_id="C-103", discount_pct=13, approver="Sales Manager", reason="1 point above Gold cap of 12%; margin after 12% meets floor.")
Approval request filed for C-103 at 13% with Sales Manager.
13% needs approval: it's 1 point over Orchid's Gold cap. Margin stays at the 12% floor. I've sent it to the Sales Manager. Meanwhile you can confirm 12% is available within policy.

Taking it to production

Enterprise platforms are sold on production readiness, so hold them to it. These are the questions to put to your vendor or platform team, in order.

Identity

Does the agent act as the signed-in user, as a service identity, or both? Each platform now gives agents their own identities (Entra identities in Foundry, per-agent identities in SAP and Google, AgentCore Identity on AWS). Insist that every action in the audit log shows both the agent and the human it acted for.

Data access and residency

Which records can the agent read, and does it respect the user's sharing rules? Where are prompts and outputs processed and stored, and is there an Indian region option where you need one? What do the model providers retain? Under the DPDP Act, customer contact data in prompts is personal data; under RBI and SEBI rules, regulated entities have further outsourcing and data localisation obligations to check with compliance.

Cost control

Get the pricing unit in writing (per conversation, per action, per credit, per token) and run a two-week pilot that measures real consumption. Set budgets and alerts per agent. Watch for agents that loop: a planner that calls five tools per request costs five times what you modelled.

Monitoring and evaluation

You want traces of every run (which tools, what inputs, what outputs), a test set that runs before every change, and a dashboard a business owner reads. M10 and M12 cover what good looks like.

Approvals and policy

Keep human approval in the platform's native approval mechanism, not in the chat. Where the platform supports policy enforcement outside the model, use it for your hard rules. Instructions are advice to the model; a policy engine is a lock.

  • Use case piloted on your own data with measured consumption
  • Agent identity and user identity both recorded in the audit log
  • Data residency, retention and model-provider terms reviewed by legal
  • Hard rules enforced outside the model where possible
  • Approvals through the native approval process
  • Test set and traces in place before go-live
  • Exit plan: where the business rules and data would go if you left
Watch out

Several vendors now pitch themselves as the governance layer for all your agents, including other vendors' (ServiceNow's AI Control Tower and SAP's AI Agent Hub both lean this way). That may suit you. But decide on one inventory of agents for the company, or in two years nobody will know how many agents you run or what they can touch. M13 covers agent governance.

Case · Customer service

A consumer durables company picks two platforms

A typical outcome in a large Indian company: service agents built on the CRM platform, because cases, warranties and customer history already live there, and a cloud-platform agent for the supply chain team, because shortage analysis needs ERP, logistics and email data together. The CIO's real decision is not which vendor wins but how both agents are inventoried, monitored and costed in one place.

Practice and quiz

  1. Map your data

    For your own organisation (or a company you know), list the five systems that hold the most important business data. For each, name the vendor's agent offering, if any. Which platform would you pilot first, and why?

    Hint / model answer

    Rank systems by how many agent use cases need their data. If most ideas need CRM data, the CRM vendor's agent platform is the natural pilot. If ideas cut across three or four systems, a cloud platform plus MCP connectors to each system is usually cleaner.

  2. Vendor questions

    Write ten questions for a vendor demo of an agent platform. At least three must be about cost and three about governance.

    Hint / model answer

    Cost: pricing unit, how a looping agent is billed, budget caps and alerts. Governance: where policy is enforced (inside or outside the model), how agent identity appears in audit logs, how approvals work, data retention by model providers. Plus: how to export agent definitions, A2A/MCP support, Indian region availability, and what changed in the last two releases.

  3. Find the policy gap

    In the AgentCore sketch, the policy rules live in the system prompt. Which rule would you move into AgentCore Policy, and which into code, and why?

    Hint / model answer

    Put "request_approval approver must be Sales Manager or Regional Head" and "no direct write of discounts" into Policy, because they constrain actions and must never be bypassed. Put the cap and margin calculation into a deterministic tool (an evaluate_discount function), because arithmetic should not depend on the model. The prompt keeps only the conversational guidance.

What is the best first question when choosing an enterprise agent platform?

  1. Which vendor has the largest model?
  2. Where does the data this agent needs already live, and who governs it?
  3. Which platform has the most prebuilt agents?
  4. Which vendor announced agents first?

Agents create value by acting on data and workflows. The platform that already holds and governs that data usually wins on cost, security and speed.

In Agentforce, what does a topic's classification description do?

  1. Encrypts the conversation
  2. Lists the Apex classes the agent may call
  3. Sets the price per conversation
  4. Helps the reasoning engine decide which topic a request belongs to

Like tool descriptions elsewhere, the classification description is what the planner reads to route a request to the right topic.

AgentCore Gateway's main job is to:

  1. Turn APIs and Lambda functions into MCP-compatible tools for agents
  2. Host the chat user interface
  3. Train custom models
  4. Store conversation memory

Gateway converts existing services into tools. Memory is a separate AgentCore service, and model training isn't part of AgentCore.

Why is policy enforced outside the model stronger than a rule in the system prompt?

  1. It is cheaper
  2. The model reads it more carefully
  3. It blocks a disallowed tool call even if the model is confused or manipulated
  4. It makes the agent respond faster

A prompt is guidance the model can ignore under pressure or prompt injection. An external check intercepts the action itself.

  4. AgentKit only works inside Salesforce

Key takeaways

  • Application platforms (Salesforce, ServiceNow, SAP) put agents on your system of record; cloud platforms (AWS, Google, Microsoft, OpenAI) give you infrastructure to run your own.
  • Choose by where the data lives and who governs it, not by keynote demos.
  • Every platform has the same five layers; ask which ones the vendor really owns and where policy is enforced.
  • Names and products change several times a year: verify against current docs before you commit.
