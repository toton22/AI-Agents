Google Agent Development Kit: agents that deploy in one command

Build the Meridian Deal Desk agent with Google's Agent Development Kit, test it in the adk web dev UI with a built-in approval step, and choose between Cloud Run and Agent Runtime for production.

45 min readTracked in your progress

Skill level

Time to first agent
30 to 60 minutes
Typical cost

Best for

The Agent Development Kit, ADK for short, is Google's open-source framework for building agents. You describe an agent in a few lines of Python (a name, a model, an instruction, a list of tools) and ADK runs the loop, keeps the conversation in a session, and gives you a browser-based dev UI to poke at it. When it works, one command ships it to Google Cloud.

Google released it as open source in 2025. As of October 2026 it ships for Python, TypeScript, Go, Java and Kotlin, and the docs have moved to adk.dev. This page uses Python, pinned to google-adk==2.11.0.

The big change this year was ADK 2.0, generally available for Python from 19 May 2026. Under the hood, ADK moved from a tree of agents calling each other to a graph-based execution engine. For you that means a new Workflow class where agents and plain Python functions are nodes joined by edges. The older SequentialAgent, ParallelAgent and LoopAgent classes still work, but in 2.11 they log a deprecation warning pointing you to Workflow.

Names on the Google Cloud side changed too. In April 2026 Vertex AI became part of the Gemini Enterprise Agent Platform, and Vertex AI Agent Engine was renamed Agent Runtime. You will see both names in tutorials for a while; the ADK command is still adk deploy agent_engine.

Manager's lens

ADK's pitch is a short path from laptop to a governed cloud service. If your company already runs on Google Cloud, with identity, billing and logging sorted, ADK lets a small team ship an agent into that estate without a separate platform project. If you are on Azure or AWS, the framework still works, but you lose much of that advantage.

When to pick it

Pick ADK when you expect more than one agent. Its core idea is composition: an agent can hold sub-agents, a workflow can chain agents with ordinary functions, and an agent on another server can join over the A2A protocol. A sales-operations assistant that hands pricing questions to a Deal Desk agent and contract questions to a legal agent is a natural ADK shape.

Pick it, too, when you want developer tooling in the box. adk web gives a local chat UI with a trace of every event, tool call and state change. adk eval runs saved test conversations. adk deploy packages and ships. Most other code frameworks leave you to assemble these yourself.

Think twice if your team has no Python skills and no plans to hire them; Gemini Enterprise and Agent Builder give you the Google stack with less code. And if your agent is mostly about searching long documents, LlamaIndex has deeper document tooling.

Strengths

  • Tools are plain Python functions; docstrings become tool descriptions
  • Multi-agent composition and graph workflows are built in
  • Excellent local dev UI, plus evaluation and deploy commands
  • Sessions and state handled for you, with persistent options
  • A2A support for agents on other servers or other frameworks

Watch-outs

  • Moving fast: 2.0 changed the runtime and deprecated older workflow classes
  • Tool confirmation is experimental and not supported with every session store
  • The dev UI is unauthenticated and must never face the internet
  • Best experience assumes Google Cloud

How it works

Four pieces. An agent (Agent, also called LlmAgent) holds the model, instruction and tools. A Runner takes a user message, runs the agent and yields a stream of events. A SessionService stores the conversation and a dictionary called state. And tools are the functions the model may call.

Tools are just functions

Give an agent a Python function and ADK reads its name, type hints and docstring to build the tool description the model sees. Write the docstring for the model, not for a programmer: say when to use the tool. Wrap a function in FunctionTool(..., require_confirmation=True) and ADK pauses before running it until a human confirms. You can also pass a function instead of True, so only risky inputs need a human.

Composition: sub-agents and workflows

There are two ways to combine agents, and the difference matters. With sub_agents, the model decides at run time whether to hand the conversation to a specialist. Flexible, but you are trusting the model's routing. With a Workflow, you draw the graph yourself: the analyst always runs, then the writer always runs. Predictable, auditable and usually what compliance wants for a defined process. ADK's old SequentialAgent, ParallelAgent and LoopAgent are fixed patterns of the same idea and remain in the docs as template workflows.

Sessions and state

Each conversation is a session holding the event history and a state dictionary. Set output_key="verdict" on an agent and its final answer is saved into state, where the next agent can read it with {verdict} inside its instruction. Prefixes change the scope: user: keys follow the user across sessions, app: keys are shared across the app, temp: keys last one turn. The default store is in memory; for production you switch to a database or Agent Runtime sessions. M06 covers the concepts.

Build the Deal Desk

  1. Install and lay out the folder

    ADK expects one folder per agent, containing agent.py with a variable called root_agent. adk create meridian_deal_desk builds the skeleton and asks for your key.

    python3 -m venv .venv && source .venv/bin/activate
pip install "google-adk==2.11.0"

# Folder layout ADK expects (adk create meridian_deal_desk builds this for you)
# meridian_deal_desk/
#   __init__.py      contains:  from . import agent
#   agent.py         defines root_agent (below)
#   .env             GOOGLE_API_KEY=...   (ADK adds .env to .gitignore)
  2. Add your key

    Use a Gemini API key from Google AI Studio for a pilot, or your Google Cloud project for anything serious. Keys stay in .env, which ADK adds to .gitignore.

    # meridian_deal_desk/.env  -- Gemini API key from Google AI Studio
GOOGLE_GENAI_USE_ENTERPRISE=0
GOOGLE_API_KEY=your-key-here

# ...or run on your company's Google Cloud project instead of an API key
# GOOGLE_GENAI_USE_ENTERPRISE=1
# GOOGLE_CLOUD_PROJECT=meridian-ai-prod
# GOOGLE_CLOUD_LOCATION=asia-south1
  3. Write the agent

    Save this as meridian_deal_desk/agent.py:

    import os
from datetime import datetime

from google.adk.agents import Agent
from google.adk.tools import FunctionTool, ToolContext

MODEL = os.getenv("MODEL", "gemini-flash-latest")

# --- Meridian data (in production: your CRM and ERP) ---
CUSTOMERS = {
    "C-101": {"id": "C-101", "name": "Sahyadri Hospitals", "tier": "Gold",
              "annual_revenue_lakh": 48, "late_payments_fy": 0, "gross_margin_pct": 22},
    "C-102": {"id": "C-102", "name": "Bluewave Logistics", "tier": "Silver",
              "annual_revenue_lakh": 19, "late_payments_fy": 2, "gross_margin_pct": 18},
    "C-103": {"id": "C-103", "name": "Orchid Schools Trust", "tier": "Gold",
              "annual_revenue_lakh": 31, "late_payments_fy": 0, "gross_margin_pct": 25},
    "C-104": {"id": "C-104", "name": "Kite Fintech", "tier": "Bronze",
              "annual_revenue_lakh": 6, "late_payments_fy": 0, "gross_margin_pct": 16},
    "C-105": {"id": "C-105", "name": "Trident Engineering", "tier": "Silver",
              "annual_revenue_lakh": 22, "late_payments_fy": 1, "gross_margin_pct": 20},
}

POLICY = """Meridian discount policy
1. Maximum discount by tier: Bronze 5%, Silver 8%, Gold 12%.
2. Customers with 2 or more late payments this financial year are capped at 3%.
3. Gross margin after discount must stay at or above 12%
   (margin_after = current_margin - discount).
4. Anything above the cap needs Sales Manager approval;
   anything above 15% needs Regional Head approval."""


def get_customer(customer_id: str) -> dict:
    """Return the customer record for an id such as 'C-101'."""
    return CUSTOMERS.get(customer_id.strip().upper(),
                         {"error": f"No customer with id {customer_id}"})


def find_customer(name: str) -> dict:
    """Find a customer by (part of) their name, e.g. 'Sahyadri'."""
    hits = [c for c in CUSTOMERS.values() if name.lower() in c["name"].lower()]
    if len(hits) == 1:
        return hits[0]
    return {"error": f"{len(hits)} matches for '{name}'",
            "candidates": [c["name"] for c in hits]}


def get_discount_policy() -> str:
    """Return Meridian's current discount policy text."""
    return POLICY


def margin_after_discount(current_margin_pct: float, discount_pct: float) -> float:
    """Gross margin % left after a discount (simplified: margin minus discount)."""
    return round(current_margin_pct - discount_pct, 2)


def request_approval(customer_id: str, discount_pct: float, approver: str,
                     reason: str, tool_context: ToolContext) -> str:
    """Raise an approval request to 'Sales Manager' or 'Regional Head'.
    Use whenever a discount breaks the tier cap, late-payment cap or margin floor."""
    ticket = f"APR-{datetime.now():%Y%m%d-%H%M%S}"
    log = tool_context.state.get("approvals", [])
    log.append({"ticket": ticket, "customer_id": customer_id,
                "discount_pct": discount_pct, "approver": approver, "reason": reason})
    tool_context.state["approvals"] = log
    return f"{ticket}: {approver} approved {discount_pct}% for {customer_id}."


INSTRUCTION = """You are the Meridian Deal Desk assistant for the sales team.
For every discount request:
1. Identify the customer with find_customer or get_customer.
2. Read the policy with get_discount_policy.
3. Work out the cap: tier cap, or 3% if late_payments_fy >= 2.
4. Call margin_after_discount and compare with the 12% floor.
5. If the discount is within the cap AND the margin stays >= 12%, approve it
   and draft a two-line reply the salesperson can send.
6. Otherwise call request_approval with the right approver (Sales Manager,
   or Regional Head if the discount is above 15%) and a one-line reason.
Never promise a discount above policy unless request_approval came back approved.
Show the numbers you used."""

root_agent = Agent(
    name="meridian_deal_desk",
    model=MODEL,
    description="Checks discount requests against Meridian's policy.",
    instruction=INSTRUCTION,
    tools=[
        get_customer,
        find_customer,
        get_discount_policy,
        margin_after_discount,
        FunctionTool(request_approval, require_confirmation=True),
    ],
)
  4. Open the dev UI

    From the parent folder, start the dev server and chat with the agent in your browser. The events panel shows every tool call, its arguments and the state after each step.

    # run from the folder that CONTAINS meridian_deal_desk/
adk web --port 8000      # browser dev UI at http://localhost:8000
adk run meridian_deal_desk   # or chat in the terminal

What this code does, in plain English

  • MODEL comes from an environment variable, defaulting to gemini-flash-latest, so IT can switch models without a code change.
  • The data block holds Meridian's five customers and the policy text. Swap these for CRM and document calls later.
  • Five functions become five tools. Notice there is no decorator. ADK reads the function name, the types (customer_id: str) and the docstring. Lookups return a dictionary with an error key instead of crashing, so the model can recover by asking a clarifying question.
  • request_approval takes an extra parameter, tool_context. ADK fills that in itself; the model never sees it. We use it to append each approval to session state, which gives a per-conversation record of exceptions.
  • INSTRUCTION spells out the procedure: identify, read policy, work out the cap, check margin, then approve or escalate. It ends with the one rule that can never bend.
  • root_agent wires it up. The last tool is wrapped in FunctionTool(..., require_confirmation=True), which is the human checkpoint. Every call to request_approval pauses until someone clicks confirm or reject.

Running it from your own code

The dev UI is for building. Inside an application you drive the agent through a Runner and a session. This script starts a session with some state, asks a question and prints tool calls and the final answer:

import asyncio

from google.adk.runners import InMemoryRunner
from google.genai import types

from meridian_deal_desk.agent import root_agent


async def main():
    runner = InMemoryRunner(agent=root_agent, app_name="deal_desk")
    session = await runner.session_service.create_session(
        app_name="deal_desk", user_id="priya.sales",
        state={"region": "West", "salesperson": "Priya"},   # starting state
    )
    question = types.Content(role="user", parts=[types.Part(
        text="Sahyadri Hospitals wants 10% off their next order. Can we do it?")])
    async for event in runner.run_async(user_id="priya.sales",
                                        session_id=session.id, new_message=question):
        for call in event.get_function_calls():
            print(f"-> {call.name}({call.args})")
        if event.is_final_response() and event.content and event.content.parts:
            print(event.content.parts[0].text)

asyncio.run(main())

In plain English: the Runner bundles the agent with an in-memory session store; create_session opens a conversation for one user with starting state; run_async streams events, and we print the function calls and whichever event is marked final. Outside the dev UI, a confirmation pause arrives as a special event; your app shows its own approval screen and sends the answer back as a function response named adk_request_confirmation.

Two agents in a fixed order

Now split the work: an analyst decides, a writer drafts. With ADK 2.x, a Workflow makes the order explicit. Put this in its own folder, meridian_pipeline/agent.py:

from google.adk import Agent, Workflow

from meridian_deal_desk.agent import MODEL, find_customer, get_discount_policy, margin_after_discount

analyst = Agent(
    name="deal_analyst",
    model=MODEL,
    instruction="Check the discount request against policy. Output: customer, cap, "
                "margin after discount, and APPROVE or ESCALATE with one reason.",
    tools=[find_customer, get_discount_policy, margin_after_discount],
    output_key="verdict",            # saved into session state
)

writer = Agent(
    name="reply_writer",
    model=MODEL,
    instruction="The analyst's verdict is: {verdict}\n"
                "Write a two-line reply the salesperson can send. If the verdict "
                "is ESCALATE, say the request is with the Sales Manager.",
    output_key="reply",
)

# A fixed pipeline: analyst always runs first, writer always second.
root_agent = Workflow(name="deal_pipeline", edges=[("START", analyst, writer)])

The analyst's answer lands in state as verdict; the writer's instruction pulls it in with {verdict}. The edge list ("START", analyst, writer) is the whole process map. You can add plain Python functions as nodes too, which is how you put a deterministic policy check between two model steps.

Letting a coordinator route

When you can't predict the order, let a coordinator choose. Here a general sales-operations assistant hands discount questions to the Deal Desk:

from google.adk.agents import Agent

from meridian_deal_desk.agent import MODEL, root_agent as deal_desk

root_agent = Agent(
    name="sales_ops_assistant",
    model=MODEL,
    instruction="You help Meridian's sales team. Send any discount or pricing "
                "question to meridian_deal_desk. Answer general questions yourself.",
    sub_agents=[deal_desk.clone()],  # a copy, so the original app stays independent
)

ADK gives the coordinator a transfer ability; the sub-agent's description and name tell it when to use it. We pass a clone() so the original Deal Desk app keeps working on its own in the same dev UI.

Taking it to production

Hosting: two good choices

Cloud Run packages the agent as a container service in your project. You control networking, scaling and who can call it. Agent Runtime (formerly Vertex AI Agent Engine) is Google's managed home for agents, with sessions, memory and scaling handled for you. Both are one command:

# Option A: Cloud Run (you manage the service; good when IT wants it in your VPC)
adk deploy cloud_run --project=meridian-ai-prod --region=asia-south1 \
  meridian_deal_desk -- --no-allow-unauthenticated

# Option B: Agent Runtime (formerly Vertex AI Agent Engine; managed sessions and scaling)
adk deploy agent_engine --project=meridian-ai-prod --region=asia-south1 \
  --display_name="Meridian Deal Desk" meridian_deal_desk

The --no-allow-unauthenticated flag after -- is passed through to Cloud Run so the service rejects anonymous calls. Pick asia-south1 (Mumbai) or asia-south2 (Delhi) if you want the service hosted in India; check which models are offered in your chosen region before you commit.

Identity and data access

Users sign in through your front end with Google Workspace or another SSO provider; the agent service trusts only that front end, enforced by Cloud Run IAM. The agent itself runs as a Google Cloud service account. Give that account read access to the CRM connector and nothing else. Keep API keys and connector secrets in Secret Manager, not in .env files baked into images.

Approvals in production

Here's the catch. ADK's tool confirmation is labelled experimental, and the docs say it is not supported with DatabaseSessionService or VertexAiSessionService, the persistent stores you'd use in production. So for a deployed Deal Desk, make request_approval create a ticket in your workflow system and return "PENDING". The agent tells the salesperson the request is with the manager; a webhook or a second conversation picks it up when the manager decides. ADK 2.0's graph workflows also include a human-input pattern for pausing a defined process. Either way, approval is a business process, and it should live where your other approvals live.

Cost and monitoring

Choose the smallest Gemini model that passes your test set, and set output limits through generate_content_config. Turn on --trace_to_cloud or --otel_to_cloud when deploying to get traces in Google Cloud's observability tools. Save the three reference cases as an eval set and run adk eval before every release; M10 shows how to grow that set.

Opening up to other agents with A2A

If another team's agent (built on a different framework, perhaps) needs Deal Desk decisions, expose it over the Agent2Agent protocol. ADK can wrap any agent as an A2A server, and adk deploy cloud_run --a2a adds an A2A endpoint at deploy time. ADK marks parts of its A2A support as experimental. M09 explains what A2A is for.

# pip install "google-adk[a2a]==2.11.0"
from google.adk.a2a.utils.agent_to_a2a import to_a2a

from meridian_deal_desk.agent import root_agent

# An ASGI app that serves an A2A agent card plus the A2A endpoints.
# Run with:  uvicorn a2a_server:app --port 8001
app = to_a2a(root_agent, port=8001)
Watch out

adk web and adk api_server are unauthenticated development servers. Run them on your laptop or a trusted network only. Every year somebody puts a dev server on a public IP; don't let it be your Deal Desk.

A fixed process with three judgement calls

Consider an anonymised FMCG distributor in western India. Its stock-out process had five steps, three of them needing judgement (which substitute, which vendor, how much). Practice

  1. Confirm only when it matters

    Replace require_confirmation=True with a function so that only discounts above 15% need confirmation in the dev UI, while smaller exceptions are logged and approved automatically. Is that a good policy for Meridian?

    Hint / model answer

    Write def needs_human(customer_id: str, discount_pct: float, approver: str, reason: str, tool_context) -> bool: return discount_pct > 15 and pass it as require_confirmation=needs_human. Technically easy; as policy, it breaks Meridian's rule that anything above the cap needs the Sales Manager. Code should implement policy, not quietly rewrite it.

  2. Add a deterministic check node

    In the Workflow version, add a plain Python function between the analyst and the writer that recomputes the cap and margin from the customer record and overrides the analyst if it disagrees.

    Hint / model answer

    Workflow nodes can be functions that take node_input. Have the analyst output structured fields (customer id, discount), recompute with the same rules as margin_after_discount, and pass a corrected verdict forward. This "model proposes, code verifies" pattern is covered in M07.

  3. Write an eval set

    Use the dev UI to save the three reference conversations (Sahyadri 10%, Bluewave 6%, Kite 5%) as an eval set, then run adk eval against it after changing the instruction.

    Hint / model answer

    The dev UI has an Eval tab where you can add the current session to an eval set. Check both the final response and the tool trajectory: an agent that reaches the right answer without calling margin_after_discount got lucky and will fail on the next customer.

How does ADK know what a plain Python function tool does?

  1. You must write a JSON schema by hand
  2. It reads the function name, type hints and docstring
  3. It asks the model to guess from the code
  4. Only from a YAML config file

ADK builds the tool declaration from the signature and docstring, which is why a clear docstring is the most important line of each tool.

In ADK 2.x Python, what is the recommended way to run an analyst agent and then a writer agent in a fixed order?

  1. Put both in sub_agents and hope
  2. Two separate Runners
  3. A Workflow with edges from START to analyst to writer
  4. A LoopAgent with max one iteration

SequentialAgent still works but is deprecated in favour of graph Workflow. sub_agents lets the model choose, which is the opposite of fixed.

An agent has output_key="verdict". How does the next agent use it?

  1. By writing {verdict} in its instruction, which ADK fills from session state
  2. By calling a tool named verdict
  3. It can't; agents don't share data
  4. Through an environment variable

Session state is the shared notebook. Templated keys in instructions are filled from state at run time.

Why does this page recommend a ticket-based request_approval for the production Deal Desk rather than relying on require_confirmation?

  1. Confirmation dialogs are too slow
  2. Confirmation only works with Gemini
  3. Managers dislike dialogs
  4. The feature is experimental and not supported with the database or Agent Runtime session stores used in production

The ADK docs list those limitations. Approvals that can take hours belong in your workflow system anyway.

A colleague wants to share the adk web URL with the sales team for a quick trial. Your advice?

  1. Fine, it has a login page
  2. Fine if the laptop has antivirus
  3. No: it is an unauthenticated dev server; deploy to Cloud Run with IAM instead
  4. Only on weekends

The CLI help states the dev server is unauthenticated and for trusted networks only. A pilot deserves a proper deploy with access control.

Key takeaways

  • ADK turns Python functions into tools and gives you a dev UI, evals and deploy commands in one kit.
  • ADK 2.0 introduced graph Workflows; the older sequential, parallel and loop agents are deprecated in Python.
  • Use sub_agents when the model should route and Workflow when the process is fixed.
  • Tool confirmation is handy in development, but production approvals belong in a ticketing flow.
  • Deploy to Cloud Run or Agent Runtime (formerly Vertex AI Agent Engine), never expose the dev server.
